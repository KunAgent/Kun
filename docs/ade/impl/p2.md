## P2-01 终端 agent：登记、PTY、退出上报（M，K M）

设计：05 §6.1。依赖：P0-08、P0-10。

| 文件 | 改什么 |
| --- | --- |
| `kun/src/server/routes/execution-units.ts`（新） | `POST /v1/execution-units`（`{ kind: 'terminal-agent', harnessId, workspaceId?, workspace, title, parentThreadId? }` → `{ unitId, tokens: { workerCallback, hookIngest }, endpoint }`）；`POST /v1/execution-units/:id/exit`（`{ exitCode, signal? }`） |
| `kun/src/services/terminal-agent-registry.ts`（新） | 记录终端 agent 单元；退出时 ActivityStore `closed`；应用重启时这些行带 `restoredUnconfirmed` |
| `src/main/terminal/terminal-pty-ipc.ts` | `terminal:create` 新增可选参数 `agent?: { harnessId, taskWorkspaceId? }`：先调 kun 登记，拿到令牌后把 `KUN_WORKER_ENDPOINT`、`KUN_WORKER_TOKEN`、`KUN_UNIT_ID` 注入 PTY 环境；命令来自 harness 定义的 `terminal` 字段（`argv` / `flag` 注入初始任务）；PTY 退出时上报 |
| `src/main/terminal/pty-launch-gate.ts` | 终端 agent 与普通终端共用现有启动闸门 |
| renderer 终端面板 | "新建终端"菜单加"在终端里运行 agent"子菜单（列出 transport 为 terminal 或有 `terminal` 字段的 harness） |

中断推断：主进程在 `terminal:write` 里检测写入的是 `\x03` 或单独的 `\x1b`，对终端 agent 调 `POST /v1/execution-units/:id/interrupt-hint`，kun 记 `inferredInterrupt`，下一个 `Stop` hook 按 cancelled 处理（行上 `provenance: 'inferred'`）。

测试：登记 → PTY 环境变量存在 → 退出上报 → 行 closed；应用退出时 PTY 与登记一起清理。

## P2-03 托管 hooks（M，K）

设计：05 §6.2–§6.3。依赖：P2-01、P2-02。

| 文件 | 内容 |
| --- | --- |
| `kun/src/harness/hook-config-writer.ts`（新） | 为执行单元生成临时配置目录 `dataDir/ade/hooks/<unitId>/`：每个 hook 事件的命令为 `<kun 可执行文件> worker hook <event>`；返回需要追加的启动参数或环境变量（由 harness 定义的 `terminal.hooks` 决定） |
| `kun/src/server/routes/activity.ts` | `POST /v1/activity/hooks`：`hook-ingest` scope；请求体上限 64 KiB；解析后只保留事件名、sessionId、工具名、时间 |
| `kun/src/services/hook-activity-mapping.ts`（新） | 05 §6.3 的映射表（按 harness 分表） |
| 退出清理 | 单元结束时删除临时配置目录 |

**先录制再写规则**：每个 harness 的 hook 事件 payload 先用真实 CLI 录制一份（脱敏后放 `kun/src/harness/__fixtures__/hooks/<harness>-<version>/`），映射测试基于录制数据。

测试：每个事件的映射；未知事件忽略；超大 payload 截断；不写用户全局配置（测试断言 `~/.claude` 等目录未被修改——用临时 HOME）。

## P2-06 AI 行归属（M，K R）

设计：11 §6。依赖：P1-03、P1-17。

| 文件 | 内容 |
| --- | --- |
| `kun/src/ade/attribution-ledger.ts` | `record(workspaceId, entry)`、`attribute(workspaceId, path, content)` → `Array<{ line, unitId?, harnessId? }>` |
| 写入事件来源 | Kun 原生文件写入工具的结果钩子；ACP `writeTextFile`（P1-04）与 diff 内容（P1-03）；Claude SDK / Cursor 的编辑类工具事件（在各自映射器里取工具输入的新文本片段） |

## P2-09 Mission Control 弹出窗口（S，M R）

依赖：P1-20。

- 主进程新建一个辅助 `BrowserWindow`（沿用现有辅助窗口的创建与关闭规则：关闭辅助窗口不退出应用；主窗口关闭时一起关闭），加载 `board` 路由并带 `?popout=1`。

## P2-11 外部 harness 的计划构建（M，K R）

设计：07 §10。依赖：P0-12、P1-12。

- 计划执行时，若所选 harness 不是 `kun`：跳过提示协议注入，改为 `TaskWorkspaceService.create` → 以计划内容为任务说明派一个 worker（总管可以是当前线程，也可以不开 team：直接在一对一线程上绑定任务工作区执行）→ 完成后打开审查面板 → 用户选择合入方式。
- Kun 原生的计划构建保持现有提示协议不变。
- 准入：`plan-build` 场景要求隔离工作区（P0-05 的规则表已包含）。
