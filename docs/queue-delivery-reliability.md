# 排队输入交付链路：故障与修复说明

## 故障原因

2026-09-08 的故障中，两条输入停留在 `admissionPending`：
queued turn 元数据已经写入，但 canonical user item 尚未写入 session。
Manager 返回 `stale_turn_fence`，原回合完成后队列也没有继续推进。

原因相互叠加：

1. queued turn 没有执行租约，写正文时未使用当前线程的有效租约。
2. turn ID 在整个写入函数返回后才保存，途中失败无法精确回滚。
3. 两个 busy enqueue 分支的提交和恢复逻辑不一致。
4. 查询接口把未提交记录当成可执行队列，前端误确认送达。
5. 调度器遇到一次阻塞或失败后等待外部事件，没有独立重试。
6. 排队时提前发布 user-item 事件，前端据此切换了当前回合。

## 提交与权限

- 当前有效执行租约授权同一线程内的写入，包括另一条待执行输入。
  跨线程写入仍被拒绝；旧回合捕获的 fence 仍保持旧代际，不能借用新租约。
- 调度器离开上一回合的异步 fence 上下文，独立提升下一条输入。
- busy 输入统一经过一个串行提交函数，第一笔写入之前保存准确的 turn ID。
- 提交顺序为 pending 元数据、canonical user item、完成标记。
  途中失败按准确 ID 回滚；若只是完成响应丢失，查询后确认原提交。
- 同一个 `clientRequestId` 在锁内重新核对，不重复建立已提交 turn。
- 在线和启动恢复采用相同规则：正文存在则补齐提交，正文不存在则回滚。
  读取失败不能当作“正文不存在”。
- 排队正文持久化后不立即发布执行事件；真正提升时再发布 user-item，
  使前端当前回合与实际执行一致。

## 调度、停止和关闭

临时写入失败、CAS 冲突或租约阻塞采用每线程退避重试，间隔从 250 毫秒递增，
最高 5 秒。提升成功和队列清空取消重试。Stop 暂停本线程后续输入；
租约释放产生的容量通知不会解除暂停。显式继续或新的队列提交恢复调度。

本地执行槽立即释放，Manager 确认租约释放后再通知调度器。
应用关闭时取消重试计时器，并等待正在进行的提升操作结束。

## 客户端契约

`GET /v1/threads/:id/queued-turns` 提供以下无正文回执：

| 字段 | 含义 |
| --- | --- |
| `queuedTurns` | 已提交、等待执行的输入 |
| `pendingAdmissions` | 提交尚未确认，可按请求 ID 恢复 |
| `settledTurns` | 已开始或已结束的 turn，含可选 `terminalCode` |

部分提交失败返回 HTTP 503 和 `queue_admission_uncertain`，附带请求 ID、
失败阶段及可重试标记。原始 Manager 错误只记录在运行日志。

前端保留原输入，并按其 `clientRequestId` 查询送达状态。其他回合仍在运行，
不能作为本消息已提交的证据。确认中的行显示“正在确认”；
未知结果重试始终使用同一份请求和 ID，不等待原回合结束。

已确认提交失败的行保留为可见失败项。用户明确重试该失败任务时使用新请求 ID；
未确认的请求继续沿用原 ID。前台和后台共用确认逻辑。
恢复查询明确返回 `activeTurn: null` 时，等待中的队列不能伪装为运行中的 agent。

## 验证与使用

- 真实 HTTP Manager、remote stores 和执行租约集成测试验证：
  活动回合后排入两条消息，模型按 FIFO 收到正文，session 中每条只有一个 user item。
- 注入元数据写入、正文写入、commit 写入和响应丢失故障，检查回滚、原地修复及并发幂等。
- 检查旧 fence、跨线程隔离、自动重试、Stop 暂停、租约释放及显式继续。
- 前端检查确认失败、无关活动回合、pending/committed/terminal 回执、导航恢复及确认提示。
- 回归图片、Write/Design 上下文、Graph 引导、队列编辑、删除和顺序调整。

新构建生效后，启动恢复会处理历史 pending 记录。本地队列仍保留正文和请求 ID，
可按回执重新确认；不需要破坏性迁移或手工清空会话。
