# 合同修订稿生成（Word 原生修订痕迹 + 批注）—— redline-docx 工具说明

> 这是合同审查（C6）/ 补充修订（C9）场景**首选的修订稿交付方式**。当用户给了一份
> `.docx` 合同并要求"审核修订/帮我改"时，**默认在原文上生成 Word 原生修订痕迹
> （track changes：逐字插入下划线 / 删除删除线）+ 批注气泡（说明每处改动理由）**，
> 交付一份用户能在 Word/WPS 里直接"接受/拒绝修订"的修订稿，**像真人律师改的稿子一样**。

## 一、为什么必须用这种形式（铁律）

❌ **错误做法**（禁止）：把条款挑出来，写成"【原文】…… / 【修订后】……"的大段对照块，
或新建一个文档逐条罗列。这不是合同修订稿，是审查笔记，用户还得自己誊回原文。

✅ **正确做法**：在**原始 docx 本身**上，对**真正变化的字符片段**打修订痕迹：
- 删除的字 → `删除线`（Word 里显示为带删除线、可"拒绝/接受"的删除修订）
- 新增的字 → `下划线彩色`（Word 里显示为插入修订）
- 未改动的字 → **原样保留**，不动
- 每处改动旁边挂一个**批注气泡**，写清楚为什么改、依据什么

效果应与"像人一样逐字修订"的样式一致：一句话里只有变化的几个词带痕迹，其余照旧。

## 二、工具位置与运行

工具：`bin/redline-docx`（纯 Python 标准库，无需第三方依赖）

```bash
# 应用修订，产出修订稿
python3 <expert>/bin/redline-docx apply \
  --in   "原始合同.docx" \
  --edits edits.json \
  --out  "合同-修订稿.docx" \
  --author "合同专家"

# 校验修订稿是否成功写入痕迹/批注
python3 <expert>/bin/redline-docx verify --in "合同-修订稿.docx"
```

`verify` 返回 `insertions`（插入痕迹数）、`deletions`（删除痕迹数）、`comments`（批注数）。
交付前**必须 verify**，确认数值 > 0 且与预期修订条数匹配。

## 三、修订指令 JSON 规范

```json
{
  "author": "合同专家",
  "date": "2026-06-27T00:00:00Z",
  "edits": [
    {
      "find": "原文中要修改的【精确锚文本】",
      "replace": "改成的新文本（空串\"\"表示纯删除）",
      "comment": "这处为什么改、依据什么法条或商业逻辑"
    },
    {
      "find": "原文中的某句话",
      "insert_after": "在这句话后面补插的内容",
      "comment": "补插理由"
    },
    {
      "anchor": "用来定位的某个现有段落文本（如某条标题）",
      "insert_paragraph": "要新增的一整条新条款全文",
      "comment": "新增此条款的理由"
    }
  ]
}
```

### edit 的四种模式

| 模式 | 字段组合 | 效果 |
|---|---|---|
| 字符级替换 | `find` + `replace` | 对 find→replace 做最小差异，只给变化片段打 ins/del 痕迹 |
| 锚后插入 | `find` + `insert_after` | 在 find 之后插入新文字（纯插入痕迹） |
| 纯删除 | `find` + `replace:""` | 删除 find（删除线痕迹） |
| 整段新增 | `anchor` + `insert_paragraph` | 在 anchor 段落后新增一整段（整段插入痕迹） |

## 四、编写 edits 的关键纪律

1. **find/anchor 必须与原文逐字一致**（含标点、全半角、空格）。匹配不到会被
   计入 `edits_missed`，必须先从提取的原文里复制锚文本，不要凭记忆敲。
2. **find 要足够唯一**：取一整句或带前后文的片段，避免短词在多处命中（默认改第一处）。
3. **replace 只写"改完后的完整句"**，工具会自动 diff 出哪几个字是删、哪几个字是增——
   不要自己手动拆增删，写整句即可，痕迹更自然。
4. **每条 edit 尽量配 comment**：批注是"修订理由书"，写清风险点 + 依据（法条/商业逻辑）+
   建议方向。批注里可保留谈判提示（如"此处示例为乙方所在地，甲方可争取改为甲方所在地"）。
5. **金额/主体/日期等事实不臆造**：拿不准的改动，用占位 `【待确认：…】` 或只在批注里提示，
   不要在正文痕迹里编造具体数字。
6. **改动要克制**：只改有风险/有问题的地方，不做无意义的措辞润色，否则满屏痕迹反而难读。

## 五、标准流程（C6 审查 → 修订稿）

```
1. 解析原始 docx 文本（提取段落纯文本，作为 find 锚文本来源）
2. 按 contract-review-engine 完成逐条风险审查，形成"问题条款 + 改法 + 依据"
3. 把每个改法翻译成一条 edit（find=原文锚，replace=改后句，comment=理由）
4. 写出 edits.json
5. redline-docx apply 产出 修订稿.docx
6. redline-docx verify 校验痕迹/批注数
7. present_files 交付修订稿；正文回复里只给"修订要点摘要 + 风险等级"，
   不再重复大段原文/修订后对照
```

## 六、交付话术

交付时附简短说明：
- "已在原合同上做了 N 处修订（M 处删除、K 处插入）并加了 N 条批注，可在 Word/WPS
  里逐条接受或拒绝。"
- 正文给一个**精简的修订要点表**（条款 | 改了什么 | 风险等级 | 依据），不贴大段原文。
- 末尾附标准免责声明。

## 七、兼容性说明

- 生成的痕迹是 OOXML 原生 `<w:ins>/<w:del>` 和 `comments.xml`，Microsoft Word、WPS
  均原生识别，可"接受全部/拒绝全部修订"、可显示/打印批注。
- 工具只增量改动命中段落，其余内容（表格、页眉页脚、样式）原样保留。
