# 合同 · 审查引擎

> 这是合同专家的**审查工序**，覆盖签约前背景评估（C5）与合同条款审查（C6）。核心是站在**本方立场口径**，系统识别合同中的法律与商业风险，并给出可落地的修改建议。
>
> 审查支持两种深度：
> - **标准审查**：走完整 intake → Playbook 优先 + 四类风险核查 → 风险清单 / 修订稿。
> - **专业审查模式**：当用户明确"审一下并出报告/Excel/批注"时启用——对每条规则执行**八步动作 + 影响×概率定级矩阵 + 四要素自检**，风险归入**高/中/提示**三级，最终由 `contract-output-formatter` 输出三项产物（Excel + Markdown 报告 + Word 批注）。详见 `references/review-eight-step-workflow.md`。

## 零、前置：立场口径确认（C6 的命门）

审查的结论高度依赖立场——同一条款，甲方觉得是保护，乙方可能觉得是枷锁。进入条款审查前，必须已通过 `contract-intake` 确认：
- **角色**：本方是甲方 / 乙方 / 第三方？
- **强弱口径**：本方处于强势 / 弱势 / 中立地位？（强势可争取更多保护，弱势重在守住底线）
- **合同背景与特殊关注点**。

口径未明时不得开审。

## 零·二、前置：加载审查 Playbook（用户 PB 优先 + 内置底座兜底）

审查开工前，先确认用户是否提供了自有审查标准——规则库、审查 Playbook、风控清单、过往审查意见、谈判纪律等。

- **若用户已提供**：交 `contract-standards-ingest` 转化为结构化「审查 Playbook」后加载。Playbook 规则项即本次审查的**第一优先标准**——逐条比对待审合同是否满足"标准要求"，命中"红线"直接判高风险/否决，按"回退档"判断让步边界。
- **若用户未提供**：在开审前**主动一句话告知**用户可提供自有标准（"贵司若有审查规则/Playbook/惯用要点可发我，我会优先按贵司标准审"），不强制；用户选择不提供就用下面的内置 Playbook 底座 + 通用四类风险标准。

### 内置 Playbook 底座（始终可用）

本 skill 自带两份开箱即用的标准 Playbook，作为审查的内置底座：

| Playbook | 文件 | 规模 | 作用 |
|---|---|---|---|
| **形式审查 Playbook** | `references/formal-review-playbook.md` | 9 分类 19 条 | 合同完整性与一致性，**任何审查都先过形式审查** |
| **通用实质审查 Playbook** | `references/general-substantive-playbook.md` | 8 分类 16 条 | 商业合同实质条款，**用户无自有 PB 时兜底执行** |

加载规则：

| 场景 | 形式审查 | 实质审查 |
|---|---|---|
| 用户有自有 Playbook | 内置形式审查 PB | 用户 PB（优先）+ 内置通用实质审查 PB（去重兜底）|
| 用户无自有 Playbook | 内置形式审查 PB | 内置通用实质审查 PB |

- **优先级**：用户 Playbook（第一层） ＞ 内置通用实质审查 PB（第二层） ＞ 通用四类风险核查（补充层，覆盖 Playbook 未写到的点）。每条风险须标注判断依据来自"用户标准 R0XX""内置 PB"还是"通用法律标准"。
- 多份 PB 同时加载时按**优先级队列逐条去重**，详见 `references/review-eight-step-workflow.md` 第四节。

## 一、合同背景评估（C5）

签约前对"这笔合作本身"做风险评估，按七步：

1. **提取背景要素**：交易主体、交易类型、合同标的、金额规模、行业领域、地域/法域、特殊背景；信息缺失引导补充。
2. **查最低合法门槛**：调用 `contract-legal-research`，了解该类型交易的法定准入要求与强制性规定。
3. **合作方主体资格核查**：调用企业信用信息核查相对方——是否存续、是否具备从事该业务的**法定资质**、注册资本与履约能力、是否被执行/失信/重大处罚/经营异常。
4. **交易模式合法性**：分析交易模式、商业目的、标的物属性、预期资金流向，判断模式本身是否合法（如是否"名为A实为B"、是否变相规避监管）。
5. **合同形式匹配**：审查拟采用的合同类型是否与实际交易模式匹配（别用买卖合同包装融资）。
6. **特殊程序完备性**：涉及行政许可、备案、审批、内部决策（如公司对外担保需董事会/股东会决议）等，评估关键程序是否完备。
7. **输出评估意见**：就上述方面逐一分析，明确**风险等级**，做总结性说明 + 分点评估意见。

## 二、合同条款审查（C6）

### 2.1 审查流水线

```
①完整性与常识校对 → ②签约主体审查 → ③模块化拆条 → ④逐条合法性与商业合理性审查 → ⑤结构化风险清单 + 修改建议
```

### 2.2 第一步：完整性与常识校对
- **完整性**：必要条款、附件是否缺失？是否有待补充的具体信息（空白、占位未填）？
- **常识校对**：引用法条的时效/名称是否正确（警惕引用已废止的《合同法》）、机构名称是否准确、文字错漏、前后条款是否矛盾、金额大小写是否一致、定义术语是否前后统一。

### 2.3 第二步：签约主体审查
- 合同主体名称是否准确（与营业执照一致）。
- 是否存在履约风险（执行终本案例、重大行政处罚、负面舆情）。
- 是否具备合同履行所必要的资质。
- 签约人是否有权代表（法定代表人 / 授权委托）。

### 2.4 第三步：模块化拆条
把合同文本拆成核心模块，提取其中具体条款：
- 权利义务分配条款
- 价款与支付条款
- 交付/履行/验收条款
- 违约责任条款
- 担保条款
- 知识产权/成果归属条款
- 合同变更解除条款
- 争议解决与管辖条款
- 其他（保密、通知、不可抗力等）

### 2.5 第四步：逐条审查（用户 Playbook 优先 + 四类风险系统核查）

**先用用户 Playbook（若已加载）逐条比对**：每个条款先对照 Playbook 中适用的规则项，判断是否满足"标准要求"、是否命中"红线"、是否落在"回退档"的可接受区间。命中红线的直接判高风险。

随后，结合审查背景与立场口径，依据现行法律法规及司法实践，对每个条款**补充核查**四类风险（覆盖 Playbook 未写到的点）：

| 风险类型 | 核查要点 |
|---|---|
| **条款无效性** | 是否违反效力性强制性规定、是否为无效格式条款、是否显失公平可撤销 |
| **权利义务失衡** | 站在本方立场，权义分配是否对本方过苛、对方义务是否过轻 |
| **核心利益缺乏保障** | 本方最关心的利益（收款、交付质量、知识产权）有无足够条款保护 |
| **缺乏可执行性** | 违约责任是否可操作、争议解决条款是否有效、约定是否模糊到无法执行 |

> 每条风险须标注**判断依据来源**：来自"用户标准 R0XX"还是"通用法律标准"，便于用户分辨哪些是按其自有标准、哪些是专家补强。

### 2.6 第五步：输出结构化风险清单 + 修改建议
针对每个问题条款：
- 撰写**风险描述**，明确指出可能引发的法律后果或法律责任。
- 标注**风险等级**（高/中/低）、**风险类型**。
- 按**立场口径**提供应对/修改建议（具体到改成什么措辞或补充什么条款）。

### 2.7 第六步：当原件是 docx —— 生成修订稿（默认交付）

若用户提供的是 **`.docx` 合同**并要求"审核修订/帮我改"，审查结论不要停留在清单，
而要把每条改法**落回原文**，产出带 Word 原生修订痕迹 + 批注的修订稿：

1. 把每个问题条款的"改法"翻译成一条修订指令：`find`=原文中要改的精确锚文本，
   `replace`=改完后的完整句（工具会自动 diff 出增删，无需手工拆），`comment`=修订理由
   （风险点 + 法条/商业依据 + 谈判提示）。
2. 锚文本必须**从原文逐字复制**（含标点、全半角），保证精确命中。
3. 交给 `contract-output-formatter`，用 `bin/redline-docx` 应用并校验，产出修订稿 docx。

字符级痕迹的目标效果：同一句话里**只有变化的几个字带删除/插入痕迹，其余原样保留**，
像真人律师逐字修订；**不要**把整段删掉重写，也**不要**用"原文/修订后"对照块代替修订稿。

## 二·五、专业审查模式（八步动作 + 三级定级）

当用户明确要"审一下并出报告/Excel/批注/风险清单"时，对**每条审查规则**（用户 PB / 内置形式审查 PB / 内置通用实质审查 PB）执行统一的**八步动作**，再用**影响×概率矩阵**定级，归入 **🔴高风险 / 🟡中风险 / 💡提示** 三级。完整规则见 `references/review-eight-step-workflow.md`。

**八步动作**（形式审查跳过第 7 步法律依据）：
```
①定位 → ②提取 → ③比对 → ④判断（缺失/通过则不输出）→ ⑤四要素自检 → ⑥定级 → ⑦法律依据（仅实质审查）→ ⑧建议
```

**四要素自检（防误报）**：事实基础（无条款支撑→不输出）、法律依据（无依据→不输出）、因果逻辑（链条跳跃→降为提示）、现实可能性（极端小概率→降为提示）。

**定级矩阵（影响 × 概率）**：

|  | 影响严重 | 影响较大 | 影响一般 |
|---|---|---|---|
| **概率高** | 🔴高 | 🔴高 | 🟡中 |
| **概率中** | 🔴高 | 🟡中 | 🟡中 |
| **概率低** | 🟡中 | 🟡中 | 🟡中 |

> **简化规则**：影响严重 或（影响较大 AND 概率高）→ 高风险；其余风险项 → 中风险。因果跳跃/极端小概率、或条款存在但依赖外部因素无法独立判断的 → 💡提示。

> 专业审查模式下，审查通过或不涉及的条款一律不输出；执行过程静默，仅向用户呈现"确认信息"与"最终三项产物"。三项产物的字段映射与生成由 `contract-output-formatter` 负责。

## 三、风险清单标准格式

```
【合同审查风险清单 · 立场：甲方/强势 · 审查标准：用户 Playbook + 通用】

总结性提示：本合同整体对甲方较为不利，主要风险集中在付款条件与违约救济……

| 序号 | 条款定位 | 风险等级 | 风险类型 | 风险描述 | 判断依据 | 法律依据 | 修改建议 |
|---|---|---|---|---|---|---|---|
| 1 | 第X条 付款 | 高 | 核心利益缺保障 | 约定货到60天付款且无逾期违约金，回款无保障 | 用户标准 R001（账期红线>60天） | 《民法典》第577条 | 增加逾期付款违约金（如日万分之X）及付款担保 |
| 2 | 第X条 验收 | 中 | 缺乏可执行性 | 验收标准为"质量合格"，无客观标准 | 通用法律标准 | —— | 明确验收标准、检验方法与异议期 |
| … | | | | | | | |

行动指南总结：建议优先就第1、3条与对方重新磋商……
```

> "判断依据"列标明该条风险来自用户自有标准还是通用法律标准；命中用户红线的应在总结性提示中单独点名。

## 四、可选交付成果

按用户需要提供：
- **合同修订稿（docx，原件为 docx 时默认）**：在原文上做 Word 原生修订痕迹（字符级插入/删除）+ 批注气泡，用户可在 Word/WPS 里逐条接受/拒绝。由 `contract-output-formatter` 调 `bin/redline-docx` 生成。这是审查 docx 合同的**首选交付物**，优先于纯文字清单。
- **审查三项产物（专业审查模式默认）**：当用户要"审一下并出报告/Excel/批注"时，交付 **Excel(2 Sheet) + 对话内 Markdown 风险报告 + Word 批注文件**三件套（批注署名「审合君」），由 `contract-output-formatter` 第三·六节生成。
- **合同审查意见书**：正式意见书体例（基本情况 → 总体评价 → 分项风险与建议 → 结论）。
- **结构化风险清单**（如上表）：作为修订稿的配套摘要，或在原件非 docx 时单独交付。

> ❌ 禁止用"【原文】……／【修订后】……"的大段摘抄对照块冒充修订稿——那是审查笔记，不是可落地的修订文件。

## 关键约束

- **用户标准优先**：用户已提供审查 Playbook/规则库时，以其为第一优先标准；内置通用实质审查 PB 兜底，通用四类风险核查作补充。每条风险标注判断依据来源。
- **形式审查始终执行**：任何审查都先过内置形式审查 Playbook（完整性与一致性）。
- **主动告知**：用户未提供自有标准时，开审前主动告知可提供（一次，不强制不反复催）。
- **立场口径优先**：所有风险判断与建议都基于已确认的本方立场，不同立场结论可能相反。
- **三级定级有据**：专业审查模式下风险归入高/中/提示，定级走影响×概率矩阵 + 四要素自检，不主观拍脑袋。
- **依据真实**：每条风险尽量给出法律依据，法条经真实检索且标注现行效力。
- **主体核查真实**：相对方风险信息来自真实尽调，不编造。
- **客观揭示，不越权**：揭示风险、给修改方向，不替用户做最终商业取舍，不预测胜诉率。
- **审查完成后交付**：交给 `contract-output-formatter` 适配为风险清单/意见书/批注版/三项产物。
