# 测试设计方法论

本 skill 提供测试设计的核心方法论和最佳实践，供专家在测试设计过程中参考。

## 一、需求分析

### 1.1 明确需求边界

- 仔细提取需求文档中明确描述的功能点
- 识别需求中的"应该"、"必须"、"需要"等关键词
- 排除需求中未提及的扩展场景和假设性功能

### 1.2 反向推导隐含前置功能

需求可能隐含了一些前置功能，这些功能虽未被明确提及，但为实现需求必须存在。

**检验标准**（防止过度设计）：
- ✅ **必须包含**：删除这个功能后，用户无法完成需求中描述的功能
- ❌ **不必包含**：删除这个功能后，用户虽然不方便，但仍能完成需求的功能

示例：需求说"用户需要选择自定义模板"，隐含了"用户必须能够创建自定义模板"（但"模板预览"不是必须的）。

### 1.3 判断需求类型和选择最优方法

根据需求特征选择最优测试方法：

| 需求特征 | 推荐方法 | 示例场景 |
|---------|---------|---------|
| 包含多个输入参数或状态变化 | 场景法 | 用户登录、订单流程 |
| 参数有明确范围或类型 | 等价类划分 + 边界值分析 | 年龄验证、金额校验 |
| 涉及状态转换或生命周期 | 状态转换测试 | 订单状态、任务状态 |
| 多条件组合判断 | 判定表 | 权限校验、优惠计算 |
| 数据流向复杂 | 数据流法 | 多系统集成、数据处理 |

**组合使用**：复杂需求可组合多种方法（如：场景法 + 边界值分析），目标是用最少用例覆盖所有功能点。

## 三、测试设计流程

### 步骤 1：获取需求内容

- **TAPD 链接**：通过 tapd-woa 连接器获取需求内容
- **CNB 链接**：通过 cnb CLI 读取 Issue/PR 内容（参见「八、CNB Issue/PR 读取方法」）
- **需求文本**：直接使用用户提供的内容

### 步骤 2：明确功能点

逐条列出需求中的所有功能点（包括反向推导的隐含必须前置功能）

### 步骤 3：分析功能点关联

判断哪些功能点可以在一个测试场景中一起验证：

- 相同流程中的功能点 → 必须合并
- 需要相同前置条件的功能点 → 必须合并
- 无关联的功能点 → 独立测试

### 步骤 4：输出 JSON 数据

设计完成后，按以下 JSON 结构组织输出。脚本 `scripts/render_html.py` 会渲染为 HTML 报告。

```json
{
  "requirement": "需求描述",
  "requirement_url": "来源链接（如有）",
  "analysis": {
    "function_points": ["功能点1"],
    "preconditions": ["前置条件"],
    "methods_used": ["等价类划分"]
  },
  "test_cases": [
    {
      "id": "TC-001",
      "module": "模块名",
      "test_point": "测试点",
      "precondition": "前置条件",
      "steps": ["步骤1", "步骤2"],
      "expected": "期望结果",
      "priority": "P0"
    }
  ],
  "statistics": { "total": 5, "p0": 2, "p1": 2, "p2": 1 },
  "coverage_checklist": [
    {"item": "正常路径已测试", "covered": true}
  ]
}
```

写入 JSON 文件后调用脚本渲染：

```bash
python3 skills/test-design/scripts/render_html.py <json_path>
```

## 四、覆盖检查清单

- [ ] 正常路径已测试
- [ ] 备选流程已覆盖
- [ ] 边界条件已验证
- [ ] 无效输入已处理
- [ ] 状态转换已验证（如适用）
- [ ] 异常场景已包含

## 五、效率原则

- **功能点驱动**：基于功能点设计用例，不基于假设场景
- **完整性优先**：功能点必须涵盖用户的完整业务流程，包括隐含的必须前置功能
- **防止功能蔓延**：反向推导时严格遵循"必须"标准，不推导可选扩展功能
- **强制合并**：多个功能点能在一个用例中验证时，必须合并为一个用例
- **严格遵循需求范围**：只为需求明确描述的功能设计测试用例，但补充隐含的必须前置功能
- **避免过度设计**：不测试需求未提及的边缘场景或扩展功能
- **最小化用例数量**：通过功能点合并，用最少用例覆盖所有功能点
- **基于业务影响确定优先级**：核心功能 P0，次要功能优先降低

## 六、范围控制规则

**禁止超出需求范围：**
- ❌ 不要为需求未提及的功能设计测试用例
- ❌ 不要添加"可能需要"、"建议测试"的额外场景
- ❌ 不要扩展需求中未明确的业务逻辑
- ❌ 不要将可以合并的用例拆分成多个
- ❌ 不要过度反向推导，包含"虽然有用但不是必须的"功能

**必须包含的功能：**
- ✅ 只测试需求文档明确要求的功能
- ✅ 只测试需求中明确定义的输入范围
- ✅ 只测试需求中明确说明的业务流程
- ✅ 多个功能点能合并时必须合并为一个用例
- ✅ 补充隐含的必须前置功能：用户完成需求所必须能做的功能

**效率检验：**
- 反向推导的功能点数量是否合理？
- 是否有功能点可以进一步合并到一个用例中？
- 是否有过度推导的功能（不是必须的）？

## 七、关键限制

- 用例步骤要高层次、粗粒度（合并相关操作，从用户执行角度思考）
- 只基于功能点设计用例，多个功能点能合并就必须合并
- 最终输出中不包含分析过程、思考过程

## 八、CNB Issue/PR 读取方法

CNB 是腾讯内部代码协作平台。当用户提供 CNB 链接时，通过 cnb CLI 读取需求内容进行测试设计。

### 8.1 URL 解析

| 类型 | 示例 URL | repo | number |
|------|---------|------|--------|
| **Issue（Bug 单）** | `https://cnb.woa.com/genie/genie/-/issues/51581` | `genie/genie` | `51581` |
| **PR（需求单）** | `https://cnb.woa.com/genie/genie/-/pulls/46014` | `genie/genie` | `46014` |

**解析规则**：URL 路径第 4 段（`/-/` 后的部分）决定类型：
- `issues/<number>` → Issue
- `pulls/<number>` → PR

### 8.2 认证检查

所有 cnb 命令执行前，必须先检查连接状态：

```bash
cnb status 2>&1
```

- `✅ 已登录` → 可以继续
- `❌ 未登录` 或报错 → **告知用户**：「CNB（司内版）连接器未登录，请前往 WorkBuddy「专家」→「连接器」→「CNB（司内版）」进行授权」

### 8.3 认证注意事项（实战踩坑沉淀）

> ⚠️ 以下为必守规则，违反会导致读取失败：

1. **登录命令**：`cnb login --woa`（**必须加 `--woa`**，否则登录的是 cnb.cool 而非 cnb.woa.com）
2. **环境变量覆盖**：`CNB_TOKEN` 环境变量会覆盖 OAuth2 令牌，**所有 cnb 命令前必须 `unset CNB_TOKEN`**
3. **令牌存储**：OAuth2 token 存储在 `~/.cnb/token`，cnb CLI 自动读取
4. **过期处理**：token 过期（报 401）时重新执行 `cnb login --woa`
5. **仓库格式**：`--repo` 参数为 `组织/仓库`（无 `.git` 后缀），如 `genie/genie`
6. **PR 编号类型**：`get-pull` 的 `--number` 参数为**字符串类型**

### 8.4 读取 Issue（Bug 单）

```bash
# 必须 unset CNB_TOKEN，否则 OAuth2 不生效
unset CNB_TOKEN && cnb issues get-issue --repo <org/repo> --number <number>
```

输出包含：标题、描述、状态、优先级、标签、处理人、评论数、正文（含截图链接）

### 8.5 读取 PR（需求单）

PR 信息量较大，分步读取：

**第 1 步：获取 PR 基本信息**
```bash
unset CNB_TOKEN && cnb pulls get-pull --repo <org/repo> --number <number>
```

**第 2 步：获取提交列表（了解改动内容）**
```bash
unset CNB_TOKEN && cnb pulls list-pull-commits --repo <org/repo> --number <number> --page-size 50
```

**第 3 步：获取评论列表（了解讨论上下文）**
```bash
unset CNB_TOKEN && cnb issues list-issue-comments --repo <org/repo> --number <number>
```

### 8.6 读取后的需求提取

从 CNB 返回内容中，提取以下信息用于测试设计：

**Issue（Bug 单）**：
- **标题**：Bug 概述，通常包含模块名和问题描述
- **正文**：版本的描述、复现步骤、期望行为、实际行为、截图/日志
- **标签**：模块归属、版本号、类型
- **优先级**：P0/P1/P2

**PR（需求单）**：
- **标题**：需求概述
- **描述**：需求详细说明、改动背景
- **文件变更**：了解改动范围（哪些模块受影响）
- **提交记录**：了解功能实现的细粒度变更
- **讨论**：评审中的需求澄清和决策

### 8.7 从 Bug 单到测试用例设计

Bug 单的测试设计应包含两类：
1. **回归验证**：确认 Bug 已修复 → 按照 Bug 描述的复现步骤执行，验证不再复现
2. **关联场景**：围绕 Bug 场景扩展测试 → 类似输入/类似环境/类似操作
3. **边界补充**：如果 Bug 发生在特定条件下，补充该条件的边界测试

### 8.8 从 PR 需求单到测试用例设计

PR 需求单的测试设计应包含：
1. **新增功能**：PR 中新增的功能点逐一覆盖
2. **改动影响**：变更可能影响到的现有功能
3. **回退兼容**：如果 PR 涉及重构或替换，需验证回退场景
