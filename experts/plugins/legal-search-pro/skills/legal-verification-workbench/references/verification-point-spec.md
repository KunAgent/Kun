# 核验点抽取规则（verification-point-spec）

脚本 `extract-verification-points.mjs` 构建**待核验点**列表，输出 `verification/verification_points.json`。核验点有**两个来源、按优先级合并**：

1. **AI 语义复盘声明（首选）—— `claims.json`**：**意见定稿之后**，专家像第三方复核一样**重新通读成稿**，对其中每个"靠了法律依据"的句子，语义判断它**关联的是哪部法、哪一条**（由真正读懂含义的 AI 判定），写成声明。`claimText` 逐字摘自成稿——这是给既有句子标注来源，不是改写它。每条声明转成一个 `declared:true` 的核验点，后续 `match-evidence.mjs` 只确认这个声明的来源/条文**真实存在**（防编造），再锚到真实段落，绝不重判对错。
2. **规则兜底抽取 —— 扫描 `answer.md`**：对没有 claims.json（或 AI 漏声明）的情况，仍用规则识别 `《法律名》第X条` / 案号 / `《...规定》` / 触发词论断。这些点 `declared:false`；命中真实来源就标已关联，否则由匹配步骤给相似度推荐（弱关联）或标待核验——**永远不会标"错"**。但当 `claims.json` 已经提供 AI 语义复盘声明时，脚本只保留规则抽取中的具体来源/条号/案号/监管文件等硬引用，抑制无具体目标的软触发结论句，避免前一句已关联法规、后一句只是分析结论却被错误显示为弱关联。

## 关键：claims.json 是「定稿后的复盘」，不是「写作时的约束」

**核验是事后挂接的外挂，不能反向影响输出。** 因此 claims.json 的产出时机是**意见已经写完之后**，专家回过头来读自己的成稿、为既有句子标注来源。绝不能因为"要声明依据"而在写作时把话写得僵硬、碎片化或逐字照抄法条——那会损害本该有的输出质量与风格。写作阶段只管按用户意图和场景标准写好；溯源声明留到定稿后再做。

- `claimText` **必须逐字摘自 `answer.md`**，脚本据此在正文中定位高亮，不得为了声明而改动正文。
- 这一步即使整体省略也能跑（退化为规则兜底），但做了溯源命中率显著更高。

## 为什么用 AI 语义复盘而非文字精确匹配

法律意见常常是对法条的归纳转述，不能要求正文与法条原文逐字雷同。核验点的关键是：**关联性由 AI 语义判断，不由文字雷同判断**。成稿里写"处理敏感个人信息须取得单独同意"时，复盘的 AI 判断这依据的是个保法第29条，并在 claims.json 里标注出来；脚本只负责确认"个保法第29条确实在本次资料里"，用户点击即可跳到原文自行核验。这样既防 AI 编造，又不牺牲正文可读性。

## claims.json 协议（定稿后复盘时产出，强烈推荐）

> ⚠️ **格式铁律（写错会让 `declared:0`、报告全红）**：
> 1. 顶层**必须是 `{"claims": [...]}` 对象**，不是裸数组 `[...]`。
> 2. 字段名**必须**是 `claimText` / `sourceTitle`（或 `sourceId`）/ `articleNo` / `caseNo`。
>    **不要**用 `sourceIds`、`articleRef`、`relation`、`source`、`title` 等变体——脚本虽已尽量兼容常见别名并告警，但别依赖兜底。
> 3. `sourceId` 仅指脚本生成的 12 位 hex 真实来源 id；优先使用 `sourceTitle`，不要写 `S1`/`C3` 这种展示编号。脚本会按 manifest.sources 顺序尽量兼容 `S1/s1`，但会告警，且不应依赖该兜底。

```jsonc
{
  "claims": [
    {
      "claimText": "处理敏感个人信息应当取得个人的单独同意",  // answer.md 里写的那句话（用于定位高亮）
      "sourceTitle": "个人信息保护法",                      // 关联来源法名；或用 "sourceId": "<12位hex>"
      "articleNo": "第29条",                               // 可选；整部法为依据时可省略
      "caseNo": "（2023）京0105民初12345号",                // 可选，案例引用时给
      "answerParagraphIndex": 12,                          // 可选；省略则脚本自动定位该句所在行
      "snippet": "《个人信息保护法》第二十九条",              // 可选；高亮锚文本，省略则取整句
      "riskLevel": "high"                                  // 可选；省略则按 type 推断
    }
  ]
}
```

- `claimText` 必填，应与 `answer.md` 中的句子尽量一致（脚本用 `locateClaimLine` 容错定位行号，支持包含/最长公共子串兜底）。
- `sourceTitle` 与 `sourceId` 二选一即可；同时给则 `sourceId` 优先解析。
- 给了 `articleNo` → 类型判为 `statute_article`；给了 `caseNo` → `case_ref`；只有来源无条号 → `regulatory_doc`；都没有 → `legal_claim`。
- `articleNo` 会被 `normalizeArticleKey` 归一化（中文数字→阿拉伯，"第二十九条"→"第29条"）。

> claims.json 通过 `legal-verify build/all --claims claims.json` 传入，脚本会复制到任务目录。**不给也能跑**（退化为纯规则兜底），但给了核验质量显著提升。

## 核验点类型

| type | 含义 | 风险级 |
|---|---|---|
| `statute_article` | 法规条文，如《个人信息保护法》第十三条 | high |
| `case_ref` | 案例 / 案号 / 指导案例 | high |
| `regulatory_doc` | 监管文件 / 规范性文件（无条号） | medium |
| `legal_claim` | 法律适用判断，如"平台应承担侵权责任" | medium |
| `conclusion` | 结论性判断（综上/因此/应予支持……） | medium |
| `viewpoint` | 裁判/监管/学说观点（法院认为/通常认为……） | low |
| `factual_claim` | 事实性或数据性表述（年份/比例/金额/人数） | low |

## 规则兜底抽取逻辑

按句切分（`[。！？；;]`，按行保留段落号），对每句依优先级匹配：

1. **statute_article（最强）**：`《([^》]{2,80})》\s*第\s*([…\d]+)\s*条(?:之[…])?(?:第[…]款)?(?:第[…]项)?`，归一化为 `{ title, articleNo:"第13条", clause, item }`。
2. **case_ref**：案号 `[（(]\s*\d{4}\s*[）)][^\s，。；：]{2,40}号`。
3. **bare 第X条 + 简称**：句中出现 `XX法 第X条` 但无《》时取法名简称（自动去掉"根据/依据"等前缀触发词）。
4. **regulatory_doc**：`《([^》]{2,80}(?:规定|办法|条例|通知|意见|标准|规范|细则|批复|决定|解释))》`（无条号时）。
5. **观点/结论/法律判断/事实**：靠触发词识别——
   - 观点：`法院认为|本院认为|裁判要旨|通常认为|一般认为|学界认为`
   - 结论：`综上|因此|故|应当承担|应予支持|不予支持|构成|成立|应予赔偿`
   - 法律判断：含 `承担|责任|义务|赔偿|侵权|违反|应当|不得|构成` 且含通用触发词
   - 事实：含 `\d{4}年|\d+(%|万元|亿元|元|人|项|……)` 且含触发词

> **标题不抽为核验点**：Markdown 标题（`#`~`######` 开头）是结构标签而非可核验论断，第 5 步的触发词分支会跳过它们——否则像"## 二、人脸信息采集的特别要求"会因含"要求"被误判为 `legal_claim` 污染统计。但标题里若含真正的法条/案号/监管文件（第 1~4 步强匹配），仍正常抽取。

## 合并去重规则

- **声明点（declared:true）排在前**，规则点（declared:false）追加在后。
- 若存在 AI 声明点（`declaredPoints.length > 0`），规则兜底只保留有具体锚点的硬引用：法条、案号、监管文件或明确来源；无具体目标的 `legal_claim/conclusion/viewpoint/factual_claim` 软触发点会被抑制，不进入最终可见核验点。遗漏依据交给 `repair-export` 的 AI 语义复核队列，而不是在最终报告里制造大量弱关联。
- 若规则点与某声明点在**同一行 + 相同法名/条号/案号**上重复，丢弃规则点（AI 声明优先）。去重键：`answerParagraphIndex|title|articleNo|caseNo`。
- 合并后按顺序重排 `pointId`（`vp-001` 起，稳定且唯一）。

## 输出结构

```json
{
  "taskId": "...",
  "generatedAt": "2026-06-20T12:14:31.000Z",
  "points": [
    {
      "pointId": "vp-001",
      "type": "statute_article",
      "text": "处理敏感个人信息应当取得个人的单独同意。",
      "snippet": "《个人信息保护法》第二十九条",
      "declared": true,
      "normalizedTarget": { "declared": true, "title": "个人信息保护法", "articleNo": "第29条" },
      "answerParagraphIndex": 12,
      "startOffset": 0,
      "riskLevel": "high"
    }
  ]
}
```

- `declared` 标识该点来自 AI 声明（true）还是规则兜底（false），HTML 据此区分"回答声明依据"与"系统辅助定位"。
- `snippet` 是用于在 HTML 正文中高亮的最短锚文本（法条/案号用精确片段，观点/结论用整句）。
- `answerParagraphIndex` 是回答中的行号，HTML 据此定位高亮位置。

## 写作与复盘的分工（务必区分两个阶段）

**写 `answer.md`（输出阶段）——不要为核验改变写法：**
- 按用户意图与场景标准自由地写，追求最佳可读性与专业度；该归纳转述就转述，不必逐字照抄法条。
- 法条引用本就该用书名号全称 + "第X条第X款第X项"；案例本就该带标准案号——这是引用规范，不是为核验服务。
- 模型先验、无来源的论断显著标注"请以官方发布为准"；不要放入 `sources.json` 参与核验，也不要在 `claims.json` 里声明为可溯源依据。

**写 `claims.json`（定稿后的复盘阶段）——只标注、不改稿：**
- 通读已定稿的 `answer.md`，对其中引用了法律依据的关键句子，标注它语义关联的来源/条号。
- `claimText` **逐字摘自** `answer.md`（脚本用 `locateClaimLine` 容错定位行号，支持包含/最长公共子串兜底），绝不为声明而回头改动正文。
- 可用普通脚注 `[^1]`，但**不要依赖 UI 渲染脚注**；引用映射由后处理脚本生成。不要把 `<cite>` 等内部标签直接展示给用户。
