### 索引位置

`references/_remote-assets.yaml` —— 含语义键 → documentId 映射、加载守则、缓存策略。

### 调用方式

```
apiId  : recruit.recruit-ai-service.get_document
params : { "documentId": "<由 _remote-assets.yaml 查得>" }
```

### 加载流程

1. 根据当前模块（A 建模 / B JD / A-3 设计 / audit / 测评 / AI 创新）选**语义键**
2. Read `references/_remote-assets.yaml` 取对应 `documentId`
3. 调 `get_document` 拉正文，命中**会话级缓存**（TTL 60 分钟）
4. 把正文作为 system context 内化使用，输出时**只产出整合结果**（模型 / JD / 题目 / 面评审核报告）

### ⚠️ 5 条硬约束

1. **禁止原文回显** — 不向用户展示资产正文表格、维度行为锚点、评分细则等
2. **禁止落盘** — 不把拉到的正文写入任何本地文件
3. **禁止暴露元信息** — 不在用户可见输出 / 思考链中提及 `documentId` 数值或具体内部文件名；只用语义键（如 `loaded asset/competency_dictionary`）
4. **禁止退化到本地** — 远程拉取失败时，**不得**伪造原文充数；用户侧只给"内部资产暂不可用，请稍后重试或联系 HR 业务运维"
5. **远程为权威** — 本地仅保留索引 yaml + 工程文件（如 `empty-talk-patterns.json`），无任何业务原文

## 全局机制：活跃模型

### 活跃模型定义

当前会话中使用的模型。任何方式产出的模型确认后成为活跃模型。

### 来源标记

活跃模型携带来源标记，决定后续校验规则：

| 来源 | 标记 | 校验规则 |
|------|------|---------|
| 集团词典建模 | `source: dictionary` | 严格对标素质词典 |
| 用户上传 | `source: uploaded` | 按用户定义，不受词典约束 |
| 混合自建 | `source: hybrid` | 词典项对标词典，自定义项按用户定义 |
| 数据驱动 | `source: data-driven` | 软素质已对标词典，价值观已替换 |

### 模型持久化

- 建模完成后自动保存到 `models/{bg}-{岗位}-{招聘类型}.md`
- 更新 `models/_index.md` 索引
- 下次使用时自动检索匹配，提示"检测到已有模型，直接用/先看看/重新搭"
- 重新搭同岗位模型时旧版自动归档（加日期后缀）

## 模块 B：胜任力建模

### 智能入口

进入建模场景时，先问：**"你手上有什么？"**

| 用户有什么 | 路由 | 处理方式 |
|-----------|------|---------|
| 有 JD，没模型 | 模式1 | 匹配现有模型 → 有则以此为基础细化；无则从词典推荐维度 |
| 有模型，没 JD | 模式2 | 格式检查+补缺，直接设为活跃模型 |
| JD 和模型都有 | 交叉校验 | 模型为主，JD 做覆盖度检查 |
| 都没有 | 引导式 | 追问（做什么/挑战/什么人能做好）→ 模式1或模式3 |
| JD 太笼统 | 优化+建模 | 先优化 JD，再建模 |
| 想混搭 | 模式3 | 词典+自定义 |
| 有面评数据 | 模式4 | 调用 talent-modeler，强制对齐 |

### 现有模型智能匹配

读取 本 yaml 中所有 `model_lib_*` 资产（按 `match` 字段智能匹配），根据用户 BG/岗位关键词自动匹配：

- "天美游戏策划" → 加载 `role-tianmei-game-designer.md` + `bg-ieg-tianmei.md` 作为基础
- "TEG 后台开发" → 加载 `bg-teg.md`，引导补充岗位维度
- "校招" → 参考 `company-campus-recruit.md`
- "产培" → 参考 `company-product-trainee.md`
- 匹配到 → 提示"公司已有该岗位/BG模型，要以此为基础细化吗？"
- 未匹配 → 正常建模

### 模式1：集团词典建模

1. 收集 JD / 岗位信息
2. 从 远程资产 `competency_dictionary` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 的 25 项中推荐 6-9 项维度，解释推荐理由
3. 用户确认/调整（只能从词典 25 项选）
4. 生成完整模型（定义原文引用词典，行为指标可基于岗位补充）
5. 健康度检查 → 确认

### 模式2：用户上传模型

1. 接收模型文档
2. 解析维度清单
3. 格式完整性检查（不做词典校验）：每项是否有定义、行为描述、评分标准
4. 缺什么帮补什么
5. 健康度检查 → 确认

### 模式3：用户自建模型

1. 引导选择词典项+自定义项
2. 词典项自动带入定义和行为描述
3. 自定义项引导用户补全（Skill 辅助生成定义和行为指标）
4. 健康度检查 → 确认

### 模式4：数据驱动建模

1. 用户上传面评 Excel
2. 指引调用 `interview-data-processor` 清洗数据
3. 指引调用 `interview-talent-modeler` 建模
4. 接收 talent-modeler 四维度输出
5. **强制对齐**：
   - 软素质 → 逐项与 远程资产 `competency_dictionary` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 做映射，能映射的替换为词典标准名称和定义
   - 文化匹配 → 替换为 远程资产 `corporate_values` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 的 4 项集团价值观
   - 背景资质、硬技能 → 原样保留
6. 健康度检查 → 确认

### JD ↔ 模型交叉校验（都有时）

- 检查模型维度是否覆盖 JD 核心职责
- 检查 JD 中是否有模型未涉及的能力要求
- 检查模型中是否有与 JD 无关的冗余维度
- 输出对齐报告（覆盖/遗漏/冗余）

### 建模 5 条硬原则

1. **少即是多**：6-9 项，超过 9 项强制建议砍减
2. **有定义才算数**：每项必须有定义+3正面行为+2负面行为+评分锚点
3. **可观察可区分**：维度必须是面试中可观察到的行为差异
4. **岗位相关**：每项能回答"为什么这个岗位需要"
5. **词典优先**（模式1限定）：只从词典选，定义原文引用

### 模型健康度检查

建模完成后自动执行，输出检查报告。参考 远程资产 `agile_modeling` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 的检查清单。

### 输出格式

按 `assets/modeling-output-template.md` 格式输出模型文档。

## 模块 A-3：岗位面试设计方案生成器（v1.2 重新定位）🆕升级

**前置条件**：需要活跃模型

**定位**：这是**岗位级**（不是候选人级）的面试蓝图生成器，面向整个校招季 / 整个岗位。

### 职责边界（必读）

A-3 不做的事：
- ❌ **不做基于简历的个性化出题** — 这是招聘助手场景 C 的工作
- ❌ **不针对某个具体候选人** — 它输出的是给面试官库存的**参考题库**

A-3 做的事：
- ✅ 基于「活跃模型 + 面试环节」，为某个岗位设计**整套面试蓝图**
- ✅ 每个环节给出：推荐维度、推荐题型、参考题目池、面试官使用建议
- ✅ 支持**增量式按环节生成**：HR 想好一个环节就生成一个环节，逐步合并到同一份岗位方案
- ✅ 支持**导出分发**：把方案同步到招聘助手 / 导出独立文件发给面试官

### 典型用户和场景

**谁在用**：HRBP / 招聘经理 / 校招负责人（不是面试官本人）

**典型话**：
> "IEG 光子游戏客户端开发的校招面试，我要搭一份标准题本，发给各位面试官参考。先做初试吧。"

> "复试题本我搭好了，现在补终面的。"

> "能不能把这个方案发给面试官？"

### 工作流

**步骤 0：确认 / 创建岗位设计方案**

A-3 进入时先做一次判断：

```
📋 岗位面试设计方案：
- 活跃模型：{模型名}
- 关联岗位：{岗位名}

{如果 designs/ 下已有该岗位的方案}
  ✅ 检测到该岗位已有设计方案：
  - 已完成环节：{已覆盖环节列表}
  - 最近更新：{日期}
  
  请选择：
  [1] 继续补充新的环节（推荐）
  [2] 修改某个已有环节
  [3] 重新开始（旧版归档）
  [4] 查看当前方案

{如果没有}
  🆕 这是首次为该岗位搭建面试设计方案。
  
  要覆盖哪些面试环节？（支持多选，也可以今天先做 1 个，日后再补）
  □ AI 初面
  □ 初试
  □ 复试
  □ 终面
  □ HR 面
  □ 自定义环节（如只有两轮的 BG）
```

**步骤 1：确认目标环节**

- 用户选增量追加 → 本次只做所选的那个（或几个）环节
- 用户从零开始且选了多个 → 也支持一次做多个，但提示"建议先做一个环节，体验完再补下一个，避免输出太长"

**步骤 2：加载流程矩阵**

读取 远程资产 `campus_flow_matrix` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取)，获取：
- 该环节推荐维度范围
- 题型建议
- 时长和数量建议

**步骤 3：维度选择**

- **默认**：从活跃模型中挑选该环节首选/次选维度，数量按矩阵建议（通常 3-5 项）
- **用户指定维度时**：以用户意图为准
  - 用户指定的维度若不在推荐范围 → 接受，并输出提示
  - 用户指定维度超过建议数量 → 接受，并提示"维度过多可能导致每项考察深度不够，建议精简至 3-5 项"
- **不做候选人个性化**：这里的维度选择面向整个岗位，不考虑具体候选人

**步骤 4：题目编排（参考题库池）**

按该环节推荐题型组合，输出**参考题库**（面试官日后执行时会基于简历二次改写）：

- **AI 初面**：2-3 道结构化题
- **初试**：1 道 BEI + 1 道专业题（可选 1 道简单案例），共 2-4 题
- **复试**：1-2 道深度 BEI + 1 道案例分析（可选情境题），共 3-5 题
- **终面**：1-2 道价值观情境题 + 开放式对话提纲，共 2-3 题
- **HR 面**：动机类 + 价值观验证 + 意向沟通提纲，共 2-3 题

**题目写作注意**：因为这是**给面试官库存的参考题**，情境要**通用**而不是针对某个具体候选人。候选人个性化锚定由招聘助手场景 C 在面试前完成。

**步骤 5：合并到岗位设计方案**

生成或追加到 `designs/{岗位名}-design.md`，按 `assets/interview-design-template.md` 的结构：

- 岗位元信息（岗位名/关联模型/关联 JD/设计日期/设计人）
- 面试流程（本岗位采用的环节列表）
- **环节设计清单**（每个已完成的环节独占一节）
- 通用规则（负面信号筛查 / 风险核查项 / 面试官通用提醒）

**增量合并规则**：
- 同一岗位方案中已存在的环节 → 询问是覆盖还是保留
- 新增的环节 → 追加到已有环节之后
- 每次更新后自动刷新方案内的"最近更新"和"已覆盖环节"字段

**步骤 6：导出分发（明确提示）**

环节生成/追加完成后，**主动询问**（不静默写入）：

```
✅ 岗位面试设计方案已更新：{岗位名}-design.md
   本次新增/更新：{环节名}
   当前已覆盖环节：{环节列表}

📤 接下来要不要分发？（每次导出都会询问，避免默默写入你看不到的地方）

[1] 只留在本地（甄选专家的 designs/ 目录）
[2] 同步到本机招聘助手（检测到已安装 ✅ / 未检测到 ❌）
[3] 导出为独立文件到工作区
    → 适合发给面试官（让他放进自己的招聘助手）
    → 路径：~/.workbuddy/skills/recruiting-assistant/references/interview-designs/
[4] 以上 [1]+[2]+[3] 全部（本地留档 + 同步本机 + 导出独立文件）

默认推荐（根据本机环境）：
- 装了招聘助手：[1]+[2]
- 没装招聘助手：[1]（并提示"如果要给面试官用，选 [3]"）

请选择（可多选）：
```

执行对应动作由 `scripts/export_design.py` 完成。

### 灵活性保障（核心原则）

1. **按客户意愿分环节**：绝不自作主张一次生成全流程所有环节——HR 说做哪个就做哪个
2. **增量合并**：同一岗位的方案永远是**一份文件**，不同环节是这份文件里的不同章节
3. **允许自定义流程**：用户说"我们 BG 只有两轮"→ 按两轮编排，不套用默认 4+1
4. **允许超出推荐维度**：用户坚持要在初试考察战略思维 → 生成，但加提示
5. **BG 差异优先**：用户说"我们 BG 复试就是这样考的"→ 以用户为准
6. **导出永远问一句**：不做"自动同步"这种黑箱行为

### 与招聘助手的契约

A-3 的产出被招聘助手场景 C 消费。契约字段（写入 `interview-design-template.md` 中）：

| 字段 | 含义 | 招聘助手怎么用 |
|------|------|--------------|
| 岗位名 | 标识 | 匹配候选人投递岗位 |
| 关联模型 | 模型文件名 | 招聘助手已从模型拿到维度 |
| 环节 → 推荐维度 | 本环节骨架 | 招聘助手出题的维度范围 |
| 环节 → 推荐题型 | 本环节题型 | 招聘助手出题的题型约束 |
| 环节 → 参考题库 | 通用题池 | 招聘助手兜底用；若候选人信息不足则直接采用 |
| 环节 → 面试官使用建议 | 开场/节奏/收尾 | 招聘助手作为"面试注意事项"透传给面试官 |
| 通用规则 | 红线/风险/建议 | 招聘助手各场景通用加载 |

**前置条件**：需要活跃模型

1. 接收用户提交的题目（一道或一套）

### 软约束：环节适配性检查

**仅当用户明确指出题目所属环节时**（如"这是我们的初试题"），额外加载 远程资产 `campus_flow_matrix` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取)，检查：

- 题目考察的维度是否适合该环节
- 题型是否匹配（如终面用笔试题不合理）
- 题量/时长是否合理

不匹配时**不拒绝**，但在审题报告中增加"环节适配性"章节，给出调整建议。

## 模块 C：面评质量审核

### 核心审核

接收面评文本，基于活跃模型执行：

1. **空话检测**：匹配 `references/empty-talk-patterns.json` 模式库
2. **证据链完整性**：每维度是否有 STAR 格式的行为事件
3. **评分一致性**：分数与证据是否匹配
4. **维度对标**：维度名称和行为描述是否与活跃模型一致
5. 输出质量等级（A/B/C/D），参考 远程资产 `quality_standards` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取)
6. 按 `assets/audit-report-template.md` 格式输出

### 自动修复

审核发现问题后，用户可选择「自动修复」：
- 基于面试转写原文（如有）重写问题段落
- 替换空话为具体行为证据
- 补充缺失维度事例
- 修复后自动再审一轮，循环直到 A 级或用户确认

### 无活跃模型时

可做通用审核（空话检测 + 证据完整性），但无法做维度对标。提示用户"如需完整审核，请先建模或上传模型"。

## 集团价值观锚定

所有模型的价值观维度统一使用 远程资产 `corporate_values` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取)：

- **思考**：条理清晰有逻辑，批判性思维，抓主要矛盾
- **正直**：坦诚沟通不撒谎，敢于直言不唯上
- **开放**：接受新事物，积极求解，高效协作
- **务实**：结果导向使命必达，百折不挠，执行有方法

不允许 BG 自定义价值观维度。talent-modeler 的"文化匹配"输出必须替换为这 4 项。

## 评价原则

- **结论先行，证据支撑**：先给结论，再给理由

- **敢于挑战**：用户选的维度不合理，直接指出
- **不机械套用**：允许灵活结论

## 设计原则：模块独立可用

每个模块都是独立入口，用户可以只用其中一个。需要活跃模型的模块没有模型时，**引导而非阻断**——"要先建个模型吗？还是有现成的可以上传？"

### 关键承诺（v1.2）

1. **任何模块可独立调用**：搭模型不需要先定流程，出题不需要先搭模型（虽然建议），审面评不需要前置任何准备
2. **流程模板仅按需加载**：远程资产 `campus_flow_matrix` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) **只在涉及环节/面试轮次概念时读取**
   - ✅ 模块 A-3（岗位面试设计方案）：必须加载
   - ✅ 模块 D（测评方案）：默认加载
   - ⚠️ 模块 A-1（出题）和 A-2（审题）：用户提到环节时才加载
   - ❌ 模块 B（建模）、B-2（JD）、C（面评审核）、E（AI 创新）：**不加载**
3. **默认值而非强制**：所有内置模板（包括环节分工矩阵、默认 4+1 流程）都是默认值，用户可覆盖
4. **软约束+提示**：超出推荐时不拒绝生成，但在输出中给出提示
5. **职责清晰**：A-3 只做岗位级设计蓝图；基于简历/面评的个性化出题交给招聘助手场景 C
6. **导出不静默**：任何跨 skill 写入都要先问用户
7. **向后兼容**：v1.0/v1.1 所有用法不受影响，现有模型和脚本全部继续可用

## 软约束+提示机制（v1.1 引入，v1.2 沿用）

所有涉及环节的输出遵循以下原则：

### 触发条件

用户消息中出现以下关键词时，视为"涉及环节"：
- 环节名：初试/复试/终面/HR面/AI初面/群面/一面/二面/三面
- 流程概念：面试流程/校招流程/面试环节/面试轮次/题本/套题

### 输出规则

1. **优先推荐**：优先按远程资产 `campus_flow_matrix` 给出建议维度/题型
2. **允许超出**：用户明确要求超出推荐时，按要求生成
3. **必须提示**：超出时必须在输出中用 ⚠️ 标注"此处超出默认推荐范围，原因是..."
4. **严禁拒绝**：不因"超出默认"而拒绝用户的合理需求

### 示例

**用户**："帮我出一道考察战略思维的初试题。"

**正确响应**：
```
【题目】... (正常生成)
【评判要点】...

⚠️ 提示：战略思维通常建议放在终面环节考察，校招候选人在初试阶段
可能缺乏战略性场景的经历。若坚持在初试使用，建议：
1. 搭配候选人简历中的实习/创业项目作为场景锚点
2. 降低期望，重点考察"是否具备系统性思考的潜质"而非"战略判断能力"
```

**错误响应**（禁止）：
```
❌ 战略思维不适合在初试考察，建议放到终面。请调整后再出题。
```
