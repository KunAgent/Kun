## 1. 执行总流程

```
用户意图（写话术 / 查画像）
      ↓
确定目标候选人（resume_id / 姓名）
      ↓
拉齐画像（基础 + 简历 + 面评）
      ↓
判定候选人所处保温阶段
      ↓
选取话术模板（assets/script-templates.md）
      ↓
画像 → 话术 Hook 个性化注入
      ↓
输出正文 + 使用建议
```

## 2. 画像三段式

候选人画像分三段信息源，按优先级拉取：

### 2.1 基础档案（数仓主表）

从 `Report_School_Recruiti_Info_List` 拉取（用 [sql-templates.md](./sql-templates.md) 的 **T6_ONE_CANDIDATE**）：

- 姓名、性别、学校、学历、专业
- 岗位、组织全路径、工作地、预计入职
- 签约/三方/入职状态
- 导师、直接上级

### 2.2 简历特征（数仓辅表 / zhaopin-mcp）

优先尝试数仓辅表 `Report_School_Recruit_Personal_Resume_Info`（按 `resume_id` 关联），拉取：

- 教育经历（含 GPA / 院校层次）
- 项目经历
- 实习经历
- 获奖 / 竞赛
- 技能标签

若数仓侧信息不全，转用 zhaopin-mcp（当前工具列表通常名为 `recruit-mcp`，见 [第 3 节](#3-zhaopin-mcp--recruit-mcp-调用指引)）。

### 2.3 面评特征（zhaopin-mcp）

面评信息通常不在主表，应通过 zhaopin-mcp / `recruit-mcp` 按 `resume_id` 查询面试环节评价：

- 各轮面试官评价（集体面 / 初试 / 复试 / GM / HR）
- 维度打分（专业能力 / 聪明度 / 协作性 / 自驱力 / 好心态 / 价值观）
- 关键亮点与顾虑

## 3. zhaopin-mcp / recruit-mcp 调用指引

### 3.1 工具发现原则

⚠️ **重要**：用户口中的 `zhaopin-mcp` 在当前工具列表中通常体现为 `recruit-mcp`，且具体业务能力需通过 `SearchAPI` 发现。不要凭记忆写死业务 API 名称或自行构造 ID。

每次新会话第一次使用招聘系统补充数据时，必须先做：

1. 用 `mcp_get_tool_description` 获取 `SearchAPI` / `CallAPI` / `CallDB` 的入参 schema
2. 用 `SearchAPI` 第①步发现能力：不传 `apiId`，通过 `query/domain/type/tags` 搜索
3. 用 `SearchAPI` 第②步获取详情：传入第①步返回的原始完整 `apiId/queryId`
4. 按第②步参数定义调用 `CallAPI` 或 `CallDB`
5. 若系统未挂载 `recruit-mcp`，降级方案见 [第 3.4 节](#34-降级方案)

### 3.2 常见用途与搜索关键词

| 能力类别 | SearchAPI 搜索关键词 | 典型输入 | 典型输出 |
|---|---|---|---|
| 候选人画像汇总 | `候选人画像 resume_id` / `candidate profile` | `resume_id` | 姓名、学校、专业、实习、项目亮点 |
| 面评查询 | `面评 面试评价 resume_id` / `interview feedback` | `resume_id` | 各轮面试官评价、维度打分 |
| 简历全文 | `简历详情 resume_id` / `resume detail` | `resume_id` | 简历结构化字段 |
| 流程详情 | `录用流程 offer resume_id` / `流程详情` | `resume_id` / `offer_id` | 当前流程状态、环节、处理信息 |
| 岗位匹配分析 | `岗位匹配 candidate job match` | `resume_id` + 岗位标识 | 匹配维度与建议 |

### 3.3 调用范式

```
# 第一步：查三类工具 schema
mcp_get_tool_description:
  toolRequests: [["recruit-mcp", "SearchAPI"], ["recruit-mcp", "CallAPI"], ["recruit-mcp", "CallDB"]]

# 第二步：发现能力（不传 apiId）
mcp_call_tool:
  serverName: recruit-mcp
  toolName: SearchAPI
  arguments: { "query": "简历详情 面评 resume_id", "domain": "recruit", "type": "all" }

# 第三步：获取目标能力详情（apiId/queryId 必须从第二步结果原样复制）
mcp_call_tool:
  serverName: recruit-mcp
  toolName: SearchAPI
  arguments: { "apiId": "<原始完整ID>" }

# 第四步：按详情调用 API 或 DB
mcp_call_tool:
  serverName: recruit-mcp
  toolName: CallAPI 或 CallDB
  arguments: { "apiId/queryId": "<原始完整ID>", "params": { "resume_id": "<resume_id>" } }
```

### 3.4 降级方案

如果当前 agent 平台**没有挂载** recruit-mcp：

1. 告知用户："当前环境未接入招聘系统补充 MCP，面评和详细简历信息暂时无法拉取，我将基于数仓可见信息生成话术"
2. 仅用数仓主表和辅表的字段（学校、专业、实习、CM 反馈等）做个性化
3. 话术中不要编造面评原话

## 4. 话术个性化注入

拿到三段画像后，按以下规则提取 Hook 注入话术：

### 4.1 Hook 提取规则

| 画像信号 | Hook 类型 | 示例注入片段 |
|---|---|---|
| 有腾讯系实习（PCG/WXG/IEG/TEG/CSIG/CDG） | **回巢认同** | "你之前在 {BG} 实习的经历是很宝贵的背景" |
| 名校 + 相关专业匹配（清北/浙大/交大/人大/港三+ 相关专业） | **学术亮点** | "从你的 {专业} 背景看，这个岗位方向很契合" |
| 博士学历 | **学术深度** | "你在 {专业} 方向的研究积累" |
| 曾在标杆互联网公司（字节/阿里/百度/网易等） | **行业背景** | "你在 {公司} 的实战经验" |
| 面评有亮点维度（如专业能力 S / A+） | **能力认同** | 面评中"思路清晰、代码扎实"类表述，简要致意（不引述原话） |
| 面评有顾虑（某维度偏弱） | **关怀问询** | 不直接指出顾虑，换成开放式问候"有什么困惑或需要我协助的吗" |
| 工作地与候选人归属地不一致 | **落地关怀** | "深圳的住宿、交通我们可以提供协助" |
| 距入职 > 60 天 | **长周期陪伴** | "离入职还有一段时间，团队这边会陆续同步信息" |
| 距入职 ≤ 30 天 | **临门一脚** | "入职临近，有几件准备事项想提前跟你对齐" |
| 高潜人才（`candidate_tag` 非空：青云计划 / 青云实习 / 产品经理培训生） | **高潜重视** | 体现平台资源与成长空间，"我们为你这样的同学规划了更系统的发展支持"，必要时由更高级别管理者出面表达重视 |

### 4.2 风险信号 → 话术策略

| 候选人状态 | 话术基调 | 重点 |
|---|---|---|
| `cm_feedback` 有"未回复/沟通意愿下降" | 轻量、开放式 | 不追问是否有其他 offer，而是邀请一次闲聊 |
| 长时间未互动（≥ 14 天） | 重新建联 | 以"近况同步/入职准备"为由头，避免问责式表达 |
| 正常进展 | 常规保温 | 定期信息同步 + 适度关怀 |
| **高潜人才**（青云计划 / 青云实习 / 产品经理培训生） | **升级重视、个性化陪伴** | 在常规保温基础上叠加：高层/上级管理者关注、平台资源与发展路径的个性化沟通；触达频率适度提高但不打扰；必要时由更高级别管理者参与一次沟通 |
| 已毁约（lost） | **不发话术** | 进入复盘环节，不再生成保温话术 |

### 4.3 禁止的个性化反面案例

❌ 引用候选人简历中未公开字段（如 GPA 具体数值、家庭情况）
❌ 引用面评中对候选人的负面描述（即使是亮点互补维度也不要转述原话）
❌ 承诺具体 offer 条款、工资数字、入职日期
❌ 暗示与其他候选人的对比
❌ 要求候选人承诺某项动作（签字/确认/放弃其他 offer）

## 5. 阶段判定与模板选择

按候选人派生字段选择话术模板（模板正文在 [assets/script-templates.md](../assets/script-templates.md)）：

| 候选人阶段 | 派生字段条件 | 模板 ID | 适用场景 |
|---|---|---|---|
| 刚签约、导师未绑定 | `mentor_bound = false` AND `signed_time ≤ 7 天内` | **S1_welcome** | 首次欢迎话术 |
| 导师已绑、首次沟通未发生 | `mentor_bound = true AND first_contact_done = false` | **S2_first_touch** | 导师首次建联脚本 |
| 已首次沟通、资料未发 | `first_contact_done = true AND welcome_material_sent = false` | **S3_welcome_pack** | 欢迎包发送话术 |
| 日常陪伴期 | `welcome_material_sent = true AND days_to_entry > 30` | **S4_routine** | 月度关怀 |
| 临近入职 | `0 < days_to_entry ≤ 30` | **S5_pre_entry** | 入职倒计时话术 |
| 长期未互动 | `days_since_last_interaction ≥ 14` | **S6_reengage** | 重新建联话术 |
| 有风险信号 | `risk_level = high` | **S7_risk_check** | 风险干预话术（招聘经理亲自出面） |

同一候选人可能有多个合适模板，按优先级：**风险干预 > 阶段任务 > 日常陪伴**。

## 5.5 三方标准动作与阶段节奏（保温全景指引）

保温是 **招聘经理、导师、直接上级** 三方协同的系统工程。生成话术、给出"使用建议 / 下一步"、以及对外通知导师/上级时，应据此明确各角色的标准动作，避免对方"不知道该做什么"。

### 5.5.1 三方标准动作

| 角色 | 定位 | 标准动作（建议清单） |
|---|---|---|
| **招聘经理** | 第一责任人与统筹者 | 1. 签约后 1 周内首次沟通，传递欢迎与祝贺，确认基本信息与入职意向；2. 绑定导师与直接上级，明确责任链；3. 每 2-4 周保持联系，了解状态变化与潜在风险；4. 关键节点（offer 发放 / 三方签订 / 毕业季 / 入职前 1 月）主动触达；5. 识别高风险并及时升级干预；6. 入职前确认报到事宜，协助住宿 / 落户 / 报到流程 |
| **导师** | 融入团队的引路人 | 1. 接到保温通知后 1 周内首次沟通，做自我介绍、建立联系；2. 分享团队技术氛围与个人成长经历，建立专业认同；3. 解答岗位 / 技术 / 团队疑问，适度分享行业动态与学习资料；4. 入职前帮助做好技术与心理准备，降低入职焦虑；5. 关注情绪变化，发现异常及时反馈招聘经理 |
| **直接上级** | 团队价值与发展空间的代言人 | 1. 接到通知后 2 周内沟通，欢迎加入团队；2. 介绍团队业务方向、文化与工作模式；3. 描绘岗位发展路径与成长空间，必要时分享团队成果增强吸引力；4. 关注合理诉求，在职责范围内提供支持；5. 入职前做好团队接纳准备，让候选人感受到被重视 |

### 5.5.2 三阶段节奏

| 阶段 | 时间窗 | 重点 | 三方动作要点 |
|---|---|---|---|
| **签约初期** | 签约后 1 个月内 | 建立连接，传递欢迎 | 招聘经理完成首次沟通并绑定导师 / 上级；导师、上级分别完成首次建联 |
| **保温中期** | 入职前 1 个月以上 | 持续互动，深化认同 | 定期信息同步（团队动态 / 行业资讯 / 学习资料）；关注状态变化；关键节点（毕业季、节日）主动触达 |
| **入职前期** | 入职前 1 个月内 | 临门一脚，确保入职 | 确认报到事宜、协助实际困难；加强互动频率缓解焦虑；导师、上级做好接纳准备 |

### 5.5.3 在话术与建议中的用法

- 生成话术后的"使用建议 / 下一步"应结合当前阶段，**点名相应角色的下一个标准动作**（如"建议导师本周内完成首次自我介绍沟通"）。
- 高潜人才（青云计划 / 青云实习 / 产品经理培训生）在三方标准动作基础上，叠加 **高层关注、资源倾斜、个性化发展规划**，必要时由更高级别管理者参与保温。
- 对外通知导师 / 上级时，话术内容须把对应角色的标准动作清单一并带出（见 `hrclaw-message.md`）。

## 6. V4 深度关注建议与稳定签约识别

当用户明确询问“毁约可能”“谁更值得重点关注”“是否更像稳定签约”“重点关注名单”“稳定签约名单”时，在场景 B 里追加 V4 深度分析：

### 6.1 使用定位

- **输出定位**：V4 不是毁约概率预测器，而是**关注建议引擎 + 稳定签约识别器**
- **适合回答**：
  - 谁更值得 recruiter / 用人主管优先跟进
  - 当前关注点更偏流程、匹配、外部竞争还是去向不稳
  - 哪些人更接近“稳定签约”画像，可维持常规保温
- **不适合回答**：
  - 这个人一定会不会毁约
  - 这个人毁约概率是多少

### 6.2 输入要求

优先将当前会话中已授权访问的候选人画像整理为 JSON，再输入 `scripts/analyze_candidate_attention_v4.py`。

推荐补齐字段（缺失可留空，但越完整越准）：

- 基础字段：`resume_id`、`name`、`highest_school`、`highest_degree`、`highest_speciality`、`position_name_cn`、`w_city`
- 风险反馈：`cm_feedback`、`cm_fb_result`、`suggestion`
- 流程节奏：`hr_pass_time`、`hr_salary_submit_time`、`offer_approve_time`、`offer_send_time`、`resume_update_time`、`resume_status_update_time`
- 文本画像：各轮面试评语、`practice_exp`、`employer_names`
- 保护性信号：`offer_type`、`tripartite_status`、是否腾讯实习/留用等

### 6.3 执行方式

```bash
python scripts/analyze_candidate_attention_v4.py <input.json> --output-csv <output.csv> --summary-json <summary.json>
```

脚本支持：
- `CSV`：适合离线批量跑分
- `JSON`：适合在当前 skill 中承接场景 A / B 查询结果直接做深度分析

### 6.4 输出解释

脚本会补充以下关键字段：

- `关注分` / `关注等级`
- `关注优先级`（P1 / P2 / P3 / P4）
- `稳定签约分` / `稳定签约等级`
- `是否识别为相对稳定签约`
- `主关注维度` / `次关注维度`
- `保护性信号`
- `关注理由`
- `招聘侧判断摘要`
- `推荐跟进行动`
- `推荐介入角色`

### 6.5 在场景 B 中的使用规则

- **单人画像**：把 V4 结果作为“候选人关注建议速览”放在画像最前面
- **多人比对**：只展示 P1 / P2 名单和高稳定签约名单，不铺全量分数明细
- **话术生成**：
  - `主关注维度 = 时间流程` → 话术优先补“流程承接、入职准备、节奏确认”
  - `主关注维度 = 匹配偏差` → 话术优先补“岗位理解、团队归属、工作地解释”
  - `主关注维度 = 去向不稳` → 话术优先补“意向确认、决策窗口、真实顾虑探查”
  - `主关注维度 = 竞争变动 / 结构信号` → 话术优先补“岗位卖点、成长空间、团队吸引力”
- **稳定签约识别为“是”**：在建议里提示“可维持常规保温，不必立即升级干预”

### 6.6 合规边界

- 只能基于**当前会话已授权范围内**的候选人做 V4 分析
- 不得把 V4 分数解释为“毁约概率”
- 不得把历史毁约率高的学校标签直接对候选人做价值判断
- 对外输出时只说“值得关注 / 相对稳定 / 建议优先跟进”，不做确定性结论

## 7. 输出规范


场景 B 的输出必须包含三部分：

### 6.1 候选人画像速览（4-6 行）

```
👤 陈思远（男 / 浙江大学 / 计算机硕士）
📋 岗位：前端开发工程师 @ PCG-信息流-推荐技术部
⏰ 预计入职：2026-07-01（距今 72 天）
🎯 简历亮点：腾讯 PCG 前端实习
⭐ 面评亮点：专业能力 A+，代码基本功扎实（来自复试评价）
🔶 保温阶段：资料已发送，日常陪伴期
```

### 6.2 推荐话术正文（核心）

```
【话术类型】日常月度关怀（S4_routine）
【建议渠道】企业微信文字消息
【建议时机】工作日 10:00-11:00 或 15:00-16:00

---正文---

思远你好，
最近一切顺利吗？距离你入职还有两个多月……
（此处为根据 Hook 个性化注入的完整正文，一般 4-8 句）

---
```

### 6.3 使用建议与跟进预期

```
💡 使用建议：
- 发送后预期 24-48h 内会有回复
- 如 3 天无回复，可由导师 {李建国} 接力发一条日常消息
- 本轮沟通重点在"保持连接",不要追问是否有其他 offer

🔄 下一步：
- 候选人回复后，建议由你在 {XX 场合} 做一次 1v1 电话沟通
- 如需要我再生成"入职倒计时话术"，候选人临近入职 30 天时再跟我说
```

### 6.4 多版本输出（可选）

如果用户要求"给我几个版本选",一次输出 **2-3 个语气不同** 的版本，并标注：

- **版本 A**：官方 / 严谨 — 适合首次正式沟通
- **版本 B**：亲切 / 邻家 — 适合已建立关系后的日常互动
- **版本 C**：简短 / 问候 — 适合节日或突发事件关怀

## 8. 禁用语与合规红线


### 7.1 禁用措辞清单

| 类别 | 禁用 | 替换 |
|---|---|---|
| 强制性承诺 | "保证你 X 月 X 日入职" | "预计 X 月 X 日入职，以正式入职通知为准" |
| 金额暗示 | "年薪 XX 万没问题" | 不写薪资 |
| 他人对比 | "其他同学都已签了" | 删除 |
| 负面假设 | "如果你不来" | "希望能在 X 月看到你" |
| 面评原话 | "面试官说你 XXX" | 抽象为"团队对你印象不错" |
| 组织承诺 | "你入职就能进 X 项目" | "入职后会有团队和岗位对齐" |

### 7.2 合规必检

每次输出话术前自检：

- [ ] 不涉及薪酬具体数字
- [ ] 不涉及具体团队/项目名承诺
- [ ] 不出现"保证 / 一定 / 绝对"等绝对化表达
- [ ] 不引用候选人未公开的个人信息
- [ ] 不让候选人做放弃其他 offer 的书面承诺
- [ ] 敏感字段已脱敏（手机号、身份证等不出现在话术中）

若发现话术中出现禁用内容，务必重写后再输出给用户。
