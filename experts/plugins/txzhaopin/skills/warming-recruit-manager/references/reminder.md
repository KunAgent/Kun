## 1. 触发时机

本 skill 被加载后，满足**任一**条件即可进入保温提醒播报流程：

1. **首次加载**：当前会话中第一次检测到 skill 被触发，且用户首条消息未明确发起其他任务
2. **显式请求**：用户说出"今日播报"、"给我提醒"、"我还有什么要跟进"、"今天要做什么"、"保温日报"
3. **结束时追加**：用户完成场景 A 查询后，若查询结果已覆盖播报所需数据，可在末尾附一段"今日建议动作"

**人群口径继承**：

- 场景 C 播报与场景 D 企微推送，均**沿用本会话已通过 〇-A 确认的人群三要素（查询范围 + 毕业届次 + 招聘类型）**，与场景 A 保持同一口径，不另起默认
- 若本会话尚未确认过人群（直接触发播报），按 〇-A 默认口径执行：范围=我名下、届次=当年+次年、招聘类型=全部，并在播报标签行注明
- 播报摘要必须在头部带上人群标签，如"范围：我名下 ｜ 届次：2026+2027 ｜ 类型：毕业生"，让招聘经理一眼确认口径

**自动触发确认**：

- 若是首次加载或连续对话中的**自动触发**，且用户本轮没有明确说"今日播报 / 给我提醒"，必须先询问："检测到当前查询范围内有 {total} 位签约后候选人，是否为你生成今日保温提醒？"
- 用户确认或明确要求播报 → 执行完整播报
- 用户说"跳过 / 不用 / 先不要" → 本会话不再主动触发场景 C
- 用户显式请求播报时，无需再次确认

**不触发**时机：

- 用户正在询问话术生成（场景 B 专注）
- 用户明确说"先不要提醒" / "别打扰"
- 本会话已触发过一次播报，且未过 30 分钟

## 2. 执行流程

```
Step 0: 检查 hr-ai-data 插件连接
        ↓ 调用 mcp_get_tool_description 确认插件可用
        ↓ 不可用则告知用户安装插件，终止流程
Step 1: 获取当前招聘经理身份
        ↓ get_current_user → loginName
        ↓ 查员工宽表 → 中文名
        ↓ 拼接 recruit_manager_name = 'loginName(中文名)'
Step 1.5: 自动触发确认
        ↓ 若用户未显式请求播报，先询问是否生成今日提醒；用户拒绝则本会话停止主动播报
Step 2: 快速 KPI 查询
        ↓ sql-templates.md 的 T7_SUMMARY_KPI
Step 3: 按优先级抓取明细清单（最多 3 类）
        ↓ T2_NO_MENTOR + T3_NO_LEADER + T4_BY_ENTRY_DATE(0-30d)
Step 4: 按三级提醒分层聚合
        ↓
Step 5: 按播报模板输出（不超过 250 字 + 一个明细表）
        ↓
Step 6: 引导下一步（场景 A 深查 / 场景 B 写话术）
```

**性能要求**：整个播报过程最多 4 次 MCP 调用（含身份解析），避免用户感知延迟。

## 3. 三级提醒分层

播报按"危急度"分成三层，层内按"距入职天数"升序：

### L1 — 红灯 🔴（立即处理）

> 如用户额外要求判断“谁更可能毁约 / 谁最值得重点关注”，可在三级提醒之外叠加 V4 深度分析结果，但 V4 只作为红黄灯排序增强，不替代本节基础口径。


必须出现在播报首屏，逐条列明。满足以下条件进入 L1：

- 距入职 ≤ 30 天 **且** 导师未绑定
- 距入职 ≤ 30 天 **且** 首次沟通未完成
- `cm_fb_result` 或 `suggestion` 非空（有风险反馈）
- 距上次互动 ≥ 21 天（长期失联）

### L2 — 黄灯 🟡（本周关注）

简要汇总（只给数字 + 3 个样例名），不展开全部。满足以下条件进入 L2：

- 30 < 距入职 ≤ 60 天 **且** 导师未绑定
- 导师已绑但首次沟通未完成
- 首次沟通已完成但资料未发送
- 距上次互动 7-20 天

### L3 — 绿灯 🟢（常规关怀）

只给一个总数，不列明细。其他所有进展正常的已签候选人。

### 高潜人才优先（跨层级）

- `candidate_tag` 非空（青云计划 / 青云实习 / 产品经理培训生）的同学，在同等条件下**提醒层级整体上提一档**（如本应 L2 的高潜人选并入 L1 首屏），并在条目前加 ⭐ 标记。
- 高潜人选的建议动作统一附"建议优先保温、必要时由上级管理者参与"。
- 高潜人群口径与场景 A 一致（见 `sql-templates.md`），随本会话已确认的人群三要素一并沿用。

## 5. 频次与防骚扰

### 5.1 频次规则

| 触发条件 | 会话内次数上限 |
|---|---|
| 首次加载自动播报 | 每个会话最多 1 次 |
| 用户显式请求 | 不限次数 |
| 查询后追加（简短版） | 每次查询后最多 1 次 |

### 5.2 防骚扰规则

- 若用户在一次播报后的下一轮对话中直接给出指令（如"查 XXX"、"写话术"），**不要**再次追加播报
- 若用户说"先不要提醒" / "别播报" / "跳过"，本会话不再主动触发；仅当用户之后再次显式说"给我播报 / 今日提醒"时恢复
- 长消息中的提醒部分**不要占用 > 40%** 的篇幅，保证后续场景 A/B 的输出空间
- 如果 KPI 查询失败或超时，**不要**输出错误栈，改为"当前保温数据暂时不可用，稍后我会再尝试提醒你"

### 5.3 隐私约束

- 候选人姓名在明细中使用全名（招聘经理的工作范畴内可见）
- 不在播报中展示手机号、身份证等敏感字段
- 默认不跨用户：严格只展示 `recruit_manager_name = '{loginName}({中文名})'` 的人选；若用户明确使用全组织视角，必须先完成权限检查并按 SKILL.md 的全组织风险提示输出
- 组织信息可展示到部门层级，更深层路径仅在详情查询时给出

## 6. 企微机器人定期推送模式

场景 D 用于引导招聘经理把场景 C 的保温提醒升级为**企微群定期推送**。核心原则：数据仍来自 hr-ai-data，内容仍按三级提醒分层，发送通道改为 `wework-bot` MCP，周期执行交给 CodeBuddy 自动化。

### 6.1 触发词

用户出现以下意图时进入本模式：

- "设置企微机器人推送"
- "每天发保温日报到群"
- "每周一推送保温任务"
- "定期执行保温提醒"
- "保温日报推群"
- "用机器人提醒招聘经理/导师"

### 6.2 执行总流程

```
Step 0: 确认推送目标与频率
        ↓ 默认当前招聘经理本人名下；若指定导师/上级，先按 SKILL.md 第〇-A 节确认范围
Step 1: 检查 hr-ai-data 插件连接
        ↓ 复用场景 C 的身份解析、KPI 查询和三级提醒分层
Step 2: 检查 wework-bot MCP
        ↓ 先 mcp_get_tool_description: [["wework-bot", "test_wework_connection"], ["wework-bot", "send_wework_message"]]
        ↓ 可用时可调用 test_wework_connection；不可用则输出接入指引并停止推送
Step 3: 生成企微 Markdown 消息
        ↓ 内容控制在 800 字以内，红灯最多列 5 人，黄灯只汇总 + 样例
Step 4: 即时发送或创建周期任务
        ↓ 即时发送：wework-bot.send_wework_message
        ↓ 定期执行：创建 CodeBuddy 自动化，任务中复用本流程
Step 5: 回写结果
        ↓ 明确告知已发送 / 已创建周期任务 / 失败原因
```

### 6.3 wework-bot MCP 调用规范

每次新会话第一次使用企微机器人时，必须先获取工具 schema：

```
mcp_get_tool_description:
  toolRequests: [["wework-bot", "test_wework_connection"], ["wework-bot", "send_wework_message"]]
```

当前已知工具能力：

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `test_wework_connection` | 测试企业微信机器人连接 | 无参数 |
| `send_wework_message` | 发送文本或 Markdown 到企微群 | `content` 必填；`type` 可选 `text` / `markdown`；`mentionUsers`、`mentionMobiles` 可选 |

发送 Markdown 示例：

```
mcp_call_tool:
  serverName: wework-bot
  toolName: send_wework_message
  arguments: {
    "type": "markdown",
    "content": "<按 6.5 模板生成的 Markdown>"
  }
```

⚠️ 禁止在对话、文档、企微消息中展示 Webhook URL、Webhook Key、Token 或机器人环境变量。

### 6.4 周期任务配置引导

当用户说"定期"、"每天"、"每周"等，应引导创建 CodeBuddy 自动化，而不是在 skill 中手写循环。

推荐频率：

| 用户说法 | 推荐周期 | RRULE 示例 |
|---|---|---|
| 每天早上推送 / 每日保温日报 | 工作日或每日 9:00 | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=9;BYMINUTE=0` |
| 每周一推送 / 周报 | 每周一 9:30 | `FREQ=WEEKLY;BYDAY=MO;BYHOUR=9;BYMINUTE=30` |
| 每两小时提醒 | 每 2 小时 | `FREQ=HOURLY;INTERVAL=2` |

自动化任务 prompt 应只描述任务本身，不写排期和工作区，例如：

```
加载 warming-recruit-manager skill，查询当前招聘经理名下签约后待入职候选人，生成保温日报 Markdown，并通过 wework-bot 发送到已配置的企业微信群。若 hr-ai-data 或 wework-bot 不可用，说明失败原因，不要编造推送结果。
```

如用户要求指定导师 / 直接上级范围，prompt 中必须写清过滤范围，例如：

```
加载 warming-recruit-manager skill，查询导师 zhangsan 名下签约后待入职候选人，生成保温日报 Markdown，并通过 wework-bot 发送到已配置的企业微信群。
```

如用户要求指定 BG / 部门 / 中心 / 组织全路径范围（范围 ④），prompt 中必须写清组织名与是否叠加"我名下"：

```
加载 warming-recruit-manager skill，查询 PCG/QQ研发部 名下、且当前招聘经理对接的签约后待入职候选人（按场景 A 范围 ④），生成保温日报 Markdown，并通过 wework-bot 发送到已配置的企业微信群。
```

如用户要求"全组织视角不限招聘经理"，prompt 中需显式声明并要求做行权限核查：

```
加载 warming-recruit-manager skill，按场景 A 范围 ④ 全组织视角查询 TEG 名下签约后待入职候选人（不限招聘经理）。先调用 get_current_user_data_permission 核查行权限，无权限则停止；查询结果不展示手机号、面评原文等敏感字段，仅做组织盘点。
```

### 6.6 群推送内容边界

企微群推送影响范围更大，必须比会话播报更克制：

- 只展示候选人姓名、学校/岗位摘要、风险标签、预计入职日期、建议动作
- 不展示手机号、身份证、家庭住址、邮箱、银行卡、详细面评原文、薪资、Offer 条款
- `cm_feedback`、`suggestion` 仅做风险标签，不在群里原文展开；如需详情，引导回到 AI 助手单人查询
- 红灯明细最多 5 人；超过 5 人时写"另有 X 人需关注"
- 默认不 `@all`；只有用户明确要求且风险紧急时，才使用 `mentionUsers` 或 `mentionMobiles`
- 不向候选人群推送内部风险判断；本模式默认面向招聘经理 / HR 协同群

### 6.7 失败处理

| 失败点 | 处理方式 |
|---|---|
| hr-ai-data 未连接 | 提示先安装/连接 hr-ai-data，终止数据查询和推送 |
| `wework-bot` MCP 未连接 | 提示先安装/连接企微机器人 MCP，说明当前未推送 |
| `test_wework_connection` 失败 | 提示检查机器人配置，不继续调用发送 |
| `send_wework_message` 失败 | 明确说明发送失败，保留已生成 Markdown 供用户复制 |
| 自动化创建失败 | 明确说明未创建周期任务，可先执行一次即时推送 |

任何失败场景都不得输出"已推送"、"已创建"等成功表述。

## 7. CodeBuddy 自动化任务定时提醒模式

场景 E 引导招聘经理把场景 C 的保温播报升级为**由 CodeBuddy 自动化按时间触发**。与场景 D 的关键区别：

| 项目 | 场景 D（企微推送） | 场景 E（CodeBuddy 自动化） |
|---|---|---|
| 接收者 | 企业微信群（团队 / 协同群） | 招聘经理本人，CodeBuddy IDE 会话 |
| 通道 | `wework-bot` MCP | CodeBuddy 自动化（`automation_update`） |
| 触发方式 | 即时发送 / 自动化任务调用 wework-bot | 自动化任务到点自动加载本 skill 并生成播报 |
| 是否需要外部机器人 | 是 | 否 |
| 适用场景 | 多人协同、责任链联动 | 个人订阅式提醒，避免每天手动唤起 |

两者可以叠加：先用场景 E 让 CodeBuddy 每天早上跑一次，再在 prompt 中调用场景 D 把摘要发到群里。

### 7.1 触发词

用户出现以下意图时进入本模式：

- "让 CodeBuddy 自动提醒我"
- "设置定时保温任务"
- "每天早上自动跑保温播报"
- "做一个保温自动化"
- "定时执行保温 skill"
- "订阅我自己的保温日报"
- "用 CodeBuddy automation 做保温"

### 7.2 执行总流程

```
Step 0: 确认场景适用性
        ↓ 若用户希望推到企微群 → 切换到场景 D
        ↓ 若用户希望"自动跑、自己看" → 继续场景 E
Step 1: 确认提醒目标与频率
        ↓ 默认当前招聘经理本人名下；指定导师/上级则先按 SKILL.md 第〇-A 节确认
        ↓ 默认工作日 09:00；可改每日 / 每周 / 自定义周期
Step 2: 前置说明
        ↓ 告知用户：自动化运行时仍依赖 hr-ai-data 插件
        ↓ 告知用户：自动化执行结果出现在 CodeBuddy 的自动化任务记录中
Step 3: 创建 CodeBuddy 自动化
        ↓ 调用 automation_update，mode="suggested create"
        ↓ 填好 name / prompt / rrule / cwds / status
Step 4: 创建后回写
        ↓ 明确告知任务名称、下一次运行时间、暂停/修改入口
        ↓ 若用户同时希望推群 → 提示可将场景 D 的发送步骤写入同一个 prompt
```

### 7.3 automation_update 调用规范

每次为用户创建保温自动化时，按以下结构填充参数：

| 参数 | 取值原则 |
|---|---|
| `mode` | 新建用 `"suggested create"`；修改已有任务用 `"suggested update"` 并带 `id` |
| `name` | 简短中文名，如 `保温日报 - 我名下`、`保温周报 - lzhang 导师` |
| `prompt` | 只写"加载 skill + 做什么 + 范围"，不写时间、不写工作区、不写密钥 |
| `cwds` | 当前工作区绝对路径，例如 `d:/P族项目及保温/保温/保温Ai先锋/warming demo/warming-recruit-manager` |
| `status` | 默认 `ACTIVE`，用户明确说"先暂停"才用 `PAUSED` |
| `scheduleType` | 周期任务用 `recurring`（默认）；一次性提醒用 `once` |
| `rrule` | 周期任务必填，见 7.4 |
| `scheduledAt` | 一次性任务必填，ISO 8601（如 `2026-05-21T09:00`） |

调用示例（创建工作日早 9 点自动播报）：

```
automation_update:
  mode: "suggested create"
  name: "保温日报 - 我名下"
  prompt: "加载 warming-recruit-manager skill，按场景 C 流程查询当前招聘经理名下签约后待入职候选人，生成三级提醒分层的保温播报。若 hr-ai-data 不可用，请明确说明失败原因，不要编造数据。"
  cwds: "d:/P族项目及保温/保温/保温Ai先锋/warming demo/warming-recruit-manager"
  status: "ACTIVE"
  scheduleType: "recurring"
  rrule: "FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=9;BYMINUTE=0"
```

### 7.4 推荐 RRULE 模板

| 用户说法 | 推荐周期 | RRULE |
|---|---|---|
| 每天早上自动跑 / 每日保温日报 | 工作日 9:00 | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=9;BYMINUTE=0` |
| 周一早上做一次周报 | 每周一 9:30 | `FREQ=WEEKLY;BYDAY=MO;BYHOUR=9;BYMINUTE=30` |
| 每天上下午各一次 | 每天 9:00 与 15:00 | 拆分为两个自动化，分别 `FREQ=DAILY;BYHOUR=9;BYMINUTE=0` 和 `FREQ=DAILY;BYHOUR=15;BYMINUTE=0` |
| 每两小时盯一次（高峰期短期使用） | 每 2 小时 | `FREQ=HOURLY;INTERVAL=2` |
| 入职月集中跟进 | 限定 6 月 | 配合 `validFrom="2026-06-01"`、`validUntil="2026-06-30"` 与 `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=9;BYMINUTE=0` |

⚠️ 受 `automation_update` 规则限制：只支持 `HOURLY` 和 `WEEKLY` / `DAILY` 范式，避免使用 `MONTHLY`、`YEARLY`、`MINUTELY`、`SECONDLY` 或多 RRULE 组合。

### 7.5 prompt 写法规范

自动化任务的 `prompt` 必须满足：

- 第一句明确"加载 warming-recruit-manager skill"
- 明确写清查询范围（我名下 / 指定导师 / 指定上级 + loginName）
- 明确写清输出形态（保温播报 / 保温日报 / 保温周报）
- 显式声明失败处理："若 hr-ai-data 不可用，请明确说明失败原因，不要编造数据"
- 不在 prompt 内写时间、工作区、Webhook、Token

**我名下日报模板**：

```
加载 warming-recruit-manager skill，按场景 C 流程查询当前招聘经理名下签约后待入职候选人，生成三级提醒分层的保温播报。若 hr-ai-data 不可用，请明确说明失败原因，不要编造数据。
```

**指定导师日报模板**：

```
加载 warming-recruit-manager skill，按场景 A 查询导师 lzhang 名下签约后待入职候选人，并按场景 C 三级提醒分层生成保温播报，结果开头标注查询范围。若 hr-ai-data 不可用，请明确说明失败原因，不要编造数据。
```

**指定组织日报模板（范围 ④，默认叠加"我名下"）**：

```
加载 warming-recruit-manager skill，按场景 A 范围 ④ 查询 PCG/QQ研发部 名下、且当前招聘经理对接的签约后待入职候选人，并按场景 C 三级提醒分层生成保温播报。结果末尾必须附"按子组织聚合小结"。若 hr-ai-data 不可用，请明确说明失败原因，不要编造数据。
```

**全组织视角周报模板（范围 ④，需用户明示）**：

```
加载 warming-recruit-manager skill，按场景 A 范围 ④ 全组织视角查询 IEG 名下签约后待入职候选人（不限招聘经理）。先调用 get_current_user_data_permission 核查行权限，无权限则停止；以"本周组织盘点"形式生成保温周报，结果不展示手机号、面评原文等敏感字段。若 hr-ai-data 不可用或权限不足，请明确说明失败原因，不要编造数据。
```

**周报模板**：

```
加载 warming-recruit-manager skill，按场景 C 流程查询当前招聘经理名下签约后待入职候选人，并以"本周重点"汇总形式生成保温周报，重点列出红灯事项与本周建议动作。若 hr-ai-data 不可用，请明确说明失败原因，不要编造数据。
```

**叠加企微推送模板（场景 E + 场景 D）**：

```
加载 warming-recruit-manager skill，按场景 C 流程查询当前招聘经理名下签约后待入职候选人，生成保温日报 Markdown，并按场景 D 通过 wework-bot 发送到已配置的企业微信群。若 hr-ai-data 或 wework-bot 不可用，请说明失败原因，不要编造数据或推送结果。
```

### 7.6 频次与边界

- **每日**：每日不超过 1 次主播报；如需上下午各看一次，第二次明确标注"补充关注"
- **每周**：每周不超过 5 次，避免占用招聘经理 IDE 通知
- **临近入职高峰期**：可用 `validFrom` / `validUntil` 限定生效区间，到期自动失效
- 若用户已存在同名 / 同范围的保温自动化，应优先建议 `suggested update`，而不是新建重复任务
- 不为同一招聘经理同时创建超过 3 个保温自动化，必要时引导合并

### 7.7 失败处理

| 失败点 | 处理方式 |
|---|---|
| 用户未在 CodeBuddy 环境 | 告知场景 E 仅在 CodeBuddy 内可用，引导改用场景 C 手动触发或场景 D 推群 |
| `automation_update` 调用失败 | 明确告知未创建自动化，保留 prompt / rrule 文本供用户手动配置 |
| 自动化运行时 hr-ai-data 不可用 | 按场景 C 失败处理输出"当前保温数据暂时不可用"，不得编造 |
| 自动化运行时查询返回空 | 输出零告警模板（见 4.3），不要伪造红灯事项 |
| 用户要求停止自动化 | 通过 `suggested update` 把 `status` 改为 `PAUSED`，并告知用户已暂停 |

任何失败场景都不得输出"已创建"、"已运行"、"已订阅"等成功表述。
