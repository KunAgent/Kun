- 单 BG、单职位，可能包含多个部门（BG 内的二级组织）
- CodeBuddy LLM 直接做分析，不依赖外部 AI 服务
- **仅支持社招和校招，不适用于活水数据**

## 前置条件（重要！必须首先检查）

本 Skill 需要 Skill1（interview-data-processor）清洗后的标准化数据（`cleaned_data.json`），要求数据已完成字段映射、归一化、过滤和质量检查（≥60 条有效记录）。

### 自动检测与前置调用

**用户通常直接带着原始 Excel 触发本 Skill，必须在开始建模前自动检测并处理：**

1. **检查输入数据格式**：
   - 如果用户上传的是 **Excel/CSV 文件**（原始数据）→ **必须先调用 Skill1 清洗**
   - 如果用户提供的是 **JSON 文件** → 检查是否包含 `resultNorm`、`gradeNorm` 等标准化字段
     - 有标准化字段 → 直接使用
     - 无标准化字段 → 视为未清洗数据，先调用 Skill1

2. **调用 Skill1 清洗**：
   ```bash
   python3 ~/.codebuddy/skills/interview-data-processor/references/scripts/data_clean.py \
     --input {用户上传的文件} \
     --output cleaned_data.json \
     --report quality_report.md
   ```

3. **清洗完成后**：展示质量报告摘要，确认职位，再继续建模流程。

**绝对不能跳过清洗步骤直接用原始 Excel 建模，否则 resultNorm 等字段为空，统计结果全部错误。**

## Step 1: 能力要素提取与统计

根据数据量自动选择路径：

| 数据量 | 路径 | 说明 |
|--------|------|------|
| < 100 条 | **路径 A：纯 LLM** | 逐批处理全量评价，语义理解准 |
| ≥ 100 条 | **路径 B：混合模式** | 本地词典批量匹配 + LLM 补充样本 |

---

### 路径 A：纯 LLM 模式（仅 < 100 条时执行）

逐批处理全量评价（每批 10 条，约 6 轮对话）：

- 从 远程资产 `skill_taxonomy` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 提取**当前职位**的专业技能列表注入 prompt
- 参考 `references/skill-synonyms.json` 同义词辅助归一化
- 使用 远程资产 `prompts` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 中的提取 prompt
- 对每条评价提取 3-8 个要素，归一化为标准词条名
- 泛化词直接丢弃，每个要素标注 sentiment

**LLM 提取后：词条融合（含频次数据支撑）**

提取完成后，将 LLM 的词条与本地标准词典做融合，结合频次统计辅助判断：

1. **精确匹配** → 直接使用标准名
2. **同义匹配** → 使用标准名，LLM 表述加入同义词
3. **含义重叠** → 结合频次比较：LLM 词频 ≥3 倍标准名 → 建议更新标准名；否则保留标准名
4. **全新发现** → 保留为新词条候选，标注频次

**交互策略**：
- 融合建议 ≥ 10 条 → 展示融合建议表，等待用户确认
- 融合建议 < 10 条 → **自动应用**（精确/同义匹配自动执行，含义重叠和新发现简要告知，不阻塞流程）

融合建议表（仅 ≥10 条时展示）：

```
💡 词条融合建议：

| LLM 提取 | 本地标准 | 数据支撑 | 建议 |
|---------|---------|---------|------|
| {LLM词} | {标准词} | LLM词{N}次({R}%) vs 标准词{N}次({R}%) | {建议} |
```

**更新规则**：
- "更新标准名"需用户确认，且必须有频次数据支撑（≥3 倍差距）
- "加入同义词"自动执行
- "新增独立词条"需用户确认

---

### 路径 B：混合模式（仅 ≥ 100 条时执行）

##### B1. 本地词典匹配（秒级完成）

```bash
python3 references/scripts/local_match.py \
  --data cleaned_data.json \
  --position {职位} \
  --recruit-type {社招/校招} \
  --output match_result.json
```

脚本自动完成：加载同义词词典 → 按职位裁剪专业技能 → 子串匹配 → 输出统计。

##### B2. LLM 补充提取（渐进式）

**第一批（20 条，必做）**：优先选零匹配记录（词典盲区），分层抽样。
**第二批（30 条，按需）**：第一批已覆盖 90%+ 标准词条 → 跳过；否则继续补充。

##### B3. 合并与统计

去重合并本地 + LLM 结果，LLM 新发现纳入统计（标记为"AI 补充"）。

---

### 统计计算（两种路径共用）

| 用户可见名称 | 内部代号 | 含义 |
|------------|---------|------|
| **提及次数** | F | 该能力项在所有面评中被提到的次数 |
| **提及率** | R_total | 多大比例的面评提到了这项能力 |
| **通过者提及率** | R_admit | 通过的候选人中多大比例被提到这项能力 |
| **结果相关度** | Phi | 这项能力被提到和面试通过之间的关联强度（≥0.3 强/0.15-0.3 中/< 0.15 弱） |

> **在报告和用户交互中，始终使用中文名称，不展示内部代号。**

### 多维度分组统计

- **社招**：按职级段（10-11级 / 7-9级）+ 按部门，各自独立统计
- **校招**：整体统计（不分职级段）+ 按部门

## Step 2: 按部门生成能力模型

**不存在"通用模型"步骤**——直接基于各部门的统计数据建模。

### 处理策略：提取共享，建模拆分

每份报告 = **1个部门 × 1种招聘类型 × 1个职位**。

- 提取只做一次（全量数据），建模按部门拆分
- 建模每个任务约 1-2 轮 LLM 对话
- 报告跑完一个立即输出，不用等全部完成
- **建模前读取 远程资产 `bg_culture` (通过 `_remote-assets.yaml` 调 MCP `get_document` 拉取) 中对应 BG 的 `s4Hint`**，将 BG 文化特色融入 definition 和 tasks 描述

### 建模输出结构

**能力模型（capabilityModel）**：
- 4 个维度，每个维度按权重降序展示**全部**能力项（不截断、不省略）
- 每项含：name、group、weight（同维度累加=100%）、definition（20-40字）、tasks（至少2条）
- tasks 按维度区分：**背景资质**→典型条件，**硬技能/软素质/文化匹配**→常见工作任务

**A+ 典型画像（portrait）**：background + professional + softSkill + summary

**五档评分标准（ratings）**：
- 覆盖各维度权重排名前 90% 的能力项
- S/A+/A/AB 四档，直接描述行为和成果，**禁止以"候选人"开头**
- 描述必须包含：具体场景 + 行为表现 + 达成结果
- **禁止**使用"优秀""良好""一般"等空洞形容词

**部门下层组织差异（deptDiff）**：
- 面试量 Top3 且 ≥10 条的子组织，**合并在建模 prompt 中一并输出**（不单独调 LLM）

**数据不足处理**：某职级段 < 10 条时，标注"样本不足"，基于整体数据调整。

## 用户反馈与调整

每份报告输出后，分两步交互：

### 第一步：确认模型

**能力项调整（需用户确认）**：

| 用户反馈 | 处理方式 |
|---------|---------|
| "去掉XX能力" | 移除该项，重新归一化权重 |
| "补充XX能力" | 新增该项，重新计算统计和权重 |
| "XX改名为YY" | 替换词条名，保留统计数据 |
| "XX权重应该更高" | 调整权重约束，重新生成 |
| "评分描述太笼统" | 追加场景化要求，只重新生成 ratings |

**同义词学习（自动追加，不阻塞）**：
- LLM 成功归一化到已有标准词条、出现 ≥2 次、词长 2-8 字、不在泛化词黑名单中 → 自动追加到 `references/skill-synonyms.json`
- 累计不认可 ≥3 次且认可率 < 30% → 自动移除
- 追加/移除后简要告知用户，不需要逐条确认

### 第二步：生成应用文档（模型确认后，用户按需触发）

```
模型已确认。需要基于这份模型生成哪些招聘应用文档？
A. JD（岗位描述）  B. 结构化面试问题库  C. 面试评分表  D. 简历筛选标准
可多选，也可以跳过。
```

各文档的详细模板见 `references/report-templates.md`。

## 注意事项

1. **不生成通用模型**：直接按部门建模
2. **社招两段、校招整体**：社招只输出 10-11 级和 7-9 级
3. **definition 和 tasks 必须场景化**：从评价原文提炼业务关键词
4. **数据不足要标注**：某维度/职级段样本不足时必须明确标注
5. **保持轻量**：面向单部门招聘经理，不做平台化批量处理
