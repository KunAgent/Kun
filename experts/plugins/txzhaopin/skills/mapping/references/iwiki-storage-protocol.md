## 用户隔离原则

共享 iWiki 用于招聘团队统一沉淀知识，但每个招聘经理只能查重、更新自己生产的知识（按 `用户-{user_key}` 命名空间隔离）。

实现方式：
1. 每次 iWiki 读写前先调用 `getCurrentUser` 获取当前用户唯一登录标识，记为 `{user_key}`。
2. 在 `root parentid=4021939025` 下为每个用户维护独立命名空间：`用户-{user_key}`。
3. 用户的公司、候选人、项目、面评、报告、索引和变更日志均写入自己的 `用户-{user_key}` 目录下。
4. 查重时必须同时满足：
   - 使用 `searchDocument` 的 `author=[{user_key}]` 限定作者；
   - 结果页面位于当前用户的 `用户-{user_key}` 目录树下。
5. 更新前必须调用 `metadata(docid)` 校验页面 `creator` 或 `owner` 与 `{user_key}` 一致。
6. 如果查到其他用户创建的相似页面，只能作为只读参考，不得 `saveDocument` 更新；如需沉淀，必须在当前用户目录下新建自己的页面。

## 写入前必须

1. 过滤隐私与敏感信息
2. 获取当前用户身份，并限定在当前用户命名空间内查重
3. 使用 `searchDocument` 查重，且只处理当前用户创建的页面
4. 明确页面类型：公司 / 候选人 / 项目 / 面评 / 报告
5. 已存在的本人页面只增量合并，不覆盖旧内容
6. 每次写入后只更新当前用户目录下的索引页和变更日志页

## 禁止写入

- 私人联系方式
- 身份证件
- 家庭信息
- 未授权的薪资细节
- 猎头私有备注
- 无来源的人才判断

## 推荐目录结构

在 `root parentid=4021939025` 下按用户维护目录：

```text
知识源
└── 用户-{user_key}
    ├── 00-索引
    ├── 01-公司组织库
    ├── 02-候选人档案
    ├── 03-项目经历库
    ├── 04-面评归档
    ├── 05-Mapping报告
    └── 99-变更日志
```

若用户目录、分类目录或索引页不存在，先使用 `getSpacePageTree` 检查，再通过 `createDocument` 创建。

## 多页面沉淀规则

`05-Mapping报告` 只保存最终交付报告，不能作为唯一知识沉淀。每次 Mapping 结束后，必须把结构化结果拆成多类页面并交叉引用：

1. `01-公司组织库`：写入目标公司、部门、团队、负责人、组织关系、地域和业务线。
2. `02-候选人档案`：写入每个候选人/关键人物的公开履历、职位、技能标签、来源证据、置信度和 open questions。
3. `03-项目经历库`：写入公开 deal、论文、开源项目、作品集、业务项目等可复用经历，并反向链接相关候选人与公司。
4. `04-面评归档`：仅在用户明确提供且已脱敏、允许共享时写入面评/访谈/评估材料；否则不得生成该类页面。
5. `05-Mapping报告`：保存完整 Markdown/HTML 报告，并链接上述实体页面。
6. `00-索引`：记录本次新增/更新的公司、候选人、项目、报告页面和交叉引用。
7. `99-变更日志`：记录本次新增、更新、跳过、过滤和未生成原因。

如果某类实体为空，不要伪造页面；在 `99-变更日志` 中说明未生成原因。

## 安全边界说明

上述规则是 Skill 层面的写入协议，可确保 Skill 不会主动查重或更新其他用户页面。若需要 iWiki 平台层面的强制隔离，还需要在 iWiki 空间/目录权限中配置“用户仅可编辑本人目录或本人创建页面”；当前 MCP 写入流程不负责修改 iWiki 权限配置。
