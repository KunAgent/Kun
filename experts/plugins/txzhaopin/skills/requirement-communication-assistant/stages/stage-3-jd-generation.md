# 📌 环节③：JD 生成

### 职责
读：①②；只写 `meta` 和 `stage_3_jd`；另外写一份独立 `JD.md` 文件到 workspace。
前置：② `completed`。

### 核心哲学
> **JD 是画像的"候选人视角"表达。同样一项能力要求，面向候选人要讲清楚"你要做什么、我们需要你具备什么、加分是什么"。**
> **反面特征不出现在 JD 里，而是转成正向表达（隐含排除）。**

## 子步骤 ③-a：数据准备

### 1. 读取上下文
- 读 `recruitment_context.json`
- 取画像：`stage_2_persona` 的 `must_have / preferred / nice_to_have / anti_patterns`
- 取胜任力模型：`stage_2_persona.competency_model`
- 取需求描述：`stage_1_requirement.clarified_need` 和 `hidden_meaning_translated`
- 取岗位基本信息：`meta.job_title / meta.project`

### 2. 数据完备性检查
| 字段 | 缺失时处理 |
|------|----------|
| `clarified_need` 为空 | 提示用户补充一句岗位的核心业务场景 |
| `must_have` 为空 | 拒绝生成，回退到环节② |
| `job_title` 为空 | 询问用户"这个岗位的对外名称是什么？" |
| 年限/城市/学历 未在画像中体现 | 从 `clarified_need` 里抽取；仍缺 → 询问用户 |

### 3. 拉取敏感词库（前置，用于生成时主动规避）

JD 生成前，通过 recruit-mcp 拉取敏感词文档，作为 ③-b 生成时的**硬约束**。可与读取 context 并行。

**调用方式**（与 SKILL.md → 🔌 MCP 文档调用规范一致）：
```
serverName: recruit-mcp
toolName:   CallAPI
arguments:
{
  "apiId": "recruit.recruit-ai-service.get_document",
  "params": { "documentId": "52" }
}
```

**解析**：成功判定见 SKILL.md MCP 规范；正文 = `response.data.data`，解析为敏感词清单（后台使用，不回显给用户）。

**失败兜底（强制，绝不阻塞）**：
- 拉取失败 / 超时 / 文档为空 → 静默跳过敏感词库，JD 照常生成；改用通用合规常识规避（性别/年龄/地域/婚育/学历歧视等）
- 在 context 标记 `stage_3_jd.sensitive_check = "skipped"`，便于审计
- ❌ 不向用户暴露"敏感词文档拉取失败"等任何内部信息

## 子步骤 ③-b：三段 JD 生成

> 🚫 **敏感词规避（前置硬约束）**：③-a 第 3 步已拉取敏感词库（documentId=52）。生成「岗位职责 / 岗位要求 / 加分项」三段以及岗位介绍语时，**必须主动避开清单中的所有敏感词**，用合规的同义表达替代——这是生成时的硬性要求，不是事后过滤。
> - 优先用语义等价的合规表达替换敏感词
> - 若某处敏感表述无法用同义表达替代，则**删除该表述**，不强行保留
> - 规避过程对用户无感：直接产出安全 JD，**不展示"规避了哪些词"清单，不要求用户确认**
> - 敏感词库拉取失败时，按通用合规常识规避（性别/年龄/地域/婚育/学历歧视等）

### 段落 1：岗位职责（Responsibilities）

**来源优先级**：
1. `stage_1_requirement.clarified_need` 中的业务动作描述（最权威）
2. `stage_2_persona.must_have` 中「核心动作」类的能力项（如"负责线上服运维"本身就是一条职责）
3. 模型基于岗位类型 + 画像自行推断（**必须标 *️⃣**）

**生成要求**：
- 3–6 条，每条一个动作 + 一个对象 + 一个目标
- 动词开头："负责 / 主导 / 参与 / 优化 / 搭建 / 跟进..."
- 避免空话（如"保证项目质量"）；要有具体对象（"保证 XX 模块线上零 P0 事故"）
- AI 推断的条目末尾加 `*️⃣`，并在 JD 末尾加注释
- ⚠️ **上限 6 条**，超过时合并相近职责或砍掉优先级最低的

**模板**：
```
【岗位职责】
1. {动词} {对象}，{目标 / 产出物}
2. ...
3. ...
*️⃣ 标记项为 AI 基于画像推断，发布前请团队核实
```

### 段落 2：岗位要求（Requirements）

**来源**：
- `stage_2_persona.must_have` 全量（硬技能）+ 年限/学历/城市等硬门槛
- `stage_2_persona.competency_model.dimensions` 中权重为"核心维度 1.5x"的软素质（提取维度名 + 一句话说明）

**生成要求**：
- 必备项，候选人不满足则直接不投
- ⚠️ **上限 6 条**（含软素质合并项）
- 每条一句话，可量化（"3 年以上"/"精通"/"主导过"）
- 顺序：硬性条件（年限/学历/城市）→ 核心硬技能 → 软素质（**合并为 1 条**）
- 面向候选人的第二人称（"你需要..."）或第三人称（"具备..."），整份 JD 统一
- **软素质合并规则**：从胜任力模型核心维度（1.5x）中提取 2-3 个最关键的，合成一条自然语言描述

**软素质合并示例**：
| 核心维度（多个） | 合并为 JD 中的一条 |
|----------------|-------------------|
| 结构化思维 + 影响力 | 善于拆解复杂问题并推动跨团队协作落地 |
| 学习敏锐度 + 抗压韧性 | 能在快节奏环境中快速学习新事物并保持高效产出 |
| 自驱力 + 结果导向 | 自驱力强，目标感清晰，能独立推进项目到交付 |

> ⚠️ 只取核心维度（1.5x权重）放入"岗位要求"，一般维度（1.0x）放入"加分项"。

**模板**：
```
【岗位要求】
1. {年限} {学历} 及以上，{城市} 办公
2. {能力1}：{简短说明}
3. {能力2}：{简短说明}
...
```

### 段落 3：加分项（Plus）

**来源**：
- `stage_2_persona.preferred` + `stage_2_persona.nice_to_have` 合并（硬技能类）
- `stage_2_persona.competency_model.dimensions` 中权重为"一般维度 1.0x"的软素质（合并为 1 条，用候选人语言表达）
- **反面特征的正向转换**：将 `anti_patterns` 翻译为"具备 XX 者优先"形式（反面特征本身不出现在 JD 里）

> ⚠️ **上限 4 条**。来源多时按优先级砍：反面转换 > preferred硬技能 > 一般软素质 > nice_to_have。一般维度软素质同样合并为 1 条。

**反面 → 加分 的转换规则**：

| 反面特征（不要这种人） | 转换为加分项（有这种人更好） |
|----------------------|------------------------------|
| 纯端游背景、无线上服经验 | 3 年以上大型线上服务运维经验 |
| 长期国企/外企舒适圈 | 在互联网/游戏行业一线团队有项目主导经历 |
| 只做过单机项目 | 有多人在线游戏/高并发项目经验 |
| 技术栈过时 | 近 2 年内接触过 {新技术栈} 或有迁移经验 |

**转换原则**：
- 只有当反面特征能被合法地翻译成正向描述时才转（即存在一个对等的正向能力）
- 不能直接表达排斥（如"非国企背景者优先"这种不合规的表达一律禁止）
- 转换后的条目如果和已有 preferred 重复，合并即可

**模板**：
```
【加分项】（最多 4 条）
1. {能力或经历}
2. ...
3. ...
4. ...
```

## 子步骤 ③-d：迭代改稿

### 用户反馈处理

| 用户回复 | 处理 |
|---------|------|
| "确认" / "没问题" / "OK" | 写回 context 收尾态；展示全链路收尾文案 |
| "XX 条不对" / "改一下 YY" | 只改那一条，其他不动；改完重新展示整份 JD，再次询问确认 |
| "加一条 XX" | 新增到对应段落，重新展示 |
| "再出一版 XX 风格的" | 生成新版本（同一 JD 的风格变体），展示对比，询问用户选哪版 |
| "整个不对，重来" | 回溯：问"是画像有问题还是 JD 表达有问题？" → 画像 → 回环节② / 表达 → 重新 ③-b |

### 改稿原则
- 每次改稿都要**重新展示完整 JD**，不要只给"改动部分"
- 每次改稿都要**重新同步写入 {job_title}.md 文件**（整份文件重写，含画像和胜任力模型）
- `meta.version +1`；`stage_3_jd.revisions` 追加一条记录

## ⚠️ 注意事项

1. **JD 是"候选人视角"的，不是"招聘经理视角"的**：不要出现"我们希望他..."、"这个人要..."；面向候选人用第二人称"你"或客观第三人称描述
2. **反面特征禁止直接出现**：一律转换为正向加分项，或干脆不写
3. **AI 推断的职责必须标 *️⃣**：让招聘经理知道哪些需要人工核实
4. **年限/学历/城市 等硬门槛**：优先从画像抽，画像没有就从 ①`clarified_need` 抽，都没有就问用户，不要猜
5. **{job_title}.md 文件是核心产物**：每次改稿都要同步更新，保持与 context 中 `jd_content` 一致
6. **写 context 必须先读后写、版本号 +1**
7. **禁止合规风险的表达**：性别/年龄/地域/婚育/学历歧视类描述一律不写入 JD，哪怕画像里有也要过滤。此外，③-a 第 3 步拉取的敏感词库（documentId=52）中的所有词，生成时必须主动避开（前置规避，详见 ③-b 开头约束）；仅校验 JD 三段+介绍语，不校验画像/胜任力模型部分
8. **整份 JD 保持语气一致**：全程用同一人称、同一风格；迭代改稿时也要确保风格统一
