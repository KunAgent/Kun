# CHANGELOG v3.9 — 通过率/转化率强约束（2026-06-11）

## 背景

用户提出关键风险：**AI 在面对"转化率/通过率"类问题时会自由发散，自己创造计算逻辑**（例如用 `COUNT(发 offer) / COUNT(发起面试)`，漏掉"未提交"扣除项），导致和 `composite/funnel-rates.md` 已治理的 9 个标准通过率口径不一致。

而通过率类指标是高频被引用的核心 KPI，错一个公式会导致**整个业务团队复述错误结论**，比"单值少算 1 天"的影响大得多。

## 新增 v3.9 三层强约束

### 层 1：Step 1 § 类型 C 标注强制路径

将原 "C 漏斗/趋势" 改为 "C 漏斗/转化率/通过率"，并加 🔴 标记，强制走 § Step 1.5。

### 层 2：Step 1.5 新增完整章节（核心铁律）

包含 4 个要点：

1. **触发关键词清单**：覆盖"通过率/转化率/接受率/入职率/漏斗"等中英文表述
2. **强制路径 3 步**：先查 `funnel-rates.md` 9 个清单 → 命中则直接复制 SQL → 不命中则强制反问用户
3. **9 个已治理通过率清单**（治理基线 Row 26-34 完整列表）+ 强制 ID 映射
4. **5 类反面案例**：列出 AI 常犯的自创公式错误 vs 正确做法

### 层 3：Step 3 § 优先级 0 前置规则

SQL 拼装阶段也加同样约束，作为兜底。

## 配套防御：R6.7-R6.9 新规则

`scripts/regression_check.py § R6` 新增 3 条子规则，确保 SKILL.md 这段约束不被误删：

- **R6.7**：必须有 "通过率/转化率强约束" / "Step 1.5" / "funnel-rates 路径" 关键词
- **R6.8**：必须列出 9 个已治理通过率清单（recruit-send-offer-rate / recruit-entry-rate / recruit-hr-intv-rate 等）
- **R6.9**：必须明确"禁止自由发散" / "不要自己拼公式"

## 关键设计原则

| 场景 | 行为 |
| --- | --- |
| 用户问的率在 9 个清单中 | 直接复制 funnel-rates.md SQL，不允许任何改造 |
| 用户问的率不在 9 个清单中 | **强制反问用户精确口径**，绝不擅自拼公式 |
| 用户问多个率 | 直接套 `recipes/card-C-funnel-rates.md` CTE 一次出全部 |
| 用户问 v3.0 已废弃的率（如"进入 offer 审批率"）| 明确告知废弃，建议改用 D11 / D12 |

## 📝 v3.9 后续补充 #2（2026-06-11 20:08）— 平均招聘天数指标按用户标准重构

### 背景

用户提供了治理口径标准 SQL，要求按其口径重写 `composite/recruit-social/avg-recruit-days.md` 和 `recipes/card-A § A5`。

### 标准文档的核心差异（vs v3.8 之前的实现）

| 维度 | v3.8 之前 | v3.9 新标准 |
|---|---|---|
| 聚合粒度 | `AVG(所有流程的 recruit_days)` — **按流程加权** | `AVG(每个岗位的岗位级平均)` — **按岗位等权** |
| 流程区分 | 社招/活水 CASE WHEN 混合 | **CTE 分流**（社招 `flow_id=3 + is_entry='是'` + 活水 `flow_id=5`）+ UNION ALL |
| `publish_time` 处理 | 直接用 t2.publish_time | **`CAST(p.publish_time AS DATE)`**（明确 DATE 字符串） |
| 负数过滤 | 无 | **`WHERE recruit_days >= 0`** 过滤异常数据 |
| 在 card-A 中位置 | 拼在 A3-A12 大 SQL 内 | **拆出独立 SQL**（同 A1/A7 模式，前端代入）|

### 业务影响

按岗位等权的 AVG 更代表业务平均水平 — 避免少数高量岗位（如校招同岗百人入职）拉偏整体平均。

### 修订文件

| 文件 | 修订内容 |
|---|---|
| `composite/recruit-social/avg-recruit-days.md` | 完全重写：CTE 分流 + 子查询模式 + 按岗位聚合 + 替代用法（按岗位明细） |
| `recipes/card-A § A5` | 从大 SQL 拆为独立 SQL；大 SQL 内 `avg_recruit_days` 列置 `CAST(NULL AS DOUBLE)` 占位 |

### 子查询模式 vs 用户标准的取舍

用户文档用直 `INNER JOIN catalog_..._T_POST` 写法，但 README 勘误 A 明确（2026-06-08 实测）：直 JOIN 跨表会触发 `dos_current_user is ambiguous` 报错。因此采用「先用子查询各自过滤再 JOIN」模式 — **业务语义完全等价**，但满足 R3 铁律。

## ⚠️ v4.0 修正（2026-06-13）— 回退「岗位等权」，恢复「流程加权」

### 背景

经复核，上文 v3.9 补充 #2 引入的「先按岗位聚合再 AVG（岗位等权）」口径**有误**：用户提供的标准 SQL 文档（`平均招聘天数_指标SQL.md`）中，整体口径其实是**流程加权**（对合并后所有流程直接 `AVG(recruit_days)`），其"按岗位聚合 + ORDER BY"只是**按岗位明细展示**用法，并非整体指标计算口径。

### 修正内容

| 维度 | v3.9（❌ 错误） | v4.0（✅ 修正） |
|---|---|---|
| 整体聚合粒度 | `AVG(每个岗位的岗位级平均)` 岗位等权 | `AVG(所有流程 recruit_days)` 流程加权 |
| `position_avg` CTE | 作为整体口径必经层 | **删除该层限制**；按岗位聚合仅保留为可选明细展示 |
| card-A § A5 | 独立 SQL + 占位 NULL + 前端代入 | **内联回 A3-A12 大 SQL**（流程加权与大 SQL 架构一致），无需独立 SQL/代入 |

### 修订文件

| 文件 | 修订内容 |
|---|---|
| `composite/recruit-social/avg-recruit-days.md` | 去掉 `position_avg` 等权层，主 SQL 改为合并流程直接 AVG；定义/公式/注意事项同步更新 |
| `recipes/card-A § A5` | A5 内联回大 SQL（流程加权 `AVG(CASE WHEN ...)`），删除独立 SQL 与前端代入段 |
