# A/B/C/D/E 输出形态规范

> 不同问题类型 → 不同回答结构。先识别问题类型，再选模板。

## 识别问题类型

| 信号词 | 类型 |
| --- | --- |
| "多少人/个" + 具体时间 + 具体组织 | **A 单值** |
| "对比/比较/A vs B" / "各部门" / "各 BG" | **B 多指标对比** |
| "漏斗" / "转化" / "走势" / "趋势" / "按月" | **C 漏斗/趋势** |
| "总体情况" / "需求进展" / "招得怎么样" / "看一下" | **D 总览** |
| "为什么 / 为啥" / "原因" / "异常" / "怎么解释" | **E 归因** |

## 口径必披露项（所有形态通用）

无论 A/B/C/D/E，回答末尾的"口径"段必须明确列出以下 5 项（不可省略）：

| 项 | 写法示例 |
| --- | --- |
| 时间窗 | `2026-05-01 ~ 2026-05-31（按 hire_date）` |
| 管理主体 | `腾讯集团本部` 或 `含子公司（请用户确认范围）` |
| 国家 | `中国` 或 `亚太` 或 `全球（含所有国家）` |
| 流程范围 | **必写**：`仅社招（flow_id=3）` 或 `社招 + 活水（flow_id IN (3,5)）` |
| 数据时效 | `数据截至 YYYY-MM-DD（T-1）` |

> 为什么"是否含活水"必写：活水（内部流转）和社招（外招）在业务方眼里是两种性质完全不同的招聘行为，
> 数据里 `flow_id=5` 的存量也很大。同一个数字"含 vs 不含活水"差异显著，
> 业务方拿数对外汇报时不能让对方猜口径。

---

**结构**：数字一句话 + 口径

```markdown

口径：
```

## B 多指标对比

**结构**：markdown 表格 + 一句结论

```markdown
**运营管理部 vs 技术运营部：2026Q1 社招漏斗对比**

| 阶段 | 运营管理部 | 技术运营部 | 差异 |
| --- | --- | --- | --- |
| 发起面试数 | 234 | 412 | - |
| 部门内通过率 | 67% | 61% | +6pp |
| Offer 发送数 | 38 | 56 | - |
| 入职率 | 78% | 81% | -3pp |

**结论**：运营管理部在面试通过率上略高，但绝对漏斗规模小于技术运营部；入职率两者相近。

口径：
- 时间窗：2026-01-01 ~ 2026-03-31
- 管理主体：腾讯集团本部
- 国家：中国
- 流程范围：仅社招（flow_id=3，不含活水）
- 对比维度：recruit_post_org_full_name LIKE '%运营管理部%' / LIKE '%技术运营部%'
```

## E 归因

**结构**：现象描述 + 2-3 个候选假设 + 数据支撑

```markdown
**问题：本月 offer 接受率从上月的 82% 降到 71%**

**数据观察**：
| 月份 | 发出 offer | 接受 offer | 接受率 |
| --- | --- | --- | --- |
| 2026-05 | 156 | 128 | 82.1% |
| 2026-06（截至 6/8）| 67 | 48 | 71.6% |

**候选解释**（按可能性排序）：

1. **样本量小造成的波动**（最可能）
   - 6 月仅 8 天数据，发出 67 个 offer，统计噪音较大
   - 建议月末再回看

2. **特定职位类的拒 offer 集中**
   - 拆 `mapping_position_name` 看，是不是某类岗位异常
   - 如需明细，可追问"按职位类拆"

3. **薪资市场变化 / 公司政策调整**
   - 数据无法直接验证，需要业务方判断

**追问建议**：要不要按职位类 / 招聘经理拆开看？
```
