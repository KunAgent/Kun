# 2.10.2 隐式转换差异

## 概述

不同引擎在数据类型隐式转换方面存在差异，这可能导致相同SQL在不同引擎中产生不同结果或报错。SuperSQL以THive和Spark 3.3的转换规则为标准。

---

## 数值类型转换

### 整数类型之间的转换

| 转换方向 | THive | Spark 3.3 | StarRocks | Presto | 说明 |
|---------|-------|-----------|-----------|--------|------|
| TINYINT → INT | ✅ 自动 | ✅ 自动 | ✅ 自动 | ✅ 自动 | 完全兼容 |
| INT → BIGINT | ✅ 自动 | ✅ 自动 | ✅ 自动 | ✅ 自动 | 完全兼容 |
| BIGINT → INT | ❌ 需显式 | ❌ 需显式 | ❌ 需显式 | ❌ 需显式 | 可能溢出 |

| INT → DOUBLE | ✅ 自动 | ✅ 自动 | ✅ 自动 | ✅ 自动 | 完全兼容 |
| FLOAT → INT | ❌ 需显式 | ❌ 需显式 | ⚠️ 可能自动 | ❌ 需显式 | StarRocks行为不一致 |
| DOUBLE → INT | ❌ 需显式 | ❌ 需显式 | ⚠️ 可能自动 | ❌ 需显式 | 截断小数部分 |

| 转换方向 | THive | Spark 3.3 | StarRocks | Presto | 说明 |

| 转换方向 | THive | Spark 3.3 | StarRocks | Presto | 说明 |
|---------|-------|-----------|-----------|--------|------|

| STRING → DOUBLE | ✅ 自动 | ✅ 自动 | ⚠️ 可能报错 | ⚠️ 可能报错 | 非数字字符串会失败 |

```sql

SELECT '123' + 1;  -- 结果: 124

SELECT CAST('123' AS INT) + 1;  -- 推荐写法
```

以下表格详细对比了Spark、StarRocks和Presto在不同场景下的隐式转换行为：

### 比较运算符中的隐式转换

| 表达式 | Spark | StarRocks | Presto | 说明 |
|--------|-------|-----------|--------|------|
| string < / > / <= / >= int | 两边转double | 两边转double | 两边转double | 数值比较 |
| string < / > / <= / >= bigint | 两边转double | 两边转double | 两边转double | 数值比较 |
| string < / > / <= / >= float | 两边转double | 两边转double | 两边转double | 数值比较 |
| string < / > / <= / >= double | 两边转double | 两边转double | 两边转double | 数值比较 |
| string = int | 两边转double | int转string | 两边转double | ⚠️ 行为不一致 |
| string = bigint | 两边转double | bigint转string | 两边转double | ⚠️ 行为不一致 |

| string != float | 两边转double | 两边转double | 两边转double | 一致 |
| string != double | 两边转double | 两边转double | 两边转double | 一致 |

### 空字符串比较特殊情况

| 表达式 | Spark | StarRocks | Presto | 说明 |
|--------|-------|-----------|--------|------|
| int != '' | NULL | int转string | NULL | 空字符串处理差异 |
| bigint != '' | NULL | int转string | NULL | 空字符串处理差异 |
| float != '' | NULL | '' 转double | NULL | 空字符串处理差异 |
| double != '' | NULL | '' 转double | NULL | 空字符串处理差异 |

**重要提示**：
- ⚠️ **等值比较**：Spark倾向于转double，StarRocks倾向于转string，Presto保持转double
- ⚠️ **不等值比较**：与等值比较规则一致
- ⚠️ **空字符串**：与数值比较时，Spark和Presto返回NULL，StarRocks尝试转换

**示例说明**：

```sql
-- 示例1: string与int的等值比较
SELECT '123' = 123;
-- Spark: TRUE (两边转double: 123.0 = 123.0)
-- StarRocks: TRUE (int转string: '123' = '123')
-- Presto: TRUE (两边转double: 123.0 = 123.0)
-- 结果一致但转换方式不同

-- 示例2: string与int的等值比较（边界情况）
SELECT '123.5' = 123;
-- Spark: FALSE (123.5 != 123.0)
-- StarRocks: FALSE ('123.5' != '123')
-- Presto: FALSE (123.5 != 123.0)
-- 结果一致但转换逻辑不同

-- 示例3: 空字符串与数值比较
SELECT 100 != '';
-- Spark: NULL
-- StarRocks: TRUE (100 != NULL or 字符串比较)
-- Presto: NULL

-- 推荐：明确类型转换
SELECT CAST('123' AS INT) = 123;  -- 推荐写法，避免隐式转换差异
```

### NULL值比较特殊行为

**Spark的NULL语义兼容（THive兼容模式）**：

Spark通过`spark.sql.thive.nullSemantic.enabled`参数（默认值为true）支持THive的NULL比较语义：

```sql
-- 示例1: NOT IN表达式的NULL处理
SELECT cstring FROM test.table WHERE cstring NOT IN ('1');

-- 当cstring含有NULL值：
-- Spark (THive兼容): NULL值会被过滤掉（不出现在结果中）
-- 标准SQL/其他引擎: NULL值不会被过滤（可能导致整个结果为空）

-- 示例2: IN表达式的NULL处理
SELECT cstring FROM test.table WHERE cstring IN (NULL);

-- 当cstring含有NULL值：
-- Spark (THive兼容): NULL值会被过滤掉
-- 标准SQL/其他引擎: NULL值不会被过滤

-- 推荐写法：明确处理NULL
SELECT cstring FROM test.table 
WHERE cstring NOT IN ('1') OR cstring IS NULL;  -- 明确是否包含NULL
```

**最佳实践**：
- 避免在IN/NOT IN中使用NULL值
- 使用`IS NULL` / `IS NOT NULL`明确判断
- 了解不同引擎的NULL处理差异

## 运算符中的隐式转换

### 算术运算符

```sql
-- 示例1: 整数与浮点混合运算
SELECT 10 + 3.5;  
-- THive/Spark: 13.5 (INT→DOUBLE)
-- StarRocks/Presto: 13.5 (一致)

-- 示例2: 字符串与数值运算
SELECT '100' + 50;
-- THive/Spark: 150 (STRING→INT)
-- StarRocks/Presto: 报错，需要CAST

-- 推荐写法
SELECT CAST('100' AS INT) + 50;  -- 明确转换
```

### 比较运算符

```sql
-- 示例1: 不同数值类型比较
SELECT 100 = 100.0;
-- 所有引擎: TRUE (INT→DOUBLE)

-- 示例2: 字符串与数值比较
SELECT '100' = 100;
-- THive/Spark: TRUE (STRING→INT)
-- StarRocks/Presto: FALSE (类型不匹配)

-- 推荐写法
SELECT CAST('100' AS INT) = 100;  -- 明确转换
```

### 逻辑运算符

```sql
-- 示例: NULL值处理
SELECT NULL AND TRUE;
-- THive/Spark: NULL
-- StarRocks: NULL
-- Presto: NULL (一致)

-- WHERE子句中的隐式转换
WHERE cint  -- THive/Spark: 0=FALSE, 其他=TRUE
-- StarRocks/Presto: 报错，需要明确的布尔表达式

-- 推荐写法
WHERE cint <> 0  -- 明确的布尔条件
```

## NULL值处理差异

### NULL的传播

```sql
-- 算术运算中的NULL
SELECT 100 + NULL;
-- 所有引擎: NULL (一致)

-- 字符串连接中的NULL
SELECT CONCAT('hello', NULL);
-- THive/Spark: NULL (NULL传播)
-- StarRocks: NULL (一致)
-- Presto: NULL (一致)

-- 使用COALESCE避免NULL
SELECT CONCAT('hello', COALESCE(name, ''));  -- 推荐写法
```

### NULL的比较

```sql
-- NULL相等比较
SELECT NULL = NULL;
-- 所有引擎: NULL (而非TRUE或FALSE)

-- 正确的NULL判断
SELECT col IS NULL;  -- 推荐写法
SELECT col IS NOT NULL;
```

## 最佳实践建议

### 1. 显式类型转换

**推荐**：始终使用`CAST`进行显式类型转换，避免依赖隐式转换

```sql
-- ❌ 不推荐：依赖隐式转换
SELECT '100' + 50;

-- ✅ 推荐：显式转换
SELECT CAST('100' AS INT) + 50;
```

### 2. 字符串格式规范

**推荐**：使用标准的日期时间格式

```sql
-- ✅ 推荐：标准格式
'2024-01-01'
'2024-01-01 12:30:45'

-- ❌ 避免：非标准格式
'20240101'
'2024/01/01'
```

### 3. 数值比较规范

**推荐**：同类型比较，必要时显式转换

```sql
-- ✅ 推荐
SELECT CAST(string_col AS INT) = int_col;

-- ❌ 避免
SELECT string_col = int_col;
```

### 4. 布尔表达式明确化

**推荐**：在WHERE子句中使用明确的布尔表达式

```sql
-- ✅ 推荐
WHERE cint <> 0
WHERE flag = TRUE

-- ❌ 避免（THive/Spark可以，但其他引擎可能不行）
WHERE cint
WHERE flag
```

### 5. NULL值处理

**推荐**：使用`COALESCE`或`NVL`处理NULL值

```sql
-- ✅ 推荐
SELECT COALESCE(nullable_col, default_value);
SELECT NVL(nullable_col, default_value);

-- ❌ 避免：直接运算
SELECT nullable_col + 100;
```

## 引擎差异总结

### THive/Spark 3.3（宽松模式）

**特点**：
- 支持广泛的隐式类型转换
- 字符串可自动转数值、日期
- 布尔可转整数（TRUE=1, FALSE=0）
- 日期格式支持多种形式

**优点**：
- 使用方便，减少显式转换代码
- 兼容性好，适合数据探索

**缺点**：
- 可能隐藏类型错误
- 性能可能受影响

### StarRocks/Presto（严格模式）

**特点**：
- 类型检查严格
- 大多数转换需要显式CAST
- 布尔不能转整数
- 日期格式要求标准

**优点**：
- 类型安全，减少隐藏错误
- 强制规范化代码

**缺点**：
- 需要更多显式转换代码
- 迁移THive/Spark SQL需要改写

## 特殊数值处理差异

### NaN（Not a Number）值处理

Spark和StarRocks对NaN值的处理存在显著差异：

```sql
-- 示例：除法运算产生NaN
SELECT abs((nvl(t.qty1,0)-nvl(t.qty2,0))/t.qty3) as target_1
FROM table t;

-- 产生NaN的情况：
-- 1. 0/0：当 qty3 = 0 且分子也为 0 时
-- 2. Infinity/Infinity：极端数值计算

-- Spark行为：
-- 将NaN值显示在结果中，所以可能会多出带NaN的数据行

-- StarRocks行为：
-- 不显示NaN值，这些行会被过滤掉

-- 数据差异示例：
-- 如果有2行数据产生NaN
-- Spark结果: 包含这2行，显示为NaN
-- StarRocks结果: 不包含这2行（少2行数据）
```

**解决方案**：

```sql
-- ✅ 推荐：显式过滤NaN值，确保引擎行为一致
SELECT abs((nvl(t.qty1,0)-nvl(t.qty2,0))/t.qty3) as target_1
FROM table t
WHERE t.qty3 != 0  -- 避免除以0

-- 或者使用CASE表达式
SELECT CASE 
    WHEN t.qty3 = 0 THEN NULL  -- 或其他默认值
    ELSE abs((nvl(t.qty1,0)-nvl(t.qty2,0))/t.qty3)
END as target_1
FROM table t;
```

**影响**：
- 数据一致性：可能导致不同引擎返回不同的行数
- 聚合计算：NaN值会影响SUM、AVG等聚合函数结果
- 排序行为：NaN值的排序位置在不同引擎中可能不同

## 窗口函数中的隐式转换

### 排序稳定性问题

窗口函数在处理相同排序值时，不同引擎的行为可能不一致：

```sql
-- 潜在问题示例
SELECT 
    device_id,
    in_vstart_cnt,
    ROW_NUMBER() OVER(PARTITION BY device_id ORDER BY in_vstart_cnt DESC) as rn
FROM table;

-- 问题：
-- 当同一个device_id有多行in_vstart_cnt值相同时（例如都是10）
-- ROW_NUMBER只能分出rn=1, rn=2, rn=3...
-- 但哪一行是rn=1在不同引擎、不同执行时可能不同

-- 原因：
-- 1. "分组排序没有主键唯一性"
-- 2. 当排序结果不唯一时，引擎按"底层扫描顺序"判定先后
-- 3. 物理扫描顺序容易变化（不同引擎、不同时间）

-- 后果：
-- WHERE rn=1 每次可能选中不同的行
-- 导致后续聚合结果不一致
```

**解决方案**：

```sql
-- ✅ 推荐：添加唯一标识字段作为次级排序
SELECT 
    device_id,
    in_vstart_cnt,
    ROW_NUMBER() OVER(
        PARTITION BY device_id 
        ORDER BY in_vstart_cnt DESC, guid ASC  -- 添加唯一标识guid
    ) as rn
FROM table;

-- 或者使用其他窗口函数
SELECT 
    device_id,
    in_vstart_cnt,
    RANK() OVER(PARTITION BY device_id ORDER BY in_vstart_cnt DESC) as rn
FROM table;
-- RANK会给相同值分配相同的排名，更符合业务语义
```

**最佳实践**：
1. **添加唯一键**：在ORDER BY中添加唯一标识字段（如guid、id等）
2. **选择合适的窗口函数**：
   - `ROW_NUMBER()`: 必须唯一，需要唯一排序键
   - `RANK()`: 相同值得相同排名，可能更符合业务需求
   - `DENSE_RANK()`: 相同值得相同排名，排名连续
3. **明确排序规则**：确保ORDER BY条件足够明确，避免歧义

## 跨引擎SQL兼容性建议

### 1. 类型转换规范

```sql
-- ❌ 避免：依赖不同引擎的隐式转换差异
SELECT col1 FROM table WHERE string_col = 123;

-- ✅ 推荐：明确类型转换
SELECT col1 FROM table WHERE CAST(string_col AS INT) = 123;
```

### 2. NULL值处理规范

```sql
-- ❌ 避免：在IN/NOT IN中使用可能为NULL的列
SELECT col1 FROM table WHERE col1 NOT IN (SELECT col2 FROM table2);

-- ✅ 推荐：明确过滤NULL
SELECT col1 FROM table 
WHERE col1 NOT IN (SELECT col2 FROM table2 WHERE col2 IS NOT NULL)
  AND col1 IS NOT NULL;
```

### 3. 数值计算规范

```sql
-- ❌ 避免：可能产生NaN或Infinity的计算
SELECT a / b FROM table;

-- ✅ 推荐：防御性编程
SELECT CASE WHEN b != 0 THEN a / b ELSE NULL END FROM table;
```

### 4. 窗口函数规范

```sql
-- ❌ 避免：不唯一的排序条件
ORDER BY score DESC

-- ✅ 推荐：添加唯一标识保证稳定性
ORDER BY score DESC, id ASC
```
