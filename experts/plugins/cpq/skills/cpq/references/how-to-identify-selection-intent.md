## 三种选品意图定义

| 取值 | 名称     | 定义                                             |
| ---- | -------- | ------------------------------------------------ |
| `a`  | 推荐常用 | 根据用户指定的产品，推荐报价场景中的热门规格     |
| `b`  | 框架选品 | 根据用户指定的产品，推荐该产品类目对应的全部规格 |
| `c`  | 精确查找 | 根据用户指定的条件精确选品（默认意图）           |

> 三种意图在 Phase 2.6 阶段只负责"在每行落一个合法选品意图"。Phase 3 入口按意图分流：`b`/`a` → 加载 [`stage/frame.md`](./stage/frame.md) 走框架推荐脚本；`c` → 走 [how-to-search-product.md](./how-to-search-product.md) 的 A→B→C→D 精确匹配。本阶段唯一目标是**确保每行都有合法的选品意图取值**。
>
> **`框架选品（b）` 的两种生效粒度**（见判定算法两层结构）：
>
> - **整单框架（第一层 · 整单生效）**：当整单行数 > 5 且存在规格不明确行时，先问用户是否"整单框架"。一旦选是，**全单所有行**（含已自动判成 `c` 的有规格行）统一设为 `b`，意图当场全部确定。
> - **单行框架（第二层 · 仅本行生效）**：用户在逐行确认时，可单独把某一行选成 `b`，只影响该行，不波及其它行。
>
> 两种粒度落盘后都是同一个意图码 `b`，区别只在"作用范围"，Phase 3 分流一视同仁。

## 判定算法

### Step A · 自动判定每行 `has_spec`

对 Phase 2.5 产物每行 `R`，判定 `Phase 3 检索关键词` 中是否包含**至少一个**详细规格信号：

**规格信号清单（命中任一即视为 `has_spec=True`）**：

| 信号类别 | 示例                                                                       |
| -------- | -------------------------------------------------------------------------- |
| 型号代号 | `S5` / `M5` / `MA9` / `D3` / `IT5` / `BMS6` / 其它型号后缀                 |
| 版本档位 | `标准版` / `高可用版` / `金融版` / `企业版` / `基础版` / `Pro` / `Premium` |
| 规格参数 | `2核4G` / `8C16G` / `100Mbps` / `1000QPS` / `4核8G` 类似组合               |
| 容量值   | `500GB` / `1TB` / `100GB` / `10TB` / `PB` 级带数值的容量                   |
| 数量指标 | `10台实例` / `5节点` / `20个集群` / 行内已含数量描述                       |
| 子类型   | `标准存储` / `低频存储` / `归档存储` / `BGP` / `静态单线`                  |

**不算规格信号**（即使存在也视为 `has_spec=False`）：

- 地域 / 可用区（如 `广州一区` / `上海` / `Singapore` / `Tokyo`）
- 售卖模式（如 `包年包月` / `按量计费`——售卖模式有专门的列，不影响 has_spec 判定）
- 纯产品名（如 `云服务器` / `云数据库 MySQL`）

判定结果：

- `has_spec(R) = True` → `R.intent = "c"`（**强制 · 不询问**）
- `has_spec(R) = False` → 进入 `ambiguous_rows`，待 Step B/C 处理

> **判定分两层**：Step B 是**第一层 · 整单框架确认**（整单生效，命中触发条件时优先问）；Step C 是**第二层 · 逐行确认**（单行生效，Step B 不触发或用户拒绝整单框架时执行）。

### Step B · 第一层：整单框架确认（条件性 · 整单生效）

**触发条件（两个都满足）**：

- `total > 5`（**整单总行数**大于 5——阈值卡的是整张清单的行数，不是规格不明确行的行数）
- `len(ambiguous_rows) > 0`（至少有一行 has_spec=False，否则全单已是 `c`，无需打扰用户）

**询问用户**：

```text
本次清单共 {total} 行，其中 {len(ambiguous_rows)} 行规格不明确。
是否对整张清单走「整单框架」？
  整单框架 —— 整张清单所有行（含已识别出详细规格的行）统一按【框架选品】处理：
              按产品类目推荐该类目的全部规格，不再逐行精确匹配。
请回复：
  1. 否，逐行确认（我再为每一行单独决定精确 / 推荐 / 框架）
  2. 是，整单框架
```

**用户选择处理**：

- 用户选 **"是，整单框架"（2）** → **全单所有行**（含 `has_spec=True` 已自动判成 `c` 的行）一律设为 `R.intent = "b"`，选品意图**当场完全确定**，**跳过 Step C**
- 用户选 **"否，逐行确认"（1）** → 进入 Step C
- 用户无明确回复 / 回复不可解析（如"看你的""默认就行"）→ 重新询问，不擅自默认

> ⚠️ 与旧行为的区别：整单框架**会覆盖**已识别出详细规格的行（把它们从 `c` 改成 `b`），这是用户主动选择"整单按框架报价"的预期结果，不是 bug。

### Step C · 第二层：逐行确认（条件性 · 单行生效）

**触发条件**（满足任一）：

- `total ≤ 5` 且 `len(ambiguous_rows) > 0`（整单行数少，没有第一层，直接逐行问）
- `total > 5` 且 `len(ambiguous_rows) > 0` 且用户在 Step B 选择"否，逐行确认"

**询问用户**：

向用户一次性列出所有 `ambiguous_rows`，每行独立选择意图。**必须随询问解释三种模式的含义**（用户看 `a/b/c` 裸字母无法判断）：

```text
以下 {N} 行规格不明确，请为每行选择选品意图（仅影响该行）：

  c · 精确查找 —— 按你给的条件精确定位具体 SPU（默认；适合已经想好买哪个规格）
  a · 推荐常用 —— 在该产品类目里推荐报价场景的热门规格（适合"要这个产品，给我常用的就行"）
  b · 框架选品 —— 按该产品类目推荐全部规格（适合"这一类先全摆上做框架"；仅本行生效，不影响其它行）

| # | 规范化产品名 | Phase 3 检索关键词 | 售卖模式 | 候选意图              |
|---|-------------|--------------------|---------|----------------------|
| 1 | 云服务器     | 云服务器            | -       | c / a / b            |
| 2 | 云数据库     | 云数据库 MySQL      | -       | c / a / b            |
| 3 | 容器服务     | 容器服务            | -       | c / a / b            |

请按格式回复：1=c, 2=a, 3=b（或 "全部 c" / "全部 a" / "全部 b"）
```

**用户回复解析规则**：

- 每行回复 `<行号>=<意图码>` 单字符，意图码必须为 `a` / `b` / `c`
- 支持快捷指令：`全部 a` / `全部 b` / `全部 c` —— 把所有 ambiguous_rows 设为对应意图（注意：这只作用于 ambiguous_rows，不覆盖已自动判成 `c` 的有规格行，与整单框架不同）
- 缺行或意图码不合法 → 重新询问缺失部分，不擅自默认
- 不强制要求同表所有行同意图——允许"1=c, 2=b, 3=a"这样的混合结果

### 算法伪代码

```python
def identify_intent(phase2_5_rows):
  # Step A · 自动判定有规格的行 → c
  for R in phase2_5_rows:
    R.has_spec = check_spec_signals(R['Phase 3 检索关键词'])
    R.intent = 'c' if R.has_spec else None  # None = 规格不明确，待确认

  total = len(phase2_5_rows)
  ambiguous = [R for R in phase2_5_rows if R.intent is None]

  if len(ambiguous) == 0:
    return phase2_5_rows  # 全单已是 c，无需询问

  # Step B · 第一层：整单框架确认（触发条件：整单行数 > 5 且有不确定行）
  # 注：上面 ambiguous==0 已提前 return，这里的 len(ambiguous) > 0 是自解释的冗余条件
  if total > 5 and len(ambiguous) > 0:
    choice = ask_user_global(total=total, ambiguous_count=len(ambiguous))
    if choice == 'frame_all':
      for R in phase2_5_rows:        # ← 全单所有行，含已判 c 的有规格行
        R.intent = 'b'
      return phase2_5_rows           # 意图完全确定，跳过 Step C
    # choice == 'per_row' → 落到 Step C

  # Step C · 第二层：逐行确认（仅对 ambiguous_rows，单行生效）
  user_choices = ask_user_per_row(ambiguous)  # 询问时附 c/a/b 中文解释
  for R in ambiguous:
    R.intent = user_choices[R.row_id]  # 取值校验为 a/b/c

  return phase2_5_rows
```

  - `精确查找（c）`
  - `框架选品（b）`
  - `推荐常用（a）`
- 括号内的字母码 `a` / `b` / `c` 是下游 Phase 3 分流、Phase 4 校验的**机器锚点**，必须保留；中文名只为人类可读，两者缺一不可

  - 门控标记里仍用字母码计数（`intent_a` / `intent_b` / `intent_c`），不带中文
  - `<N>` = 总行数，必须等于 Phase 2.5 产物的总行数
  - `<X>` / `<Y>` / `<Z>` = 三种意图各自的计数，三者之和必须等于 `<N>`

## 门禁规则

| 规则                                                                                            | 违规后果               |
| ----------------------------------------------------------------------------------------------- | ---------------------- |

| Step B / Step C 的用户回复未明确（如"看你的""默认就行"）就擅自给行填默认值（强制为 c 或 b 等）  | 流程违规，必须重新询问 |
