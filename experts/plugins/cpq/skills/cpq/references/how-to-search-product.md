# 产品搜索与匹配指南（C 段 · Phase 3）

> **定位**：本文档是 **C 选品段** 的 **Phase 3** 子步骤（编排见 [how-to-select-product.md](./how-to-select-product.md)），读 Phase 2.6 产物的检索关键词 / 售卖模式 / 选品意图三列，产出搜索结果记录供 Phase 4 映射表确认。无 SPUID 的方式 D 四层查找见 [how-to-query-four-layer.md](./how-to-query-four-layer.md)。Phase 4 门控 = `check-phase4-confirm.mjs`。

Phase 3 对每条检索关键词执行匹配。**入口必须先按选品意图分流**，再执行对应的匹配策略。

> CLI 命令语法、参数、输出格式详见 [cpq-cli.md](./cpq-cli.md) 的"产品搜索"章节。本文档只列出**选品流程特有的搜索策略和结果过滤规则**。

## 按选品意图分流（⚠️ Phase 3 入口强制调度）

Phase 3 的输入是 Phase 2.6 产物 `<CPQ_SESSION_DIR>/phase2_6.md`（`<CPQ_SESSION_DIR>` 解析见[cpq-session-dir.md](./cpq-session-dir.md)），每行 `选品意图` 列写法为 `中文名（字母码）`（如 `精确查找（c）` / `框架选品（b）` / `推荐常用（a）`）。**分流以括号内的字母码 `a` / `b` / `c` 为准**（中文名仅为可读性）。Phase 3 **必须按意图分流执行**，不同意图使用不同的匹配策略：

> **透传约束**：除 `选品意图` 用于分流外，Phase 2.6 产物的 `站点` / `地域` / `售卖模式` 三列**必须原样携带到每条搜索结果记录**（站点必有值，地域可能为 `-`）。其中 `售卖模式` 不为 `-` 时用于过滤 `payMode`；`站点` / `地域` 不参与搜索过滤，仅作为透传列供 Phase 4 映射表继承（Phase 4 只读 Phase 3 产物，不会回读 Phase 2.6，因此这两列若在 Phase 3 丢失，C 的映射表将无法继承）。

| 选品意图        | 执行策略                                  | 加载文档                                                                       |
| --------------- | ----------------------------------------- | ------------------------------------------------------------------------------ |
| `c`（精确查找） | 本文档下方定义的 A→B→C→D 四种匹配方式     | 无需额外文档（本文档即是）                                                     |
| `b`（框架选品） | 委托框架推荐脚本，按类目推荐高频 SPU      | **必须加载** [`stage/frame.md`](./stage/frame.md)                              |
| `a`（推荐常用） | 委托框架推荐脚本，每类目取 top N 热门 SPU | **必须加载** [`stage/frame.md`](./stage/frame.md)（使用 `--top` 参数限制数量） |

**分流规则**：

1. 从 Phase 2.6 产物中按 `选品意图` 列括号内的字母码（`a` / `b` / `c`）将所有行分为三组
2. **intent=b 或 intent=a 的行**：提取这些行的 `规范化产品名` / `缩写` 列，作为框架推荐脚本的类目输入（`--category` 或 `--lv1`）。加载 `stage/frame.md` 按其流程执行（推荐 → 互斥检测 → 确认）
3. **intent=c 的行**：使用本文档下方定义的 A→B→C→D 流程逐条精确匹配
4. 两组结果最终在 Phase 4 映射表中统一汇总展示给用户确认

> ❌ **禁止**：对 intent=b/a 的行使用 A→B→C→D 通用搜索流程——框架/推荐场景下通用搜索会召回大量无关 SPU，且无法利用历史频次数据做筛选。
> ❌ **禁止**：跳过分流直接对所有行执行 batch-search——必须先检查 `选品意图` 列。
> ✅ **允许**：当所有行都是 intent=c 时，直接进入下方 A→B→C→D 流程（无需加载 frame.md）。

## 搜索结果后续操作

| 结果类型                  | 后续操作                                                                                                                                                                                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 目录节点（spuId=-）       | 使用目录名作为更精确的关键词重新搜索，获取该目录下的叶子产品节点，按规则 2-3 处理后**全部记录为待添加**。展开数量多是正常的（一个目录下可能有数十甚至上百个 SPU），不应因数量多就截断或标记"过多"——通过搜索结果中的 `mutexSpus` 字段检测互斥冲突即可，留到 Phase 4 统一确认 |
| 产品节点 100% 匹配        | 记录 SPU ID，标记"待添加"；若 `mutexSpus` 非空，在 Phase 4 标注互斥关系让用户决策                                                                                                                                                                                           |
| 产品节点部分匹配（<100%） | 检查 `unmatchedTokens` 是否关键，决定是否采纳或换关键词重搜                                                                                                                                                                                                                 |
| 空结果                    | 走方式 B/C/D 兜底                                                                                                                                                                                                                                                           |
| `✗(停止销售)` 等          | 排除该产品或联系产委申请白名单                                                                                                                                                                                                                                              |

## 误报防护规则（减少错误匹配）

搜索返回结果后，必须执行以下验证步骤，过滤掉不相关的产品：

### 规则 1：产品大类一致性验证

搜索结果的产品名前缀必须与用户清单中的产品大类一致。

| 用户输入     | 应保留                         | 应排除                                                |
| ------------ | ------------------------------ | ----------------------------------------------------- |
| CVM 标准型S5 | 云服务器CVM-标准型S5（\*）     | 弹性MapReduce-标准型S5、边缘可用区TEZ-标准型S5        |
| Redis 标准版 | 云数据库Redis-标准架构（\*）   | 大数据Redis（如有）                                   |
| 负载均衡     | 负载均衡-实例、公网负载均衡-\* | DNS增值服务-负载均衡、金融专区-负载均衡（非主流场景） |

**执行方式**：搜索结果中 `path` 路径的第 3 层（产品线）应与用户意图的产品线一致。如果不一致，从结果中剔除。

### 规则 2：售卖模式 / 计费模式匹配

Phase 3 必须读取 Phase 2.5 产物中的 `售卖模式` 列。该列来自 Phase 1 对用户原始描述的识别，优先级高于搜索结果默认策略。当 `售卖模式` 不为 `-` 时，优先选择 `payMode` 匹配的结果：

| 售卖模式描述     | 对应 payMode    | 说明                    |
| ---------------- | --------------- | ----------------------- |
| 包年包月、预付费 | `prepay`        | 用户明确指定预付费      |
| 按量计费、后付费 | `postpay`       | 用户明确指定按量/后付费 |
| 包销             | `underwritepay` | 大客户包销合同          |
| 竞价、竞价实例   | `spotpay`       | 明确提到竞价            |
| 预留、容量预留   | `reservedpay`   | 明确提到预留/容量预留   |
| 节省计划         | `savingsplan`   | 明确提到 SP             |

**默认行为**：`售卖模式 = -` 或用户未指定计费模式时，将同一主线产品下所有 100% 匹配且可售卖的付费模式变体**全部添加**到报价单（如预付费、后付费、包销、竞价等），不要只选一个。只有当 `售卖模式` 明确指定了某种计费模式时，才只选对应的变体。

### 规则 3：多结果去歧义

当同一关键词返回多个结果时，先按规则 1 做产品大类一致性过滤，再按以下规则处理：

1. **完整子串匹配** > 散布 token 匹配（如 `CVM标准型S5` 完整出现在名称中）
2. **主线产品** > 衍生产品（如 `云服务器CVM-*` > `边缘可用区TEZ-*` > `专属集群-*`）
3. **同一产品名的不同付费模式变体全部保留**：经过规则 1、2 过滤后，将产品名称去掉付费模式后缀（如 `（预付费）`、`（后付费）`、`（包销）`、`（闲时竞价）`、`（忙时竞价）`、`（容量预留）`、`（节省计划）`）后，基础名**完全一致**的视为同一产品的付费变体，**全部添加**到报价单。基础名不同的视为不同 SKU/子产品，不自动全加。
   - ✅ 示例（全加）：`云服务器CVM-标准型S5（预付费）` 与 `云服务器CVM-标准型S5（后付费）` → 基础名均为 `云服务器CVM-标准型S5`，全部添加
   - ❌ 反例（不全加）：`SSD云硬盘` 与 `增强型SSD云硬盘` → 基础名不同，属于不同子产品
4. **路径层级浅** > 路径层级深（仅用于不同产品之间的去歧义，不用于同产品的计费模式变体）

### 规则 4：已知易混淆产品对（黑名单）

以下关键词容易跨产品匹配，**必须**加产品大类前缀限定：

| 易混淆关键词 | 可能误匹配的产品         | 正确搜索方式                    |
| ------------ | ------------------------ | ------------------------------- |
| 标准型S\*    | MapReduce、TEZ、专属集群 | `CVM 标准型S5`                  |
| 内存型M\*    | MapReduce                | `CVM 内存型M5`                  |
| 标准版       | 多个产品都有"标准版"     | `Redis 标准版`、`CKafka 标准版` |
| 企业版       | 多个产品都有"企业版"     | `TCR 企业版`、`TSF 企业版`      |
| 实例         | 几乎所有产品都有"实例"   | 不能单独用作关键词              |
| 流量         | CDN、CLB、COS 等多产品   | `CLB 流量`、`CDN 流量`          |

### 规则 5：结果数量阈值

> **重要区分**：此规则仅适用于**逐条搜索**场景（即用具体关键词搜出多个不同产品）。当搜索命中的是**目录节点**，需使用目录名重新搜索获取叶子产品时，展开数量多是正常的（同一目录下不同付费变体、不同规格都会独占一行），应全部记录为待添加，不受此阈值限制——通过搜索结果中的 `mutexSpus` 字段检查互斥冲突即可。

| 命中数量 | 处理策略                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 1        | 直接采纳（唯一匹配）                                                                                             |
| 2~5      | 按规则 1-3 过滤；同一产品名（去掉付费后缀后基础名一致）的不同付费变体全部添加；不同产品则列出候选让用户选        |
| 6~10     | 按规则 1-3 过滤后，同产品名不同付费变体全部添加；不同产品间仍需追加大类前缀或计费模式限定后重搜                  |
| 11~50    | 先按规则 1 过滤产品大类，再按规则 3 收集同产品名的所有付费变体；仍过多则重构搜索关键词                           |
| >50      | 先按规则 1 过滤产品大类；过滤后仍 >50 则向用户展示前 10 条结果和总命中数，让用户确认是否需要缩小范围或改换关键词 |

## 方式 A — batch-search 批量搜索（首选，强制）

使用 `product batch-search` 批量搜索，**无需 --cpqcode**，离线数据源覆盖 15000+ 产品。

> ⚠️ **推荐用法**：`batch-search` 结果通过 `--stdout` 输出到 stdout，再用管道或 `read_file` 读取。旧版 `-o <filepath>` 写法已弃用。

```bash
cpq product batch-search -q "CVM 标准型S5" "Redis 标准版" "MySQL 高可用版" \
  --stdout
# 或 JSON 数组输入
cpq product batch-search --json '[{"keyword":"CVM 标准型S5"}]' \
  --stdout
```

**关键词完整性约束**：传给 `batch-search` 的每条关键词，必须与 Phase 1 产物（或 Phase 2.5 规范化产物）中的搜索关键词**完全一致**。禁止在此阶段自行简化、截断或改写关键词。违反后果：宽泛关键词会召回大量无关产品，导致清单膨胀。

**关键词构造**（按优先级尝试，命中即停）：

1. **缩写 + 型号**（最优）：`CVM 标准型S5`、`Redis 标准版`、`MySQL 高可用版`
2. **缩写单独搜获取目录**：`CVM`、`WAF`、`DDoS`（先看分类再精确搜索）
3. **中文全名**：`云服务器`、`负载均衡`、`对象存储`

**执行方式**：

- 将 Phase 2.5 产物中所有 `Phase 3 检索关键词` 一次性传给 `batch-search`，一次调用完成全部搜索
- 同时保留每个关键词对应的 `售卖模式`，搜索返回后按规则 2 过滤 `payMode`
- 结果文件中 `hits` 为命中项（含 SPU ID），`misses` 为未命中项
- 未命中的关键词，先换变体关键词用 `batch-search` 或 `quick-search` 重试一次，仍然为空再转方式 B/C

**结果处理**：

- 返回 `[DIR]` 目录 → 使用目录名作为关键词重新搜索获取目录下的叶子产品节点，按规则 2-3 处理后**全部记录为待添加**。展开数量多是正常的，不应因数量多就截断；通过搜索结果的 `mutexSpus` 字段检测互斥冲突，有互斥的产品在 Phase 4 标注让用户决策
- 返回产品列表 → 按规则 1-3 过滤后，**将同一基础名的所有有效付费变体全部记录**，每个 SPU ID 独立一条。❌ **禁止只取 top 1 或截断变体**——"为效率截断"会导致映射表不完整，Phase 4 用户看到的产品数少于实际可选数
- 返回空 → 换变体关键词重试一次，仍空则尝试方式 B 或 C

## 方式 B — 通过计费四层精确搜索

当用户给出官网购买页的具体规格（如机型系列"标准型SA9"、实例规格"SA9.MEDIUM2"），而方式 A 结果过多或无法精确定位时，先通过计费四层映射数据查到四层编码，再用四层编码在报价器中精确搜索。

1. 用 `bash` 在 `references/billing-catalog/` 中 grep，从购买页名称得到四层编码：

```bash
grep "标准型SA9" references/billing-catalog/cvm.md || true
```

> `references/billing-catalog/cvm.md` 每行格式：`购买页（计费模式/机型系列/实例规格/核数/内存）=> 四层（p/sp/v/sv）`
> 所有 grep 必须以 `|| true` 结尾。四层结果只能来自 grep 命中，禁止推测编造。

2. 从 grep 结果中提取四层编码（如 `sp_cvm_sa9`），用 `product search` 在报价器中查找对应的产品 ID：

```command
product search -q "sp_cvm_sa9"
```

## 方式 C — 按分类名搜索（兜底）

以上方式均无法定位时，用分类名作为关键词搜索，搜索结果会返回完整的父级路径帮助定位：

```command
product quick-search -q "分类名"
```

搜索结果包含 `路径` 列（如 `计算 > 计算 > 云服务器 > 云服务器CVM（包销）`），可根据路径确认产品归属。搜索结果会返回完整父级路径，无需逐层浏览。

## 方式 D — 委托 tencent-cloud-pricing 获取四层编码（⚠️ 不可跳过的兜底）

> **硬约束**：方式 A/B/C 均失败的条目，**必须**进入方式 D 执行四层查询，禁止直接标记"未匹配"后跳过。只有方式 D 也明确失败（`tcloud-price search` 无此产品 / `--with-four-level` 返回空 groups / `four-level query` 无匹配）后，才可最终标记"未匹配"。

当方式 A/B/C 均无法匹配（搜索无结果、关键词变体穷尽、目录树中找不到对应产品）时，委托同 plugin 下的 **tencent-cloud-pricing** 技能生成精准的四层计费编码。

> **⚠️ 调用方式（关键）**：`tcloud-price` 是内置本地二进制，**不是 npm 包**，不能通过 `npx` 调用。已在 PATH 中，直接执行即可。
>
> ```bash
> tcloud-price <子命令>
> ```
>
> ❌ **禁止** `npx tcloud-price` / `npx @tencent/tcloud-price-cli` — 不存在这些 npm 包，会导致 E404 错误浪费时间。

**触发条件**：方式 A（batch-search）+ 方式 B（billing-catalog grep）+ 方式 C（分类搜索）全部失败后，对"未匹配"条目执行。多条未命中产品可**并行**调用 `tcloud-price`。

**执行步骤**：

1. 确认站点（国内站 `--site cn` / 国际站 `--site intl`）
2. 使用 `tcloud-price search "<产品名>"` 确定产品代码；若返回空则最终标记"未匹配"并停止
3. 使用 `tcloud-price help --site cn --product <code>` 了解该产品需要哪些规格参数
4. 用**最小必填参数**执行报价并同时获取四层编码（推荐 Quick path 一步到位）：
   ```bash
   tcloud-price quote --site cn --product <code> <最小必填参数> --with-four-level
   ```
5. 从 JSON 结果中提取 `fourLevel.groups[]`：
   - 若 `fourLevel.skipped == true` 或 `groups` 为空 → 退回 Manual path：
     ```bash
     tcloud-price four-level query --site cn --product <code> --price-cents <totalPrice×100>
     ```
   - 若 Manual path 也无匹配 → 最终标记"未匹配"

**四层编码产出格式**（映射表中展示给用户确认用）：

```
购买页（{计费模式}/{规格系列}/{实例规格}/{核数}/{内存}）=> 四层（{productCode}/{subProductCode}/{valueItemCode}/{valueSubItemCode}）
```

示例：

```
购买页（包年包月/内存型MA9/MA9.MEDIUM16/2核/16GiB）=> 四层（p_cvm/sp_cvm_ma9/v_cvm_mem/sv_cvm_mem_ma9）
```

- 等号左边的"购买页"部分，从 `tcloud-price help` 的参数说明 + 实际传入值拼接
- 等号右边的"四层"部分，从 `fourLevel.groups[].productCode` / `subProductCode` / `svList[].ValueItemCode` / `ValueSubItemCode` 提取
- 如果 `svList` 有多条（如 CVM 同时含 cpu + mem + disk），选与用户清单中产品最相关的一条作为主计费项展示；其余在映射表的"备注"列列出

**传给 `row add` 的四层编码值**：取 `subProductCode` 字段值（如 `sp_cvm_ma9`），传入 `row add --four-layer-codes "sp_cvm_ma9"`。

> `--four-layer-codes` 参数规则：多项用英文逗号分隔；每项内部可用斜杠拼接（如 `p_cvm/sp_cvm_ma9`），CLI 内部取最后一段作为查询 code。

**结果处理**：

- 成功获取四层编码（`groups` 非空） → 记录四层映射，状态标记为"待添加（四层）"
- `tcloud-price search` 无此产品 → 最终标记"未匹配（pricing 无此产品）"
- `--with-four-level` 返回 `skipped: true` 且 `four-level query` 也无匹配 → 最终标记"未匹配（四层不可用）"

> ⚠️ 方式 D 的产物是四层编码而非 SPU ID，Phase 5 添加时使用 `row add --four-layer-codes` 而非 `--spu-ids`。
> ⚠️ 方式 D 失败后**不需要再回头重试方式 A/B/C**——直接标记"未匹配"进入 Phase 4 向用户确认即可。

---

## 匹配判定

到达叶子节点后判断：

- **唯一匹配**（方式 A/B/C） → 记录叶子节点名和 SPU ID，状态"待添加"
- **同产品多付费变体**（方式 A/B/C） → 经规则 1-3 过滤后，基础名一致的所有付费变体（预付费/后付费/包销/竞价等）**全部记录，每个 SPU ID 独占一条**，状态"待添加"。❌ **禁止为了效率或批量处理而只取 top 1 / 截断变体 / 合并多个 SPU 到一行**
- **四层匹配**（方式 D） → 记录四层映射（购买页参数 => 四层编码），状态"待添加（四层）"
- **多个候选** → 记录全部叶子节点候选，标记"待用户选择"，**不在 Phase 3 中途询问用户，留到 Phase 4 统一决策**
- **方式 D 也失败** → 最终标记"未匹配"（需说明失败原因：pricing 无此产品 / 四层不可用）

> 只有叶子节点（isDir=false）可添加，目录节点不可添加。
> 多个清单条目可能落在同一分类路径下，浏览一次该路径即可覆盖，无需重复检索。
> ❌ 禁止在方式 A/B/C 失败后直接跳过方式 D 就标记"未匹配"。

## Phase 3 产物

每条产品的搜索结果记录，包含：原始产品名 → 规范化/对标后的搜索关键词 → `站点` → `地域` → `售卖模式` → `选品意图` → 返回的 SPU ID 和节点名（或四层 code）→ 匹配状态。
其中 `站点` / `地域` / `售卖模式` / `选品意图` 四列**必须从 Phase 2.6 产物原样透传到每条搜索结果记录**，不得在 Phase 3 丢弃或改写——它们是 Phase 4 映射表的数据源，Phase 4 只读 Phase 3 产物即可拿到，无需回读上游 Phase。同一关键词拆出的多个 SPU 变体行共享同一站点 / 地域 / 售卖模式 / 选品意图。
Phase 3 完成的标志是：进入 Phase 3 的每一条检索关键词都有对应的搜索结果（无论匹配成功与否），且能追溯回 Phase 1 原始清单行。

> ❌ **硬约束**：Phase 3 阶段只执行 `product search` / `product quick-search` / `product batch-search` / `tcloud-price` 查询命令，禁止执行 `row add`。
> ❌ **硬约束**：在 Phase 4 获得用户确认前，禁止执行任何写入操作（`row add` / `row import` / `row update`）。

## Phase 3 门控检查清单

AI 自检，**全部通过**后才可进入 Phase 4：

- [ ] 方式 A 中是否已用 `batch-search` 批量搜索所有关键词？搜索关键词是否与 Phase 1/2.5 产物完全一致（未被简化）？
- [ ] 是否已为每个关键词保留 Phase 2.5 的 `售卖模式`，并在不为 `-` 时按规则 2 过滤 `payMode`？
- [ ] **（关键）是否已把 Phase 2.6 的 `站点` / `地域` 列原样透传到每条搜索结果记录？缺失会导致 Phase 4 映射表无法继承（只读 Phase 3 产物，不回读 Phase 2.6）**
- [ ] 100% 匹配的结果是否检查了**产品大类一致性**（`path` 中产品线与用户清单一致）？不一致的结果必须剔除。例如搜"CAS"时，命中"共享带宽包-anycast"（path 含网络）应排除
- [ ] 部分匹配的结果是否检查了 `unmatchedTokens`，确认未命中词不影响产品识别？
- [ ] 同一关键词命中 >10 条结果时，是否已用 `payMode`（计费模式）和 `path`（产品线）过滤后只保留相关结果？
- [ ] 是否检查了 `eol` 可售卖状态，排除已退市产品？
- [ ] 方式 A 未命中的产品是否至少尝试了一个变体关键词后才判定失败？
- [ ] **（关键）方式 A/B/C 均未命中的每条产品，是否都已执行方式 D（`tcloud-price`）？存在任何"方式 A/B/C 未命中但未走方式 D"的条目 = Phase 3 未完成，禁止进入 Phase 4**
- [ ] **（关键）每条命中的关键词，是否保留了所有有效的 SPU 付费变体（预付费/后付费/包销/竞价等）？禁止为了效率只取 top 1 或截断变体——截断会导致映射表不完整**
- [ ] 方式 D 的 `tcloud-price` 命令是否直接在 PATH 中调用（非 npx / npm）？
- [ ] 方式 D 中多条未命中产品是否并行调用了 `tcloud-price`？
