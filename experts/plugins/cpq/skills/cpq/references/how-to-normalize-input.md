# 输入归一化（Phase 1 阶段 A.0 子规则）

> **定位**：[how-to-parse-product-list.md](./how-to-parse-product-list.md) 阶段 A.0 的执行细则。仅在输入是**非表格类**（自由文本 / 邮件 / OCR 烂格式 / 多附件混合）时触发；表格类直接跳过 A.0 进 A.1。
>
> **设计目标**：把任意输入形态归一化成一份"虚拟表格"，让下游 A.1 / A.2 / B / C / D 都能用同一套算法处理。

---

## 触发判断（A.0 入口）

| 输入形态 | 处置 | step_input_normalized |
|---------|------|----------------------|
| Markdown 表格 | 跳过 A.0 | `n/a` |
| Excel / PDF 抽取的表格 | 跳过 A.0（合并展平推迟到 B.1） | `n/a` |
| 自由文本 / 邮件正文 | **触发 A.0**：执行虚拟列化 | `yes` |
| OCR 烂格式 / 截图 | **触发 A.0**：虚拟列化 + 标记低置信 cell | `yes` |
| 多附件混合（邮件 + Excel/Word/PDF 附件） | **触发 A.0**：附件优先解析 + 正文做上下文补充 | `yes` |
| 全部解析失败 | 终止流程，提示用户检查输入 | - |

---

## 自由文本归一化（最常见场景）

### Step 1 · 识别"产品提及"（每个独立产品 → 一行虚拟表格行）

扫描自由文本，找出独立的"产品提及"。判据：

- 含一个或多个产品名 token（如"CVM"、"云数据库"、"对象存储"）
- 用句号 / 分号 / "另外" / "还要" / "和" 等分隔符断开

**示例输入**：

```
帮我做选品：CVM 标准型 S5 4核8G，在广州、上海、北京、深圳、成都都要 10 台，
对象存储 COS 标准存储 1TB 每个地域都要一份。
```

**识别出 2 个产品提及**：

1. `CVM 标准型 S5 4核8G` + `广州/上海/北京/深圳/成都` + `10 台`
2. `对象存储 COS 标准存储 1TB` + `每个地域都要一份`

### Step 2 · 提取语义片段

对每个产品提及，分类各 token / 短语：

| 语义类 | 提取规则 | 示例 |
|--------|---------|------|
| `IDENTIFIER` | 名词短语，匹配产品名 | `CVM`、`对象存储 COS` |
| `SPEC` | 规格描述，匹配 `explicit-spec.{site}.md` 词典 | `标准型 S5`、`4核8G`、`标准存储 1TB` |
| `CONSTRAINT` | 形容词 / 性能描述 / 合规词 | `Ice Lake`、`IOPS≥1800` |
| `LOCATION` | 地域名（cn 30 个 / intl 18 个） | `广州`、`新加坡` |
| `QUANTITY` | 数字 + 量词（台 / 节点 / 个） | `10 台`、`5 节点` |
| `BILLING` | 售卖模式描述 | `包年包月`、`按量计费`、`三年承诺` |
| `META` | 备注 / 价格 / 折扣 / 业务标识 | `战略客户`、`框架协议` |

### Step 3 · 落到虚拟表格

```
| 产品名         | 规格               | 地域                          | 数量 | 售卖模式 |
|---------------|--------------------|-------------------------------|------|---------|
| CVM           | 标准型 S5 4核8G    | 广州、上海、北京、深圳、成都   | 10 台/地域 | (空) |
| 对象存储 COS   | 标准存储 1TB       | 广州、上海、北京、深圳、成都   | 1 份/地域 | (空) |
```

注意：

- "每个地域都要" → 数量列填 "1 份/地域"，下游 B.4 笛卡尔积时按地域复制
- 售卖模式没明确 → 留空，进 D 阶段追问

### Step 4 · 交还 A.1

虚拟表格交给 A.1 列级语义分类。后续 A.1 / A.2 / B / C / D 与表格类输入完全相同。

## 邮件正文 + 附件混合

### 优先级

```
附件优先级 > 正文上下文
```

理由：附件通常是 SA 准备的结构化清单（Excel/Word），正文是补充说明。

### Step 1 · 解析附件

按 [SKILL.md §附件处理能力](../SKILL.md#附件处理能力) 加载对应 skill：

- Excel → `xlsx-manipulation`
- Word → `docx-manipulation`
- PDF → `pdf-extraction`

附件解析后得到的表格作为**主清单**。

### Step 2 · 正文做上下文补充

正文里寻找以下信息，补充到主清单（**不覆盖**附件已有字段）：

- 售卖模式描述（"我们想包年包月 3 年"）
- 地域信息（"在新加坡部署"）
- 优惠目标（"希望 65 折"）
- 客户信息（"这是金融行业客户"）

如果附件已经有售卖模式列，正文的描述**忽略**（避免冲突）。

### Step 3 · 虚拟列化

附件主清单 + 正文补充字段 → 虚拟表格。

### 示例

**邮件正文**：

```
你好，附件是某金融客户的资源规划，需要在新加坡部署，预算 200 万。
他们倾向 RI 3 年。
```

**附件 Excel**（5 行 CVM + 5 行 CBS）：

| 产品 | 规格 | 数量 | 售卖模式 |
|---|---|---|---|
| CVM | 4c8g S5 | 5 | （空）|
| CVM | 8c16g S5 | 3 | （空）|
| ... | ... | ... | ... |

**虚拟列化结果**：

| 产品 | 规格 | 数量 | 售卖模式 | 地域 | 客户类型 |
|---|---|---|---|---|---|
| CVM | 4c8g S5 | 5 | 待 D 追问（候选含 RI 3 年） | 新加坡 | 金融行业 |
| ... | ... | ... | ... | ... | ... |

注意：

- 售卖模式不直接填 "RI 3 年"，仍走 A 段追问，但选项里把 "RI 3 年" 列为**首选高亮**（基于正文意图）
- 金融行业作为 META 进 C 段一次性告知（如不影响 SKU 选择）或 A 段追问（如命中 COMPLIANCE 词典）

## OCR 烂格式 / 截图

### Step 1 · 标记低置信 cell

OCR 识别结果通常带置信度，对置信度 < 0.85 的 cell 标记 `low_confidence=true`。

如果 OCR 工具不返回置信度，AI 用以下启发式判断：

- 含罕见字符（如 `S$5`、`l00GB`）
- 全是字母数字混合（如 `S0` 可能是 `SO` 或 `S5` 或 `S0`）
- 跨行断字（如行尾 `数据` + 行首 `盘`）

### Step 2 · 虚拟列化（保留低置信标记）

```
| 产品 | 规格           | 数量 | low_confidence_cells |
|------|---------------|------|---------------------|
| CVM  | 标准型 SS5 (?)  | 10   | yes (规格列)         |
```

### Step 3 · 进 A 段追问

低置信 cell 必须进 [`how-to-resolve-phase1-ambiguity.md`](./how-to-resolve-phase1-ambiguity.md) §A.4 OCR 低置信 cell 追问。

## 边界情况

### 输入完全无产品提及

**触发条件**：

- 自由文本里只有客户信息 / 业务描述，无任何产品 token
- 例：`帮我看看这个客户能做什么报价方案`

**处置**：

- 不进 A.0 归一化
- 提示用户："您的输入未识别到具体产品。请提供产品清单 / Excel 附件 / 自由文本中明确说明产品。"
- **不落盘** phase1.md（不算流程违规，是输入不完整）

### 多个版本号 / 重复产品提及

**触发条件**：

- 同一产品在自由文本里被多次提及（如先后说"5 台 CVM"和"再加 3 台 CVM"）

**处置**：

- 合并为一行虚拟表格行，数量取**累加**（5 + 3 = 8）
- 在 update_history 留 init 备注："数量来自多次提及合并"

### 输入是 JSON / YAML

**处置**：

- 视为**结构化数据**，等同于表格类
- 跳过 A.0，直接按 JSON/YAML 字段名做 A.1 列级语义分类

## 自检（A.0 出口前）

| 自检项 | 通过标准 | 不通过的处置 |
|-------|---------|-------------|
| 虚拟表格至少含 1 行 | 行数 >= 1 | 终止流程（输入未识别到产品） |
| 每行有 IDENTIFIER（产品名） | 每行产品名列非空 | 重做 Step 1（产品提及识别） |
| 低置信 cell 已标记 | OCR 输入下 `low_confidence_cells` 非空 | 重做 Step 1 |
| `step_input_normalized=yes` 已记录 | 准备写入 phase1-done | - |

---

## 与下游的衔接

A.0 完成后产出虚拟表格 + `step_input_normalized=yes`；A.1 启动时用虚拟表格当作输入，与表格类输入走同一套算法。

下游 phase1-done 标记的 `step_input_normalized` 字段值：

- `yes`：A.0 触发了归一化
- `no`：A.0 跑了但发现是表格类不需要归一化（理论上 A.0 入口判断已经跳过，这种值少见）
- `n/a`：表格类输入，未触发 A.0

---

## 反模式

- ❌ 自由文本输入跳过 A.0 直接做"产品行解析"（容易丢字段、漏拆产品）
- ❌ OCR 输入不标记低置信 cell，直接当确定值传到下游
- ❌ 邮件正文 vs 附件冲突时擅自取舍（应附件优先 + 正文补充）
- ❌ A.0 阶段做规格展开 / 地域笛卡尔积（这是 B.3 / B.4 的职责，A.0 只做"列化"）
- ❌ 把 JSON / YAML 当自由文本归一化（结构化数据应直接进 A.1）
