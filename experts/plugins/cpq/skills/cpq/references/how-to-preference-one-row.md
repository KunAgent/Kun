# 针对老商品库（spu_id）产品进行精细配置优惠。

## 前提条件

- 已通过折扣计算或其他方式获得了部分产品的优惠数据
- 如果没有一个产品拥有优惠数据，就**跳过本步骤**

## 先过滤分流：批量处理无条件行，逐行精配带条件行

设置优惠前，先把全单**有优惠数据的产品**按优惠信息形态过滤分流成两组，分别处理：

| 优惠信息形态                                                                                      | 归组                     | 处理步骤                  |
| ------------------------------------------------------------------------------------------------- | ------------------------ | ------------------------- |
| **仅含折扣值**（如 `8折`,`80%`,`0.8`），**或仅含一口价**（如 `5元`,`5元/月`），且不带任何附加条件 | **A 组 · 无条件单一值**  | **第一步 · 批量写入**     |
| **含折扣值 / 一口价以外的任何条件**（地域、多档策略等），**或同一行含多个不同优惠值**             | **B 组 · 带条件 / 多值** | **第二步 · 逐行精细配置** |

本流程是**一条有序流水线**：先把 A 组所有行用一次批量写入（第一步），再逐个对 B 组行做逐行精配（第二步）。若 A 组为空则直接从第二步开始，B 组为空则只跑第一步。

> 🚫 **铁律 · 分流即安全闸**：优惠描述出现任何限定维度（地域、可用区、时长、规格、档位…）即为条件型，一律入 B 组；即使所有条件下优惠值相同，也不能分入 A 组。把带条件 / 多值行误判进 A 组批量，等于绕过第二步的逐行精细配置，是本流程最危险的错误。

## 取值铁律（A / B 组通用）

分流铁律决定「行进哪组」，取值铁律决定「值怎么写」。

> 🚫 **铁律 · 不支持优惠的产品必须跳过**：优惠信息为「产品不支持优惠申请」时，**不设置 `preference` 字段**，直接跳过该行。强行设置会导致 CPQ 报错「未获取到有效的优惠策略」。注意：「10 折」**不是**"不支持优惠"，而是设置 `{"preferenceType":"discount","value":100}`（= 原价 = 不打折）。

> 🚫 **铁律 · 折扣值精度不可损失 + 必须消除浮点尾差**：折扣统一按「折数 × 10」表达：6.5 折 → `65`、3.919 折 → `39.19`、2.61 折 → `26.1`。**转换必须用 `round(float(折数) * 10, 6)`**——`round` 不可省略（不 round 会产生 `26.099999999999998` 这样的浮点尾差，CPQ 会拒绝）。**禁止拆分整数部分和小数部分分别处理**（拆分会导致 `6.5折→60.5`、`3.919折→30.919`）。

> 🚫 **铁律 · 折扣值小数长度不能超过 7 位**：CPQ 系统对 **discount**（折扣）字段有硬限制——**小数部分最多 7 位**（submit 时校验）。一口价（fixedPrice）不受此限制。

> 🚫 **铁律 · 带条件优惠必须用 policyList**：
> - 源数据含"地域"、"可用区"、"服务区域"、"规格"等条件词，或含"策略1"、"策略2"等多策略时，**必须**用 `preference` 字段 + `policyList`（完整格式），**禁止**用简写的 `{"preferenceType":"discount","value":85}`（简写会丢失条件，变成全量生效）
> - **禁止**只提取第一条策略的折扣值——必须解析每一条策略的条件和值，构建完整的 `policyList` 数组

> 🚫 **铁律 · 禁止合并策略**：即使多条策略的折扣值相同，也**必须逐条写入 policyList**，一条策略对应一条 policy。
> - ❌ 禁止：源数据 68 条策略（每条 1 地域、同折扣），合并为 1 条 policy + 68 个地域数组
> - ✅ 正确：源数据 68 条策略 → policyList 有 68 条 policy，每条 `{"conditions":{"1":"gz"},"value":60}`
> - 理由：CPQ 系统按 policy 粒度展示和管理优惠，合并后无法还原原始的逐地域策略结构

## 分流门控（不可跳过）

> 🚫 **铁律 · 分流结果必须先展示再执行**：在执行第一步和第二步之前，必须先完成分流并输出分流清单：
> - A 组（无条件单一值）: N 个产品
> - B 组（带条件/多值）: M 个产品
> - 跳过（不支持优惠）: K 个产品
>
> **B 组数量 > 0 时，禁止把 B 组行的优惠用 preference 简写处理**——这是最常见的"偷懒"错误，简写会导致系统自动展开全部地域（把"贵阳 6.5折"变成"全部 37 个地域 6.5折"）。B 组必须走第二步的 policyList 完整格式。
>
> **关键判定规则**：即使源数据只有**一条策略、一个折扣值**，只要优惠文本中出现了"地域"/"可用区"/"服务区域"/"规格"/"策略"任一词，就**必须入 B 组**使用 policyList。
> - ❌ 错误：源数据"策略1 地域：贵阳，6.5折" → 用简写 `{"preferenceType":"discount","value":65}` → 结果：全部地域都被设为 6.5折
> - ✅ 正确：源数据"策略1 地域：贵阳，6.5折" → 用 policyList `{"preferenceType":"discount","policyList":[{"conditions":{"attr_id":"gy"},"value":65}]}` → 仅贵阳 6.5折
>
> **判定关键词**：优惠文本中出现以下**任一词**即为 B 组：`策略`、`地域`、`可用区`、`服务区域`、`规格`、`指定价`、`一口价`。即使所有条件下优惠值相同，也必须入 B 组。
>
> **特别注意一口价**：所有含"一口价"的行都是 B 组（因为一口价总是带地域条件的）。
> - `preferenceType` 必须用 `"fixed_price"`（**下划线格式**），❌ 禁止用 `"fixedPrice"`（驼峰，系统不认识会静默丢弃）
> - `value` 必须是一口价的**单价值**（如 `0.00456`），不是折后总价
> - 必须用 policyList + conditions 格式，不能用简写

## 第一步 · 批量写入无条件单一值行（A 组）

> 仅处理分流中判为 A 组（无条件单一值）的产品；若 A 组为空则跳过本步。

1. 将 A 组所有产品的优惠数据组装为单个 JSON 对象（以产品节点 ID 为 key）
2. A 组使用 `preference` 字段的简写格式：
   - 折扣：`{"preference": {"preferenceType": "discount", "value": 85}}`
   - 一口价：`{"preference": {"preferenceType": "fixed_price", "value": 500}}`
3. 使用 `--compress` 压缩传输（`compressed = base64(zlib.compress(json))`）
4. 执行：`row batch-update --compress {compressed} --cpqcode {code}`
5. CLI 会校验并批量执行；若某些行校验失败，根据错误信息修复对应字段后重新执行

## 第二步 · 批量/逐行精细配置（B 组）

> B 组 = 带地域/规格条件的优惠，或含多条策略的行。**必须用 `preference` 字段。**

> ⚠️ **元信息一律现场探索**：该行支持的优惠类型、条件字段 id、可选 code、value 格式，都以该行 `row cat` 的实际返回为准，禁止依赖记忆、文档或其他行。

### B 组批量处理流程

1. 解析源数据中**每一条策略**（策略1、策略2...），提取条件（地域/规格值）和优惠值
2. 通过 `row cat --key preference --id {nodeId}` 查看节点的属性 ID 映射（如地域 attr_id=1 或 2）
3. 构建 `preference` 对象，包含完整的 `policyList`：
   ```json
   {
     "preference": {
       "preferenceType": "discount",
       "policyList": [
         {"conditions": {"1": "gz"}, "value": 40},
         {"conditions": {"1": "bj"}, "value": 50},
         {"conditions": {"1": "sh"}, "value": 45}
       ]
     }
   }
   ```
4. 多个 B 组节点可合并为一个 batch-update JSON，通过 `--compress` 一次性提交

> 🚫 **铁律 · 禁止脚本批量解析**：B 组每行的优惠`读取、拆解、映射、组装`**必须**逐行人工走下面闭环，时间久一点没关系，但**禁止以任何理由编写脚本批量解析优惠文本**。因为 Excel 里的优惠信息是**纯文本、非结构化**，每一行的优惠信息组成方式都不一样，脚本 100% 会解析错误。

按以下 6 步闭环执行，**每一步都不可跳过**：

### Step 0 · 读取该行的优惠配置元数据

`row cat --key preference --id <row_id>` — 返回：支持的**优惠类型**列表、每个类型下的**条件字段**（字段 id、是否必填、单选/多选）、每个条件字段的**可选值 code 列表**。

### Step 1 · 结构化拆解优惠信息

把优惠信息拆成一张 `(条件组合 → 优惠值)` 表：有几个不同的优惠值，`policyList` 就有几条策略，为每个不同优惠值各建独立 policy 并挂上其取值集合。

> 🚫 **差异禁抹平**：同一维度下不同取值对应不同优惠值时，禁止用多数取值的优惠值覆盖少数取值。

### Step 2 · 把条件值映射为合法 code（不得用原始文本）

- 条件值（中文名 / 顿号串）必须逐个在 `row cat` 返回的可选值表里查到 code 后写入。
- 同名条件在不同产品的 attr_id 可能不同，必须各自 `row cat`，禁止跨行复用。
- **非地域条件也必须映射**：如「远端及目的端地域：中国大陆到中国大陆」→ 查 `row cat` 可选值表得 `mainland_to_mainland`，写入 `{"752": "mainland_to_mainland"}`。
- ❌ 禁止：条件值为空（`"conditions": {}`）或条件值留中文名（`"conditions": {"752": "中国大陆到中国大陆"}`）→ CPQ 会忽略条件，导致优惠条件丢失。
- 🚫 **铁律 · 条件值只写 inbox 中明确列出的**：`row cat` 返回的是该产品**所有可选**条件值，但提交时只写 inbox 优惠信息中**实际出现的**条件值。
  - ❌ 禁止：inbox 写了"地域：贵阳"，但提交时把 `row cat` 返回的全部 46 个地域都塞进去
  - ✅ 正确：inbox 写了"地域：贵阳"，只提交 `{"1": "gy"}`（仅贵阳）

### Step 3 · 组装优惠 JSON

按 Step 1 的拆解结果，把每个"优惠值 + 其条件取值集合"组装成一条 policy，**全部放进同一个 `policyList`**（格式见下方模板）。

**老商品库优惠 JSON 模板**

示例1：源数据"策略1 地域：广州，4折；策略2 地域：北京，5折；策略3 地域：上海，4.5折"
```json
{
  "21819_prepay": {
    "preference": {
      "preferenceType": "discount",
      "policyList": [
        {"conditions": {"1": "gz"}, "value": 40},
        {"conditions": {"1": "bj"}, "value": 50},
        {"conditions": {"1": "sh"}, "value": 45}
      ]
    }
  }
}
```

示例2：源数据"策略1 地域：广州、北京、上海，4折"（多地域同折扣，conditions 用数组）
```json
{
  "21819_prepay": {
    "preference": {
      "preferenceType": "discount",
      "policyList": [
        {"conditions": {"1": ["gz", "bj", "sh"]}, "value": 40}
      ]
    }
  }
}
```

示例3：源数据"策略1 地域：广州，一口价 0.00456元/GB/日"
```json
{
  "11243_postpay": {
    "preference": {
      "preferenceType": "fixed_price",
      "policyList": [
        {"conditions": {"1": "gz"}, "value": 0.00456}
      ]
    }
  }
}
```

| 字段                      | 说明                                                    |
| ------------------------- | ------------------------------------------------------- |
| `preferenceType`          | 优惠类型：`"discount"` 或 `"fixed_price"`               |
| `policyList`              | 策略列表，**源数据有几条策略就必须有几条 policy**        |
| `policyList[].conditions` | 优惠条件，key 为 attr_id（通过 `row cat` 获取），value 格式见下方说明 |
| `policyList[].value`      | 优惠值，折扣类型时 40 表示 4 折；一口价类型时为金额（元） |

**conditions value 格式（必须区分）**：
- **单地域/单值**：value 为**字符串** → `{"1": "gz"}`
- **同条件多地域/多值**：value 为**数组** → `{"1": ["gz", "bj", "sh"]}`
- **不同地域不同折扣**：拆成多条 policy，每条 value 为字符串 → `[{"conditions":{"1":"gz"},"value":40}, {"conditions":{"1":"bj"},"value":50}]`

> ⚠️ **最常见错误**：源数据有 3 条策略（策略1/策略2/策略3 分别对应不同地域和折扣），只取第一条的折扣值。**必须逐条解析，全部写入 policyList。**

### Step 4 · 批量提交（全部 B 组行组装完后执行一次）

> Step 0–3 对每个 B 组行依次循环。全部行的 preference JSON 组装到**同一个 items 对象**中。

将所有 B 组行的 preference 数据合并为一个 JSON 对象，通过 `--compress` 一次性提交：

```python
import json, zlib, base64
items = {
  "1000638_postpay": {"preference": {"preferenceType": "discount", "policyList": [...]}},
  "11025_postpay": {"preference": {"preferenceType": "discount", "policyList": [...]}},
  # ... 所有 B 组行
}
compressed = base64.b64encode(zlib.compress(json.dumps(items).encode())).decode()

# 必须先写入文件再通过变量传入
with open('<CPQ_SESSION_DIR>/pref_b_compressed.txt', 'w') as f:
    f.write(compressed)
# 执行: COMPRESSED=$(cat <CPQ_SESSION_DIR>/pref_b_compressed.txt) && cpq row batch-update --compress "$COMPRESSED" --cpqcode {code}
```

> ⚠️ **禁止在命令行中直接用引号包裹 base64 值**（如 `--compress 'eJyt...'`）——base64 中的 `+`、`/`、`=` 等字符会被 shell 转义破坏，导致 `invalid stored block lengths` 错误。必须用文件或变量传入。

> ⚠️ **B 组 `row cat` 并发限制**：同时并行执行多个 `row cat` 时（如用 task 并行），可能导致 CLI 的本地 session cache 损坏（`cpqStore.json 解析失败`）。建议串行执行 `row cat`，或每批间隔 1-2 秒。

若返回部分行失败，根据失败原因修正对应行的 preference 数据后重新提交。

### Step 5 · 批量写后回查（不可省略）

用 `row list --fields preference` 批量读回 B 组各行的优惠信息，逐行逐项核对：

- `conditions` 非空（条件型优惠的条件数组不得为 `[]`）；
- 每个条件值都是合法 code（非中文名、非顿号串、非空）；
- `policyList` 策略条数 = Step 1 拆出的"不同优惠值个数"；
- 每条 policy 的取值数量与优惠描述一致（无遗漏、无被覆盖）。

任一项不符 = 配置失败，修正后重提；**未回查不得宣布配置完成**。

## 常见错误形态对照

> 本表仅针对**第二步 B 组（带条件 / 多值行）**，A 组无条件单一值行不适用。全为结构示意，`<...>` 为占位符；真实字段 id / code / value 一律以该行 `row cat` 返回为准，不要照抄占位符。

| 失败模式          | ❌ 错误形态                                            | ✅ 正确形态                                                                       |
| ----------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 丢条件维度        | `conditions:[]`、`value:50`（明明限定了取值）          | `conditions:{"<字段id>":["<code1>","<code2>"]}`、`value:50`                       |
| 同维度差异抹平    | 所有取值塞进一条、统一 `value:80`（少数取值其实是 50） | 两条 policy：多数取值 `value:80` ＋ 少数取值 `value:50`                           |
| 原始文本当 code   | `value:["广州、上海、北京"]`（整串 / 中文名直接塞）    | 逐个映射展开 `value:["<广州code>","<上海code>","<北京code>"]`                     |
| 循环写入覆盖      | 把同一行拆成多个 json / 分多次提交、每次只放一个取值   | 所有 policy 组装进该行同一个 json、一次批量提交                                   |
| 写后不查 / 空条件 | 写完即宣布完成；回查发现 `conditions:[]`               | `row list --fields preference` 批量回查：conditions 非空、code 合法、策略数对得上 |
