# Winback 友商产品对标

> **段定位**：本文是 **B 段（友商产品对标）** 的运行时说明。**触发条件**：A 解析出 `phase1.md` 末行 `phase1-done` 的 `competitor>0`（有友商行）；无友商行时主 agent 跳过 B（并在 `context.md` 标 `b_status=skipped(no_competitor)`）。**产物**：`<CPQ_SESSION_DIR>/phase2.md`。**gate**：`node scripts/check-phase2.mjs --session-dir <CPQ_SESSION_DIR>` exit 0（校验 site / 摘要五要点 / `phase2-done` 计数自洽）。**下游**：腾讯云对标产品进入 C（选品）/ D（询价）。

将友商云产品配置清单转换为腾讯云对标方案，生成面客材料。**委托对象按 site 分叉**：

- `site=cn` → 委托同 plugin 下的 **cloud-mapping** 技能（含字典查询 + migraq 兜底）
- `site=intl` → 委托同 plugin 下的 **cloud-mapping-intl** 技能（仅字典查询；字典未命中直接 `unresolved`，**禁止 migraq 兜底**）

再由本流程组装面客输出。

> **site 上下文来源**：从上游 `<CPQ_SESSION_DIR>/phase1.md` 首行 `<!-- site: cn|intl -->` 读取。若该标记缺失或本流程未确定 site，必须停止并提示主流程补齐启动判断 0。

## 核心原则

1. **数据即真值**：所有对标关系只能来自委托技能的映射结果。
   - `site=cn`：映射结果可能是字典 `dict:*` 或 migraq 兜底 `migraq(session:*)`
   - `site=intl`：映射结果只可能是字典 `dict:*`；字典未命中即 `unresolved`，禁止以任何方式调用 migraq（`cloud-mapping-intl` 红线 #2）
   - 即使"知道"某个友商产品对应我方哪个产品，也绝对不得使用自身知识填充。映射结果为 `unresolved` = 无对标 = 填 `-`，没有例外
2. **批量处理**：所有产品一次性提交给所选委托技能的流程，禁止逐个产品分开调用
3. **站点隔离**：site=cn 时不得读 `../cloud-mapping-intl/` 的字典；site=intl 时不得读 `../cloud-mapping/` 的字典。两个字典覆盖范围不同，混读会得到该站点不可售卖的规格
4. **面客友好**：最终输出中不得出现"映射""grep""查询""命中""覆盖""参考数据""数据库""dict:""migraq"等技术词汇，也不得出现文件路径。产品名称使用我方官方名称

## 策略定义

| 策略     | 含义                       | 选型倾向                                         |
| -------- | -------------------------- | ------------------------------------------------ |
| 性能对等 | 规格对等替换               | 同代或更高代次、同类型机型，保证性能不降级       |
| 成本优先 | 满足基本需求前提下降低成本 | 性价比更高的机型（如 SA 系列 AMD），可跨类型映射 |

映射数据中每条记录标注 `策略：标准推荐`（对应性能对等）或 `策略：成本优先`。

### 意图识别

| 判定结果     | 用户信号词                                         | 后续动作                   |
| ------------ | -------------------------------------------------- | -------------------------- |
| **性能对等** | "性能对等""标准推荐""不降配""1:1 替换""性能优先"   | 锁定为性能对等             |
| **成本优先** | "成本优先""降本""省钱""低成本""预算有限""性价比"   | 锁定为成本优先             |
| **待定**     | "生成对标清单""Winback 方案""帮我对标"等无偏好信号 | 标记待定，完成映射后再确认 |

上述仅为示例，实际识别应关注用户的**业务意图**而非逐词匹配。

## 工作流

### 步骤一：解析友商清单

逐条解析友商配置，提取：

- **产品类别**：友商产品名（ECS、OSS、Redis 等）
- **规格族**：友商实例规格族标识（如 g7、c7、r7 等）
- **核心规格**：vCPU 核数、内存 GiB
- **磁盘**：磁盘类型（如 ESSD PL0）与容量
- **地域**：部署地域
- **售卖模式**：从原始产品描述、规格描述、备注或行描述中提取预付费 / 按量计费 / 后付费 / 包年包月 / 竞价 / 包销 / 预留等收费模式描述；未识别到填 `-`
- **数量**

> **伴生 SPU 必须独立成行**：解析出的"磁盘（系统盘/数据盘）"、"公网带宽 / EIP"等字段，在腾讯云属于**独立产品 SPU**（CBS、EIP、BWP），必须按 [how-to-identify-companion-products.md](./how-to-identify-companion-products.md) 拆成独立行进入 Phase 1 临时清单，**不要合并写入 ECS / EC2 主行的配置摘要**。本步骤一在 Phase 1 阶段就应当完成拆分，本节"提取字段"只是声明哪些信号词需要被识别，最终的临时清单形态以 Phase 1 文档为准。

### 步骤二：委托规格映射（按 site 分叉）

将步骤一解析出的所有友商产品规格，按 site 分叉到对应技能批量映射。**不再手工 grep 数据文件**——直接遵循目标技能 SKILL.md 定义的流程。

#### 步骤二（site=cn）：委托 cloud-mapping

1. **读取 cloud-mapping SKILL.md**（`../cloud-mapping/SKILL.md`）了解完整映射工作流
2. **执行 migraq 环境预检**（Step 0）
3. **逐条解析规格要素** → 按字段查询 cloud-mapping 字典
4. **以下情形均必须调用 migraq 兜底**（批量合并，≤15 条/批）：
   - 字典完全未命中的条目
   - **字典 1:N 命中且无优先级的条目**（如 `disk.md` 多 CBS 类型候选、`region.md` 多腾讯云地域候选等没有"策略：标准推荐 / 策略：成本优先"标签的多候选场景）
5. **输出标准化 4 列表格**

> cloud-mapping 字典位置：`../cloud-mapping/references/data/cloud-mapping/`
> cloud-mapping 脚本位置：`../cloud-mapping/scripts/`

**关键约束**：

- grep 字典时**不要过滤策略**，完整保留 `策略：标准推荐` 和 `策略：成本优先` 两种结果
- cloud-mapping 返回的 `备注` 列中包含映射来源（`dict:*` / `migraq(session:*)` / `unresolved`），用于后续步骤判断

#### 步骤二（site=intl）：委托 cloud-mapping-intl

1. **读取 cloud-mapping-intl SKILL.md**（`../cloud-mapping-intl/SKILL.md`）了解完整映射工作流
2. **跳过 migraq 预检**（红线 #2：intl 模式禁止任何形式的 migraq 调用）
3. **逐条解析规格要素** → 按字段查询 cloud-mapping-intl 字典
4. **字典未命中 / 1:N 候选无优先级 → 直接标 `unresolved` 或保留全候选**：
   - 字典完全未命中 → `备注` 列填 `[unresolved] dict_not_found: <源厂商> <源产品/规格> 未在 intl 字典中找到对标`
   - 字典 1:N 命中且无策略标签 → `备注` 列填 `[候选] <列表>`，状态标"待用户选择"
   - **绝对禁止**：跳过候选保留、凭自身知识钦定一个候选、调用 migraq 消岐
5. **输出标准化 4 列表格**

> cloud-mapping-intl 字典位置：`../cloud-mapping-intl/references/data/cloud-mapping/`
> cloud-mapping-intl 脚本位置：`../cloud-mapping-intl/scripts/`

**关键约束**：

- grep 字典时**不要过滤策略**，完整保留 `策略：标准推荐` 和 `策略：成本优先` 两种结果
- cloud-mapping-intl 返回的 `备注` 列中只可能是 `dict:*` 或 `[unresolved]` / `[候选]`，**不可能**出现 `migraq(session:*)`；若出现 = 流程违规，必须返工
- 国际站字典覆盖范围小于 cn（64 款产品 / 18 个地域），`unresolved` 比例会显著高于 cn，属于正常现象，不要为了"凑全"而调用 cn 字典或 migraq

### 步骤三：确认策略

**禁止在映射完成前向用户提问策略偏好**。先完成步骤二，再根据映射结果中实际包含的策略类型判断：

| 情形             | 条件                                     | 处理                     |
| ---------------- | ---------------------------------------- | ------------------------ |
| 用户已明确       | 步骤一已锁定策略                         | 跳过，直接按锁定策略继续 |
| 数据仅含一种策略 | 字典命中的实例映射中仅出现一种策略标签   | 自动采用该策略，无需提问 |
| 数据含两种策略   | 字典命中的实例映射中同时出现两种策略标签 | `askUser` 让用户选择     |

**数据含两种策略时的 askUser 调用**：

```
askUser({
  type: "question",
  question: "对标数据同时包含「性能对等」和「成本优先」两种策略，请选择您需要的方案：",
  options: [
    "性能对等（规格对等替换，优先保证性能不降级）",
    "成本优先（最优性价比，优先降低成本）",
    "两种都要（分别生成两份对标清单）"
  ]
})
```

用户选择后确定最终模式：

- 选择"性能对等"或"成本优先" → **单策略模式**
- 选择"两种都要" → **双策略模式**

### 步骤四：选型决策

基于 cloud-mapping 返回的映射结果进行选型：

1. **映射结果优先**：以 cloud-mapping 返回的 `腾讯云产品` + `腾讯云规格` 为第一依据
2. **代际优先**：多候选时（备注含 `[候选]`）优先选最新代次（S9 > S8 > S6、SA9 > SA5 > SA3）
3. **规格不降配**：vCPU 和内存必须 ≥ 友商配置
4. **策略隔离**（仅适用于带策略标签的字典字段）：
   - 对实例规格族映射（来自 `instance.md`）：按策略标签筛选
   - 单策略模式：仅采用对应策略（`策略：标准推荐` 或 `策略：成本优先`）的映射行
   - 双策略模式：分别从两种策略独立选型，不得混用
5. **无策略标签的 1:N 候选处理**（适用于 `disk.md`、`region.md` 等没有"策略：xxx"标签的字典字段）：
   - **site=cn**：
     - **必须**先按步骤二（cn）第 4 项把这些条目送进 migraq 消岐（绝对不允许跳过 migraq 凭直觉钦定单选）
     - migraq 给出**有业务依据**的单选 → 采用 migraq 结果，备注引用 `migraq(session:<id>)` 并保留依据原文（如"ESSD 无 PL 默认 PL1 → CLOUD_HSSD"）
     - migraq 回复"无法确定"或回答含糊 → 保留全部候选项，备注标 `[候选] <列表>` 并标记状态为"待用户选择"，**禁止**自行从候选中钦定一个
   - **site=intl**：
     - **直接保留全候选**，备注标 `[候选] <列表>`，状态标"待用户选择"
     - **禁止**调用 migraq，**禁止**借用 cn 字典推断，**禁止**凭自身知识钦定（红线 #2 + 红线"禁跨站点取数据"）
   - ❌ 禁止（共通）：在备注中给候选自创"标准推荐 / 成本优先"等字典里不存在的策略标签来伪装已决策
6. **unresolved 处理**：备注含 `[unresolved]` 的产品，结论为 `-`（暂无对标产品）。site=intl 时 `unresolved` 比例较高属正常现象，请在面客材料中按"暂无对标"如实呈现，由用户决定是否手工补充

### 步骤五：验证结论（必须执行，不可跳过）

> **为什么需要这一步**：Winback 流程上下文较长（友商清单解析 + 映射结果 + 策略确认），到此处时早期映射数据可能已被截断或混淆。echo 验证强制逐条核实每个产品的最终结论与实际映射结果一致，防止步骤六凭上下文"印象"填充表格导致对标错误。

使用 `bash` 执行 echo，逐条列出每个产品在确定策略下的结论。此输出是步骤六生成表格的**唯一数据来源**。

**单策略模式**：

```bash
echo "1. <友商产品A> → [unresolved] → -
2. <友商产品B (规格族)> → [性能对等] <腾讯云规格> → <选定规格>
3. <友商产品C> → [unresolved] → -
..."
```

**双策略模式**：

```bash
echo "1. <友商产品A> → [unresolved] → -
2. <友商产品B (规格族)>
   [性能对等] <腾讯云规格> → <选定规格>
   [成本优先] <腾讯云规格> → <选定规格>
..."
```

> 映射结果为 `unresolved` 的产品，结论必须写 `→ -`。

### 步骤六：输出对标清单（Phase 2 中间产物）

**严格根据步骤五 echo 输出的结论生成表格**。步骤五结论为 `→ -` 的产品，表格中我方对标产品和推荐配置必须填 `-`，不得填写任何产品名。

> **格式硬约束**：本步骤的产物**是 Phase 2 中间产物**（落盘到 `<CPQ_SESSION_DIR>/phase2.md` 供 Phase 3 消费），**不是 Phase 4 面客交付物**。必须用 `write_to_file` 直接写**纯 Markdown 表格**：
>
> - ❌ 禁止用 `openpyxl` / `pandas` / `xlsxwriter` 等工具生成 Excel
> - ❌ 禁止写 Python 脚本来生成本文件 —— 直接 `write_to_file` 写 MD 即可
> - ❌ 禁止给中间产物加图例、配色、合并单元格、统计面板（这些只属于真正的 Phase 4 面客交付物）
> - ✅ 增量修改用 `replace_in_file` 改对应行，不重新生成整个文件
> - 完整规则见 [how-to-select-product.md §阶段间临时文件流转契约](./how-to-select-product.md#阶段间临时文件流转契约仅-phase-1--2--25)

> 标题里的"对标清单"指的是 Phase 2 的产出形态，最终是否进入 Phase 4 面客 Excel 由主流程决定 —— 但 Phase 2 阶段本身只产 MD。**生成面客 Excel 前必须读取 [how-to-export-excel.md](./how-to-export-excel.md) 并应用其格式规范**。

**备注列硬约束**：

- **site=cn**：每行的"备注"列**必须**包含映射来源标签之一：
  - `dict:<file>` — 字典直接命中
  - `migraq(session:<id>)` — migraq 兜底命中（无论是字典空白还是 1:N 候选消岐）
  - `[候选] <列表>` — migraq 仍无法判定时保留的候选项，**该行必须配套填"待用户选择"作为补充说明**
  - `[unresolved] <原因>` — 字典+migraq 双重失败
- **site=intl**：每行的"备注"列**必须**包含映射来源标签之一（**禁止出现 `migraq(session:*)`**）：
  - `dict:<file>` — 字典直接命中
  - `[候选] <列表>` — 1:N 候选无优先级且无策略标签时保留全候选，**该行必须配套填"待用户选择"**
  - `[unresolved] <原因>` — 字典未命中（intl 字典覆盖范围有限，此项比例可能偏高）
- 多候选未消岐的条目：在"我方推荐配置"列**禁止**单选钦定，必须列全候选并在备注里标 `[候选]` + "待用户选择"
- ❌ 禁止：备注里出现 `字典里不存在的策略标签`（如 disk.md 字典本身没有"策略：标准推荐"，就不能给磁盘候选编造"标准推荐 / 成本优先"）
- ❌ 禁止（site=intl）：备注里出现 `migraq(session:*)`、跨站点字典路径（`../cloud-mapping/`）、或任何来自 cn 字典的产品/规格条目
