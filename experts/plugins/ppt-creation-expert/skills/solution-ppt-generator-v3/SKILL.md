# 面客解决方案 PPT 生成器（V2）

## 概述

本 skill 专门用于生成**行业面客解决方案演示文稿**。

**文档定位**：基于行业内客户的使用场景，围绕自身产品能力与行业打法，提炼出的满足特定场景需求的解决方案。

**核心目标**：生成一份**能直接拿去面客的专业解决方案 PPT**，内容深度和完整度对标行业头部售前方案水准（30-45页）。

**工作模式**：用户只需给出**行业 + 场景**关键词（如"具身智能AI训练"、"金融风控"、"智慧医疗"），Agent 自动完成：
1. 🔍 **深度研究**：优先通过乐享 MCP 知识库语义检索获取内容，不足时用 `WebSearch` + `WebFetch` 补充，整理为结构化研究素材
2. 🧠 **框架化内容组织**：基于调研报告，按解决方案标准四大板块 + 附录组织内容
3. 📋 **幻灯片规划**：逐页规划 PPT 结构、内容和布局
4. 🎨 **PPT 生成**：调用 `generate_ppt` 工具，将规划和调研报告转化为 PDF 演示文稿

用户也可以额外提供补充材料（PDF/文档/文字），Agent 会将其与调研结果融合。

---

## 核心工作流程

```
需求确认 → 深度调研 → 信息提炼与框架填充 → 幻灯片规划 → 调用PPT生成 → 汇总输出
```

## Phase 1 — 需求确认

### 1.1 意图澄清方式

> ⚠️ **必须使用 `show_form` 工具**进行需求确认，以**选择题**形式让用户快速选择，**禁止使用开放式填空题**。
>
> Agent 应根据用户输入的关键词，先自行推断可能的选项，再通过 `show_form` 呈现给用户选择确认。

### 1.2 需求确认信息

| 信息项 | 说明 | 是否必须 |
|--------|------|---------|
| 行业/场景 | 如"具身智能"、"金融风控"、"智慧医疗" | ✅ 必须 |
| 腾讯云产品 | 方案核心依赖的腾讯云产品线 | ✅ 必须（可从调研推断） |
| 目标客户 | 面向的客户类型 | 可选（调研推断） |
| 目标客户岗位 | 汇报对象的岗位级别：CEO / CTO | ✅ 必须 |
| 客户画像及痛点 | 目标客户的画像描述和核心痛点（支持选填，后续方案围绕痛点展开） | ✅ 必须 |
| 页数要求 | 默认 30-40 页（面客级方案的标准规模） | 可选 |
| 补充材料 | 用户额外提供的 PDF/文档 | 可选 |

### 1.3 show_form 构造规则

Agent 需要根据用户输入的行业/场景关键词，**智能推断候选选项**，然后通过 `show_form` 工具一次性呈现选择题表单。

**构造原则**：
1. **核心问题用选择题**，降低用户输入成本；**客户画像及痛点提供填空框**支持用户选填
2. **每道题提供 3-6 个选项** — Agent 基于行业知识预生成合理选项
3. **必须包含"其他"选项** — 允许用户突破预设范围
4. **可多选的问题标注多选** — 如"腾讯云产品"可能涉及多个产品线

**示例 show_form 构造**（以用户输入"具身智能"为例）：

> **客户画像及痛点的使用规则**：
> - 若用户填写了客户画像/痛点，Phase 3 板块二的痛点内容**必须优先围绕用户填写的痛点展开**，调研补充其他相关痛点
> - 若用户未填写，则由 Phase 2 深度研究自动发现行业通用痛点
> - 板块三的解决方案必须逐一对应板块二中的痛点（包括用户手动填写的痛点）

### 1.4 快速通道

如果用户的初始输入已经非常明确（如"帮我生成一个腾讯云HCC在具身智能AI训练领域的面客方案PPT"），Agent 可以**跳过 show_form**，直接提取关键信息并进入 Phase 2。但如果有任何不确定项，**必须用 show_form 选择题确认，不要用文字追问**。

如果用户提供了补充材料（如 PDF），先提取材料内容，然后在后续调研中说明已有材料的覆盖范围和需要补充的维度。

### 1.5 模板与语言自动路由规则

#### ⚠ 规则一：英文腾讯云模板自动路由

用户 query 命中英文腾讯云模板意图时，**必须**将 template_id 设为 `tencent_cloud_template_en`，并将 PPT 内容语言切换为用户指定的外语（默认英文）。判定条件（满足任一即可）：

- 用户明确要求用某种外语（英语、日语、韩语等）制作

- 用户 query 本身为某种外语（英语、日语、韩语等）

- 用户 query 包含关键词：`国际版`、`英文版`

> 命中此规则时，Phase 5 中 `use_template` 改为 `"tencent_cloud_template_en"`，Phase 2 的 WebSearch 搜索关键词也应使用对应外语构造。

> ⚠️ **全流程语言切换**：当用户 query 本身为英文（或其他外语）时，即使未明确要求英文模板，整个交互流程也必须切换为对应语言：
> 1. **大模型输出**：所有对话回复、说明文字、提示信息全部使用英文（或用户使用的外语）
> 2. **需求澄清**：show_form 的标题、字段 label、选项文案全部使用英文
> 3. **深度研究**：检索 query 和 WebSearch 关键词使用英文构造
> 4. **PPT 生成**：context、planning 内容使用英文输出
> 5. **汇总报告**：最终输出的汇总报告使用英文

#### ⚠ 规则二：页数范围选项约束

页数范围选项**禁止**出现超出实际能力（40页）的具体大区间选项（如"40-50页"、"50-80页"等）。

#### ⚠ 规则三：国际化内容调研路由（命中规则一或涉及海外/出海时触发）

当满足以下任一条件时，Phase 2 调研阶段**必须先筛选出国际版文档范围，后续只在该范围内进行检索和内容生成**：

1. 命中规则一（英文腾讯云模板）
2. 用户 query 涉及海外/出海场景，包含关键词：`海外`、`出海`、`国际化`、`global`、`overseas`、`international`、`海外市场`、`跨境`、`多地区`、`多语言`

**国际版文档判定规则**：

符合以下任一条件的文档视为"国际版文档"：
- 文档内容专为海外市场编写
- 文档内容包含关键词：`global`、`international`、`overseas`、`worldwide`、`cross-border`、`海外`、`全球`、`出海`、`国际站`、`国际版`、`海外版`
- 文档标题为纯英文

**执行流程**：
1. 使用 `mcp__lexiang__search_kb_embedding_search` 进行检索
2. 从检索结果中按上述判定规则筛选出国际版文档
3. 后续所有内容获取和生成**仅限定在国际版文档范围内**，非国际版文档的结果丢弃
4. 将筛选后的内容进行深度研究，整理为 context 传给 `generate_ppt`

### 1.6 用户岗位获取规则

用户岗位**优先从 show_form 中用户选择获取**。若用户选择了"其他"或未明确，则尝试从 `<user_context>` 中的 `work_position` 字段自动映射作为兜底：

**兜底映射规则：**
- **销售**：`work_position` 为"直客销售"、"渠道销售"、"销售支持"
- **架构师**：`work_position` 为"技术咨询"、"行业咨询"、"行业应用"
- **未识别**：若 `work_position` 不在上述列表中，默认按"架构师"处理

> 岗位信息确定后传入 PPT 生成流程，决定使用哪套内容框架（见 Phase 4.2 用户岗位适配规则）。

## Phase 2 — 深度研究

这是本 skill 的**核心驱动环节**。Agent 优先使用乐享 MCP 知识库语义检索，不足时用 `WebSearch` + `WebFetch` 补充，进行系统性深度研究，为四大板块收集充足素材。

### 2.1 调研维度矩阵

针对用户给出的行业/场景，调研需覆盖以下**8个维度**：

| 维度 | 调研目的 | 期望获取的信息 | 对应板块 |
|------|---------|---------------|---------|
| ① 行业趋势 | 市场规模、发展阶段、技术路线 | 市场规模数据、增长率、发展阶段划分 | 板块一 |
| ② 产业链全景 | 上下游企业、核心玩家、产业链结构 | 产业链结构图、头部企业名单 | 板块一 |
| ③ 痛点与挑战 | 客户共性痛点、技术瓶颈、行业难题 | 3-6个核心痛点及其影响 | 板块二 |
| ④ 腾讯云方案 | 腾讯云在该领域的产品、方案、白皮书 | 产品能力、技术架构、官方方案描述 | 板块三 |
| ⑤ 技术细节 | 具体技术方案、架构设计、性能指标 | 技术参数、性能 benchmark、最佳实践 | 板块三 |
| ⑥ 基础设施能力 | 腾讯云底层IaaS/PaaS能力、硬件规格 | GPU规格、网络带宽、存储性能等硬件级数据 | 板块三 |
| ⑦ 竞品对比 | 真实竞品的方案对比、差异化分析 | 友商方案对比、差异化优势（用真实名称） | 板块三 |
| ⑧ 客户案例 | 已公开的客户合作案例、成功故事 | 客户名称、合作内容、量化成效 | 板块四 |

### 2.2 深度研究执行策略

**Step 1：乐享 MCP 知识库语义检索（优先内容来源）**

优先使用乐享 MCP 的 `mcp__lexiang__search_kb_embedding_search` 工具在乐享知识库中进行语义向量检索：

- **前置门禁**：调用 `mcp__lexiang__whoami` 校验 MCP 绑定状态。未绑定/过期时，引导用户通过 `https://lexiangla.com/mcp?company_from=CSIG` 获取 `LEXIANG_TOKEN` 完成绑定，绑定成功后再继续

按以下 8 个维度的 query 框架逐一构造检索 query，批量并行调用 `mcp__lexiang__search_kb_embedding_search`：

```
围绕"{行业}{场景}"进行系统性深度调研，需要覆盖以下方面：

一、行业全景与趋势
1. 行业趋势与市场规模：{行业}的市场规模（最近1-2年数据）、发展阶段、技术演进路线、未来趋势预测
2. 产业链全景：{行业}的上下游产业链结构、头部企业（5-8家）及其核心业务、与云计算的关联

二、痛点与挑战
3. 痛点与挑战：{行业}客户在{场景}场景下面临的核心痛点（3-6个维度）、技术瓶颈和业务挑战

三、腾讯云解决方案与技术能力
4. 腾讯云解决方案：腾讯云在{行业}领域的产品和解决方案，特别是{腾讯云产品}的功能、架构和应用场景
5. 技术细节：{腾讯云产品}的技术架构、性能指标（benchmark数据）、核心技术参数
6. 基础设施能力：腾讯云HCC高性能计算集群规格、GPU型号与性能（H100/H20/A100等）、星脉网络架构与RDMA性能、存储方案（CFS Turbo/GooseFS/COS）性能指标、TCCL集合通信优化数据

四、竞品对比
7. 竞品对比：腾讯云 vs 阿里云/AWS/华为云在{场景}场景的方案对比、性能测试数据对比、差异化优势分析。请提供具体的数字和参数（如带宽、IOPS、延迟、算力规模等），用真实竞品名称，不用"竞品A/B"

五、客户案例
8. 客户案例：腾讯云在{行业}领域的公开客户合作案例、量化成效数据

请重点关注最近1-2年的数据和信息，优先使用腾讯云官方资料和行业权威报告。技术参数请尽量提供具体数字。
```

- **调用参数**：`{"filters": {"keyword": "<query>"}, "limit": 10}`
  - ⚠️ **不要传 `_mcp_fields` 正向选择**：该参数 schema 要求**字符串**类型（非数组），且只接受负向排除路径（如 `"-staffs,-entry.html_content"`），正向选择（`@default` / `chunks.content`）会被忽略并可能触发 `/_mcp_fields: must be string` 校验报错。默认返回即包含正文片段，无需指定字段。
- 汇总所有维度的检索结果，评估内容覆盖度
- 乐享知识库中已有的内容直接采用，无需再搜
- **🔗 溯源链接（参考文档可点击）**：`search_kb_embedding_search` 每个 chunk 都带 `target_id`（即 entry/doc id），可用它反查并拼出可访问的乐享页面 URL，让最终输出的「参考文档」是真链接而非裸标题：
  1. 记录每条采用素材的 `target_id`
  2. URL 规则：`{domain}/pages/{target_id}`。`{domain}` 取 `whoami()` 的 `company.company_domain`；若为顶级域名 `lexiangla.com`，需追加 `?company_from={company_from}`（如 csig 企业为 `https://lexiangla.com/pages/{target_id}?company_from=csig`）；若为三级域名（如 `csig.lexiangla.com`）则无需追加参数
  3. 标题可用 `lexiang_search`（type=doc）按关键词回查 `original_title` 校正，避免凭记忆杜撰标题
  4. 在调研报告/PPT 的参考文档区列出「标题 — 链接」，并提示链接可访问性取决于账号对该知识库的权限
- **📋 全量素材追踪表（强制，边检索边记录，禁止事后凭记忆补写）**：每跑一轮 `search_kb_embedding_search`，**立即**把本轮命中的每条 chunk 逐条登记到一张「素材追踪表」，字段为：`target_id` | 标题（`original_title`）| 命中的调研维度（8 维度中的哪一个）| 采用/弃用。
  - ⚠️ **不可压缩、不可失真**：最终「参考文档」清单必须**如实反映全部被采用的素材来源**（按 `target_id` 去重后通常为十几到几十条），**严禁**只手工挑几条"代表性"来源充当参考清单——那会让读者误以为调研单薄、且无法溯源。
  - 同一 `target_id` 的多个 chunk 片段，去重后算 **1 条**参考文档，但不得整体省略。
  - 若确需精简展示，应在报告中明确区分「核心引用来源（正文 [序号] 标注）」与「全量命中素材清单（附录表格）」两部分，而不是直接砍掉。
- **🔢 正文内联引用（强制，杜绝「不知道哪段参考了哪篇」）**：调研报告正文中，**每一处具体数据、论断、案例、痛点、架构描述都必须在句末或段末标注来源序号 `[n]`**（n 对应文末「全量命中素材清单」的编号），同一段引用多篇用 `[3][4]` 连写。
  - **禁止**把参考文档孤零零堆在文末却在正文里 0 处标注——这会导致读者完全无法溯源「哪段用了哪篇」。
  - 文末清单的每个序号都应能在正文找到至少一处对应的 `[n]`；正文出现的每个 `[n]` 也必须在文末清单有对应条目（双向可对应）。
  - 纯属常识性背景过渡句可不标；凡来自知识库检索的事实性内容一律须标。

> 若乐享 MCP 检索已充分覆盖全部维度，可跳过 Step 2 和 Step 3，直接进入 Step 4。
> 若乐享知识库检索结果不足，进入 Step 2 WebSearch 补充缺失维度。
> ⚠️ 若 MCP 未绑定/过期，**必须先引导用户完成配置**，不得跳过直接使用 WebSearch 替代。流程在此阻塞，直到用户完成绑定或明确表示放弃使用本 skill。

**Step 2：WebSearch 多轮搜索（补充知识库不足的维度）**

- 抓取竞品官方技术文档（用于真实对比数据）

### 2.3 调研执行规则

1. **乐享优先**：优先通过乐享 MCP 检索覆盖 8 个维度，不足的维度用 WebSearch 补充（至少 3-5 轮）
2. **高质量抓取**：对关键页面用 WebFetch 获取详细内容，不依赖搜索摘要
3. **调研不足处理**：如果某些维度信息不足，Agent 在内容规划中标注 `[建议补充]`，并告知用户
4. **补充搜索**：若前几轮搜索缺失关键维度信息，追加针对性搜索轮次补充
5. **国际化场景路由**：若命中 Phase 1.5 规则三，必须先按判定规则筛选出国际版文档范围，后续只在该范围内检索生成，按深度研究正常流程继续

### 2.4 补充材料的处理

当用户额外提供 PDF/文档时：
1. 先提取材料内容
2. 在 WebSearch 时重点补充材料未覆盖的维度
3. 如果材料本身内容非常丰富（如40+页PDF），以材料为主，WebSearch 调研为辅

### 2.5 信息提取要点

从研究结果中提取以下类型的信息：

- **关键数据**：市场规模、增长率、性能指标、成本数据等（必须标注出处，记录数据来源名称/机构/年份）
- **行业观点**：行业发展趋势、技术演进方向（标注观点来源）
- **痛点清单**：客户共性问题、技术瓶颈
- **方案能力**：腾讯云具体产品能力、技术参数、架构特性（标注来源：官网/白皮书/文档）
- **基础设施规格**：GPU 型号、网络带宽、存储性能、集群规模等硬件级数据（标注规格来源）
- **竞品对比**：腾讯云方案 vs **真实竞品**的差异化优势（必须用真实竞品名称，不用"竞品A/竞品B"，标注对比数据来源）
- **案例素材**：客户名称、合作内容、**具体的量化成效**（含测试数据、前后对比，标注案例来源）

> ⚠️ **数据来源追踪**：提取每条数据/指标时，必须同步记录其来源（如"IDC 2025年报告"、"腾讯云官网"、"Gartner 2024"等），这些来源信息将在 PPT 页面中以小字脚注形式展示。

## Phase 3 — 信息提炼与框架填充

将 Phase 2 调研报告中的信息，按**解决方案标准四大板块**进行提炼和组织。

### 最佳实践结构模式

> 以下结构模式提炼自优秀解决方案PPT案例，是经过验证的内容组织方式。

#### 板块一：行业趋势与背景

**整体思路**：通过描述行业趋势、客户在这个场景的痛点，引出方案的必要性和对客户的价值。

**最佳实践内容层次**（参照优秀案例的组织方式）：

```
1. 行业核心概念定义
   → 用一句话定义清楚这个行业/场景是什么

2. 技术发展阶段/时间线
   → 梳理该领域的发展历程和阶段（如：早期基础→技术多样化→大规模爆发→前沿探索）

3. 核心范式与关键技术
   → 该领域的技术架构是什么样的，有哪些关键技术栈
   → 与传统方案的对比（用表格对比维度差异）

4. 行业应用全景图
   → 产业链概览：上游→行业本体→下游应用场景
   → 头部企业/核心玩家（列举 5-8 家代表企业）
   → 企业核心业务域分析（哪些与云计算相关）

5. 典型平台/产品分析
   → 行业内主流平台的功能模块拆解
   → 引出"这些能力背后需要什么基础设施支撑"
```

**关键手法**：
- 用**时间线**展示发展历程
- 用**对比表格**凸显新旧范式差异
- 用**产业链全景图**建立行业全貌认知
- 用**头部企业列表**增强说服力
- 最终自然过渡到"这些趋势带来了哪些挑战"
- 涉及市场规模、增长率等数据引用的页面，在**页面底部用小字标注数据来源**（如"数据来源：IDC 2025"）

---

#### 板块二：需求和挑战

**整体思路**：为了解决痛点，明确关键业务需求、挑战和技术点。

**最佳实践内容层次**：

```
1. 核心痛点矩阵
   → 将痛点归纳为 3-6 个维度
   → 每个痛点用"痛点标题 + 一句话描述"的格式

2. 痛点之间的关联关系
   → 展示痛点之间如何相互影响、叠加
   → 引出"需要一个整体解决方案"的结论

3. 解决路径的暗示
   → 在痛点旁边暗示解决方向
   → 为下一板块的方案做铺垫
```

**关键手法**：
- 用**多列卡片**展示痛点矩阵（3-4 列并排）
- 用**对比箭头**展示"问题→解决方向"
- 痛点数量控制在 **3-6 个**，太多则合并
- 每个痛点都要**对应后续方案中的一个能力**

---

#### 板块三：解决方案

**整体思路**：详细阐述解决方案的整体设计。这是PPT的**核心板块，页数最多**（占总页数 40-50%）。

**最佳实践内容层次**：

```
1. 整体架构总览（1页）
   → 用分层架构图展示方案全貌
   → 典型分层：行业应用层 → 业务框架层 → 训练/推理框架层 → 容器调度层 → 基础资源层
   → 每层列举 3-5 个关键组件

2. 痛点-方案映射页（1页）⭐
   → 将板块二的每个痛点与板块三的具体方案能力一一映射
   → 左侧列出痛点，右侧对应解决方案，箭头连接
   → 让客户直观看到"每个问题都有对应的解"

3. 核心能力详解（按模块逐页展开，每个子能力 1-2 页）
   → 子能力A详解：功能描述 + 技术参数 + 使用场景
   → 子能力B详解：功能描述 + 技术参数 + 与传统方案/竞品对比
   → 每页配合示意图/流程图/对比表格
   → 每个子能力页面必须有至少一个量化指标

4. 能力矩阵总结（1页）
   → 用一张大表格/矩阵图汇总所有能力
   → 标注"开源方案 vs 腾讯优化"对比

5. 基础设施能力（2-4页）⭐
   → 计算能力：GPU集群型号、HCC高性能计算集群规格、算力规模
   → 网络能力：RDMA、星脉网络架构、带宽数据
   → 存储能力：CFS Turbo、GooseFS、COS的性能数据和适用场景
   → 通信能力：TCCL集合通信库、定制优化模块、线性扩展性数据
   → 每页聚焦一个基础设施层能力，必须包含具体的硬件规格和性能数字

6. 性能对比与测试数据（1-2页）⭐
   → 腾讯云 vs 友商的真实性能对比（必须用真实友商名称）
   → 用柱状图/折线图呈现性能测试数据
   → 标注具体测试条件（GPU型号、数据集、batch size等）

7. 差异化优势总结（1页）
   → 提炼 3-5 个核心差异化优势
   → 每个优势附带量化指标（如"性能提升30%"、"成本降低80%"）
```

**关键手法**：
- **架构图用分层布局**表达，每层用不同色块
- **子能力页面采用"标题+要点+图示"三段式**
- **性能数据必须突出展示**（大字号、对比图表）
- **"开源 vs 腾讯优化"对比**是高频手法，增强差异化感知
- 此板块页数最多，但每页只聚焦一个子能力，不贪多
- **基础设施能力必须单独成页**，不能在架构图中一笔带过
- **痛点-方案映射**必须在解决方案板块开头建立，形成逻辑闭环
- 涉及性能指标、benchmark 数据、竞品对比数据的页面，在**页面底部用小字标注数据来源**（如"数据来源：腾讯云官方测试数据，2025"）

---

#### 板块四：客户案例

**整体思路**：通过真实案例证明方案的利益真实性。

**最佳实践内容层次**：

```
每个客户案例页（单客户一页，重点客户可用 2 页）：
  • 客户背景：公司简介、成立时间、核心业务
  • 业务需求：希望解决什么问题
  • 测试/部署方案：使用了什么产品、什么配置
  • 量化成效：性能提升XX%、成本降低XX%
  • 测试数据表格（如有）：GPU型号、batch size、step耗时、加速比等
  • 关键结论：1-2句话总结
  • 前后对比：使用前 vs 使用后的关键指标变化 ⭐

案例墙页（汇总页）：
  • 多个客户卡片网格排列
  • 每卡片：客户名称 + 行业 + 一句话成效
```

**关键手法**：
- 每个案例**必须有量化数据**（性能提升百分比、成本变化等）
- 案例描述遵循 **"背景→需求→方案→成效"** 四段式
- **重点案例必须包含测试数据表格**（含具体测试条件和数值）
- **必须有"前后对比"**：使用腾讯云方案前 vs 使用后的关键指标变化
- 最后一页用**案例墙**汇总，形成"众多客户都在用"的感知
- 案例数量：至少 2-3 个详细案例 + 1 个案例墙
- 案例中的量化成效数据，在**页面底部用小字标注数据来源**（如"数据来源：XX客户公开演讲/腾讯云案例库"）

---

#### 板块五：附录（可选但推荐）⭐

**整体思路**：补充技术参考材料，增强方案的严谨性和专业性。

**内容选项**（根据方案复杂度选择 1-3 项）：

```
1. 技术参数对照表
   → 产品功能/规格对照（腾讯云 vs 友商）
   → 硬件规格汇总（GPU型号、内存、网络带宽等）

2. 产品功能清单
   → 方案涉及的所有腾讯云产品列表
   → 每个产品的核心功能点

3. 行业数据集/标准对照
   → 行业主流数据集横向对比
   → 行业标准/认证信息

4. 部署架构参考
   → 推荐部署架构图
   → 高可用保障说明

5. 联系方式/下一步
   → 商务联系方式
   → 下一步行动计划（POC、试用等）
```

| 板块二：需求挑战 | 8-10% | 2-3页 | 3-4页 |
| 板块三：解决方案 | 40-50% | 12-16页 | 16-20页 |
| 板块四：客户案例 | 12-15% | 3-5页 | 4-6页 |
| 板块五：附录（可选） | 5-8% | 1-3页 | 2-3页 |

**核心原则**：
- 解决方案板块占比最大，是 PPT 的**绝对重心**
- 解决方案板块内，子能力详解和基础设施能力是两大核心
- 板块三页数不足 12 页的方案不合格

**用户岗位适配规则**（自动从 user_context.work_position 获取，决定内容框架）：

- **架构师**：采用完整解决方案框架（30-40页），即本文档 Phase 3 定义的标准四大板块结构不变。在此基础上，板块三中增加"重点产品介绍"子章节（2-3页），对方案核心依赖的腾讯云产品进行单独深入介绍（产品功能、技术架构、核心参数、适用场景）

- **销售**：采用轻量级销售方案框架（15页以内），内容结构为：
  1. 封面（1页）
  2. 目录（1页）
  3. 腾讯/腾讯云介绍：集团概览 + 腾讯云能力概览（1-2页）
  4. 基础设施与资源分布（2-3页）：
     - 若命中国际化规则（规则一/规则三）：海外经验、全球节点分布、资源分布、当地国家/地区优势
     - 若为国内场景：全球节点分布、多可用区能力、本地化服务与合规优势
  5. 行业解决方案概览：初步方案建议（1-2页）
  6. 专业服务能力（1页）
  7. 客户案例 + 案例墙（3-4页）
  8. 结尾页（1页）
  > 销售方案不展开技术细节，侧重展示腾讯云全球能力、行业经验和合作价值

**目标客户岗位适配规则**（从 show_form 获取，决定技术细节深度，仅在架构师框架下生效）：

- **CTO**：板块三完整展开，生成结构不变（子能力详解 5-7 页，基础设施能力 2-4 页，技术参数和性能数据详细呈现）
- **CEO**：板块三精简为概览模式，子能力详解压缩为 1 页（仅展示整体架构和核心差异化优势），基础设施能力 0-1 页，省略详细技术参数；相应增加板块二（业务痛点）和板块四（客户案例/ROI）的页数，突出业务价值和投资回报

### 4.4 布局多样性指导

在 planning 中应体现多种布局类型：

| 内容类型 | 推荐布局 |
|---------|---------|
| 概念定义 | 大字定义 + 下方关键特征卡片 |
| 发展阶段/时间线 | 水平时间线 + 阶段标注 |
| 技术对比 | 全宽表格（维度 × 对比项） |
| 架构图 | 分层横向布局，自上而下，每层不同底色 |
| 产业链全景 | 三栏布局（上游→行业→下游） |
| 市场规模 | 柱状图/折线图 + 关键大数字 |
| 痛点矩阵 | 多列卡片（2×3或3列） |
| 痛点-方案映射 | 左右对应式（痛点→方案） |
| 子能力详解 | 标题+要点+图示三段式 |
| 能力矩阵 | 大表格/多层网格 |
| 基础设施规格 | 核心参数卡片式 |
| 性能对比 | 分组柱状图/对比表格 |
| 数据流/流程图 | 节点+箭头流向图 |
| 客户案例 | 上下二分/左右二分 |
| 案例墙 | 网格卡片（2×3 或 3×3） |
| 关键数据突出 | 大数字+小标签 |
| 左右对比分屏 | 传统方案 VS 腾讯方案 |

**布局多样性规则**：
1. **连续 2 页不能使用相同布局类型**
2. **每5页内至少包含1个数据可视化**（图表、对比表格、关键数字突出）
3. **板块三内必须包含至少 3 种不同的布局类型**
4. **全PPT至少包含 6 种以上不同的布局模式**

## Phase 5 — 调用 PPT 生成工具

### 5.1 调用方式

完成 Phase 4 的 planning 后，调用 `generate_ppt` 工具生成 PPT。

### 5.2 参数构造规则

Phase 2 的研究内容整理为 context 后，按以下方式调用：

```
generate_ppt({
    "planning": "<Phase 4 输出的完整 planning 文本>",
    "context": "<Phase 2 整理的结构化研究内容，2000-4000字>",
    "use_template": "tencent_cloud_template"
})
```

> 注意：由于不使用 deep_research 工具，**不传** `deep_research_report_url` 参数，统一使用 `context` 传入研究素材。

**若用户提供了补充材料**：将材料内容与 WebSearch 研究结果合并整理后，一同作为 `context` 传入。

### 5.3 模板选择

**默认使用腾讯云中文模板**：常规场景下 `use_template` 设置为 `tencent_cloud_template`。

**英文/国际化模板**：若命中 Phase 1.5 规则一，`use_template` 改为 `tencent_cloud_template_en`。

> ⚠️ PPT 工具调用时**必须**传入 `use_template` 参数。中文场景传 `"tencent_cloud_template"`，英文/国际化场景传 `"tencent_cloud_template_en"`。

### 5.4 轮询策略

调用 `generate_ppt` 后需要轮询等待生成完成：

- **首次查询**：建议等待 **15-20 秒**再开始轮询
- **轮询间隔**：建议 **30-60 秒**
- **整体生成时长**：通常在 **20-30 分钟**，需耐心等待，不要频繁轮询
- **状态流转**：`pending` → `running`（多个子阶段）→ `success`
- **子阶段依次为**：规划并搜索配图 → 规划幻灯片结构 → 预生成SVG图表 → 并发生成幻灯片 → 视觉质量检查与修正 → 上传文件

### 5.5 返回结果

从 `generation_result.preview_url` 取链接展示给用户。

### 5.6 planning 质量检查

在传入 planning 前，Agent 须自检：

- [ ] planning 中每一页都有明确的页面类型、标题和内容要点
- [ ] 总页数符合用户要求（默认 30-40 页）
- [ ] 板块三（解决方案）页数 ≥ 12 页
- [ ] 包含痛点-方案映射页
- [ ] 包含基础设施能力页 ≥ 2 页
- [ ] 布局类型多样化（≥ 6 种）
- [ ] 每个客户案例有量化数据要求
- [ ] 所有涉及数据引用的页面都标注了数据来源（小字脚注）

## 特殊场景处理

### 场景一：调研信息不足

某些小众行业/场景可能调研结果有限：
1. 在乐享 MCP 检索和 WebSearch 中使用更宽泛的行业关键词，扩大搜索范围
2. 追加搜索轮次，搜索相近行业的解决方案作为参照
3. 明确告知用户哪些部分信息不够充分，建议用户补充
4. 在 planning 中对信息不足的页面标注 "[建议补充具体数据]"

### 场景二：用户提供了补充材料

当用户额外提供 PDF/文档时：
1. 先提取材料内容
2. 乐享 MCP 检索和 WebSearch 时重点补充材料未覆盖的维度
3. 如果材料本身内容非常丰富（如40+页PDF），以材料为主，深度研究为辅
4. 如果材料已涵盖所有维度，可将材料内容直接作为 `context` 传给 generate_ppt，跳过深度研究

### 场景三：用户指定页数

1. 按 Phase 4.2 的比例分配各板块页数
2. 页数极少（<20）时：减少板块一和板块二的页数，保住板块三，但要提醒用户"面客级方案建议 30+ 页"
3. 页数极多（>40）时：板块三可拆分更多子能力页，板块五附录可扩展
4. **底线**：无论用户指定多少页，板块三（解决方案）占比不低于 35%

### 场景四：非腾讯云方案

如果用户需要的是非腾讯云的解决方案：
1. 调整乐享 MCP 检索和 WebSearch 搜索关键词，搜索对应厂商的产品和方案信息
2. `use_template` 仍然设为 `tencent_cloud_template`（统一使用腾讯云模板）
3. 其余框架不变

### 场景五：海外/出海/国际化方案

当用户需求涉及海外/出海但未命中规则一（即不需要外语输出）时：
1. 仍使用中文模板 `tencent_cloud_template`
2. 但必须触发规则三：按判定规则筛选国际版文档范围，后续只在该范围内检索生成
3. PPT 内容用中文，但检索来源限定为国际版文档

### 场景六：销售岗位方案

当用户岗位自动识别为"销售"时：
1. **跳过 Phase 3 的标准四大板块框架**，改用销售专用框架（见 Phase 4.2 用户岗位适配规则）
2. 页数限制在 15 页以内
3. 乐享 MCP 检索和 WebSearch 搜索侧重：腾讯云全球基础设施、节点分布、行业案例、客户成功故事、专业服务能力
4. 不需要深入技术架构、性能 benchmark、基础设施规格等技术内容
5. planning 中的页面结构按销售框架构造
6. "目标客户岗位"（CEO/CTO）字段在销售框架下不影响内容结构

## 关键约束

1. **信息可靠**：所有内容必须来自调研结果或用户提供的材料，禁止编造数据
2. **标注来源**：所有涉及数据引用的页面，必须在页面底部用**小字脚注**标注数据来源（如"数据来源：IDC 2025"、"来源：腾讯云官网"），planning 中需为每个包含数据的页面标注 `数据来源:XXX`
3. **框架完整**：四大板块必须齐全，附录推荐但可选
4. **方案为重**：解决方案板块（板块三）必须是篇幅最大、最详细的部分（≥12页内容页）
5. **数据突出**：关键指标、性能数据、百分比必须在 planning 中标注需醒目展示
6. **章节清晰**：每个大板块都有独立的章节封面页
7. **案例真实**：客户案例必须基于公开可查的真实信息，必须含量化数据
8. **品牌合规**：必须使用腾讯云模板（`use_template: "tencent_cloud_template"`），确保 Logo 和品牌元素正确
9. **痛点闭环**：板块二的每个痛点都必须在板块三有对应的解决方案
10. **真实竞品**：竞品对比必须使用真实竞品名称和公开数据，不用"竞品A/竞品B"
11. **基础设施独立**：腾讯云基础设施能力（计算/网络/存储）必须有独立的详解页面
12. **布局多样**：planning 中连续2页不能使用相同布局，全PPT至少6种不同布局模式
13. **多轮研究**：优先乐享 MCP 检索，不足时 WebSearch 补充（至少 3-5 轮），对关键页面用 WebFetch 抓取详情
14. **context 传参**：研究内容整理为 2000-4000 字结构化文本，通过 `context` 参数传给 `generate_ppt`
