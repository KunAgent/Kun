# Design-Library Consumption

Use this guidance only when the service supplies selected design-library context. Treat the library as read-only evidence, not as a source of new product scope.

## Apply constraints by authority

- Treat supplied library specifications, tokens, component contracts, composition guidance, and caveats as authoritative for the dimensions they define.
- Apply confirmed product requirements to behavior and content while preserving the library's visual language. Do not reinterpret library constraints to force a preferred style.
- Use configured visual choices only where the selected library is silent or explicitly permits variation.
- Preserve the same core tokens and component language across pages and viewport sizes.

## Plan with real library capabilities

- Prefer components, variants, states, icons, and composition patterns named in the supplied context.
- Record concise semantic component names in the PageMap. Do not copy source markup, CSS, file paths, or long prose into component lists.
- Respect forbidden components, unsupported variants, and documented unknowns. Never turn an unknown behavior into a promised feature.
- When the library lacks a needed component, describe the smallest generic semantic control required by the confirmed journey and align it with known tokens and patterns.
- When restraint or density guidance is supplied, reduce column count and card fragmentation before inventing compact variants.

## Preserve fidelity

- Keep navigation, typography, color, spacing, radius, surface, icon, and interaction conventions consistent throughout the PageMap.
- Reuse a component name for the same role; do not create near-duplicate names page by page.
- Ensure page states and acceptance scenarios cover the library-supported interaction states that matter to the requirement.
- Do not infer business flows from demonstration content, preview examples, or component names.
- Do not modify library resources or claim that a missing asset, component, or behavior exists.

If no design library is supplied, follow the immutable visual configuration and confirmed requirement. Use neutral semantic component names and avoid implying library-specific fidelity.
